# SHA-1 还安全吗

> 你问的是这个决定的关键。直接回答：**对我们这个用途，够用——但必须说清"够用"是什么意思。**

---

## 一、SHA-1 的现状（事实）

| 攻击类型 | 难度 | SHA-1 现状 |
|---|---|---|
| **碰撞**（造两个不同输入，哈希相同） | **已被实际做到** | 2017 年 SHAttered 攻破（约 2⁶³ 次运算，当时约 11 万美元 GPU 成本）；学界后来进一步降低 |
| **第二原像**（给定一个已有哈希，造另一个输入匹配它） | **仍然不可行** | 约 2¹⁶⁰ 次运算 —— **这才是关键** |

**这两者的区别决定了 SHA-1 能不能用。**

- **碰撞**便宜 → 攻击者能造出"一对"内容不同但哈希相同的对象
- **第二原像**昂贵 → 攻击者**没法**针对一个已存在的特定哈希造出匹配的输入

**用一句话说：** SHA-1 能让你"伪造一对新东西"，但**不能**让你"改动已经存在的东西"。

---

## 二、git 自己的态度

- git 从 2005 年至今**默认仍是 SHA-1**（GitHub 上的仓库现在也全是 SHA-1）
- 2017 年 SHAttered 之后，git 做了三件事：
  1. 改用**带碰撞检测的 SHA-1 实现**（`sha1dc`）
  2. **拒绝**包含已知碰撞特征的对象
  3. 加了 `transfer.fsckObjects` —— 传输时校验对象是否完好
- git 已支持 SHA-256 仓库（`--object-format=sha256`），但**没有迁移时间表**，生态也基本没跟上：

| 平台 | SHA-256 仓库 |
|---|---|
| GitHub | ❌ 不支持 |
| Gitea / Forgejo | ❌ 不支持（实测推送直接断开） |
| GitLab | ❌ 不支持 |
| 裸 git 仓库（ssh / 本地） | ✅ 支持 |

## 三、★ 关键：对我们来说，git 层的哈希根本不是信任来源

**这是整件事的转折点。**

```
┌──────────────────────────────────────────────┐
│  记录级信任（这是我们真正的防线）               │
│    sha256(记录内容)  →  prev 串成链            │
│    Ed25519 签名      →  谁写的                 │
│    ★ 全部与 git 无关 —— 把文件拷到任何地方都成立 │
└──────────────────────────────────────────────┘
┌──────────────────────────────────────────────┐
│  git 层（这是运输与协作）                       │
│    commit SHA  →  对象寻址、去重、分发          │
│    tag / 分支  →  协作入口                      │
└──────────────────────────────────────────────┘
```

**任何人 clone 之后跑 `python3 tools/validate`，验证的是下面那条链——它用的是 SHA-256 和 Ed25519。**

**git 用什么哈希方案，不影响这条链的任何一步。**

## 四、把攻击场景套进来（逐个走一遍）

### 场景 A：攻击者造两个不同的 commit，SHA-1 相同

**他能做到**（碰撞是可行的）。

**但对他有什么用？** 他造的两个 commit 都是**他自己带来的**。而：

- 记录里没有他的有效签名 → `p-002` 判失败
- 他改不了别人的记录（改了签名就失效）

**无害。**

### 场景 B：攻击者想针对**一个已存在的** commit 造出同 SHA-1 的替换品

**这需要第二原像攻击 —— 不可行（2¹⁶⁰）。**

**所以他没法"替换"你已有的历史。**

### 场景 C：★ 唯一真实的攻击路径

**同一个作者**（有合法私钥）这样做：

1. 造两份内容不同的记录，**它们的 git commit SHA-1 相同**
2. 提交无害的那份，被合并
3. 事后把有害的那份换进去 —— commit 哈希对得上，看不出改过

**这条路怎么被堵住：**

- **两份记录的记录级哈希不同**（因为是 SHA-256，碰撞概率可忽略）
- 有害那份的 `hash` 与 `sig` **对不上** → `p-001` 和 `p-002` 都判失败
- 而且 `prev` 链会断

**所以即使 git 层被骗过，记录层仍然会拆穿它。**

**★ 而且这条路径的前提是：这个人本来就有合法的签名权。他不是在"篡改历史"，是在"用自己身份的两种版本"。** 这已经不是密码学问题，是人的问题。

---

## 五、结论

**对我们：SHA-1 在 git 层是可接受的。**

理由不是"SHA-1 还安全"，而是：

> **git 层不是我们的信任边界。** 真正的边界是记录级的 SHA-256 哈希链加 Ed25519 签名，
> 而它能被任何人独立复算 —— 不依赖任何平台、不依赖 git 的哈希方案。

**代价说清楚：** commit 哈希本身只有 SHA-1 的抗碰撞强度。这意味着**git 层不是密码学意义上的强证据**。但它不需要是 —— 它是运输工具。

## 六、要额外加固的话，加这三样（都是零成本或低成本）

| # | 做法 | 作用 |
|---|---|---|
| 1 | `git config transfer.fsckObjects true` | 用 git 自带的碰撞检测，传输时拒绝坏对象 |
| 2 | `git config fetch.fsckObjects true`（接收端） | 同上，取的时候也查 |
| 3 | **周期签名 tag** | 把当期链尾钉住 —— 这是**独立于 git 哈希**的时间锚点 |

**第 3 条最重要，而且我们本来就要做。** 签名 tag 是对 tag 指向的 commit 签名，同时 tag 的说明里写入四份文件的链尾哈希（那是 SHA-256）。

**于是：即使 git 的 SHA-1 被完全攻破，篡改者也没法伪造你的 tag 签名。**

---

## 七、什么时候该重新考虑

| 触发条件 | 那时该做什么 |
|---|---|
| 主流 forge 支持 SHA-256 | 迁过去（git 有 `git-filter-repo` 之类的转换路径，但要重写全部历史） |
| 有人开始用碰撞攻击实际作恶 | 立刻迁，或改用"只锚裸 git 仓库 + forge 只做协作" |
| 这个池子变得值钱到值得攻击 | 重新评估（但现在它值钱的地方是内容，不是 commit 哈希） |

**现在不是那个时点。** 而"记录级 SHA-256 + Ed25519"这个设计，让那一天的代价小很多——因为**核心证据不在 git 里**。

---

## 八、一句话

> **SHA-1 的原像是安全的，只有碰撞被攻破。**
> **碰撞让攻击者能"造一对新东西"，但没法"改已有的东西"。**
> **而对我们来说，git 层的哈希只是运输工具 —— 信任建立在记录级的 SHA-256 和 Ed25519 上，那部分不受影响。**
> **所以：改用 SHA-1，同时打开 git 的碰撞检测，并且按计划打签名 tag。**

## 附录：最终决定（2026-09-16）

**决定：git 层用默认的 SHA-1，不用 `--object-format=sha256`。**

### 决定依据

1. **实测确认：SHA-256 仓库无法推送到任何主流 forge。**
   - GitHub：不支持
   - Gitea：报 `fatal: 接收端不支持这个仓库的哈希算法`
   - GitLab：不支持
   - 只有裸 git 仓库（本地 / ssh）支持

2. **我们的信任链不依赖 git 的对象格式。**
   - 记录级：`sha256(记录内容)` 串成链
   - 归属级：Ed25519 签名
   - 这两者与 git 用什么哈希方案**完全无关**，把文件拷到任何地方都成立

3. **不做的代价是零。** 记录哈希仍然是 SHA-256，签名仍然是 Ed25519。

### 配套加固

- `transfer.fsckObjects` / `fetch.fsckObjects` / `receive.fsckObjects` 全部打开
  （用 git 自带的碰撞检测，传输时拒绝坏对象）
- **周期签名 tag，且 tag 说明里写入四份文件的 sha256 链尾哈希**
  —— 这是独立于 git 哈希的时间锚点。即使 git 的 SHA-1 被完全攻破，
  篡改者也没法伪造 tag 签名。

### 将来若要迁移

等主流 forge 支持 SHA-256 时再迁。届时 `data/` 里的记录**不需要重签**——
因为签名覆盖的是记录内容，不是 git 对象。
