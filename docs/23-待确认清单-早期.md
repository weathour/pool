## 零、先把"两个中心"的区别写清楚（因为它是后面所有问题的根）

| | 仓库层 | 平台层 |
|---|---|---|

## 一、真阻塞：先要答案才动手（4 条）

### Q1 ★ 平台是"信息撮合"还是"承担结果"？

这是**本轮最重要的一条**，因为它同时决定技术复杂度、法律形态、和要不要结算。

| 选项 | 平台做什么 | 后果 |
|---|---|---|
| **A. 只提供接触面** | 发布需求/提议，双方自己联系，责任在当事人 | 最轻。**基本不碰中介责任**。但也不产生任何收入 |
| **B. 撮合并收费** | 成功匹配后平台收费 | 进入"中介/居间"的形态，有明确法律要求 |
| **C. 承担结果** | 担保质量、托管资金、裁决争议 | 最重。接近"平台责任"，需要实体、需要资金托管、需要争议机制 |

**我的建议：先做 A，把 B 留成"以后再说"。** 理由：A 已经能验证核心假设（陌生人能不能靠记录对接），而 B 和 C 的全部复杂度都是为收入服务的——**在没验证"有人用"之前，不值得引入。**

**这条不定，招募板的技术和法律设计都写不了。**

### Q2 ★ 钱在平台上走不走？

- 如果 Q1 选 A：**平台上不发生金钱往来**，劳务契约在线下签，平台只留"谁和谁对接过"的记录
- 如果 Q1 选 B/C：需要收款通道 → 需要主体 → 需要税务 → 需要争议处理

**我的建议：第一阶段平台上不走钱。** 这条和 Q1 联动，但就算 Q1 选 A，你也要明确**"平台上禁止直接标价"还是"允许标价、只是平台不经手"**——这两个差别很大。

### Q3 公开性的边界（结构和 §5.2 的隐私约束是同一个问题）

| 层 | 三个选项 |
|---|---|
| **仓库公开度** | ① 全公开（含原文） ② 只公开结论+锚点，**原文不上线** ③ 只公开方法，不放内容 |
| **平台公开度** | ① 谁都能看 ② 只有登录/邀请的人能看 ③ 需求公开、接单者隐藏 |
| **申请记录公开度** | ① 全公开（含双方 ID） ② 公开成交、隐藏失败 ③ 只公开统计数字 |

**我的建议：②/①/②。** 理由：原文涉及 B 站版权（这是硬约束，不是我保守），**结论和锚点是你们自己的**；需求公开才可能有人接；失败的申请不公开，避免"被拒=丢脸"导致没人敢提。

### Q4 法律形态

按 Q1 的答案分岔：

- Q1 选 A：**可以是个人项目 + 免责声明**，风险最低
- Q1 选 B/C：必须考虑**实体注册**（境内个体户/公司，或境外实体，看客户在哪）

**米波大神第一轮问的"会不会违法"，按现在的读法是这个设计的第一个硬约束，被当成小事跳过了。** 我需要你给一个明确答复：**要不要为这件事做法律咨询，还是先按 A 走、根本不碰？**

## 二、仓库层：关于维护者（4 条）

### Q5 维护者几个人？

- **A. 一个（当前就是 weathour）** —— 你和雁雁说的"需要中心"就是这个意思
- **B. 每个板块一个维护者**（语料、工具、经验文档分开）
- **C. 不设人，只设规则** —— 我不同意这个，仓库确实需要一个能判断"这个该不该进去"的人

**我的建议：A 起步，但把"板块"这个概念先留着。** 因为你说的"板块维护者"暗示你已经在想多板块了——**那就要提前说清：板块之间的冲突谁裁？**

### Q6 ★ 维护者缺席怎么办？

这是**唯一一个不问就会出事的问题**。

- 连续 N 天没响应，是自动授权某人代管，还是就停着？
- 维护者生病/失联/失去兴趣，谁接管？**写在哪儿？**
- 有没有"备位维护者"这个角色？

**我的建议：设一个备位。** 不用复杂，就在 README 里写"若维护者 30 天未响应，由 X 接管并公示"。**成本是一行字，收益是仓库不会因为一个人的意外而归零。**

### Q7 维护者的权力边界：写入权和删除权必须拆开

- **写入权**：什么进仓库
- **删除权**：什么出仓库（这条危险得多）

**我的建议（直接照搬 ismism 自己的纪律）：只追加，不删除。** 要改就写一条 amend，保留原记录。这条纪律那个仓库已经跑了四个月，**它同时防了"维护者乱删"和"维护者被质疑时无法自证"。**

### Q8 维护者能不能被约束？

- 维护者的判断要不要**写理由**？（ismism 的审查条目已经这么做了）
- 别人能不能**对维护者的决定提异议**？走什么流程？
- 维护者自己犯了错，谁能改？

**我的建议：决定必须写理由（已有先例），异议走"挂号"制（提出来就进队列，维护者必须回应，哪怕回应是驳回）。** 这条不引入任何权力结构，只引入"必须回应"的义务。

## 三、平台层：关于形式（3 条）

### Q9 ★ "协作申请"的原子单位到底是什么？

这决定整个记录格式。

| 选项 | 例子 |
|---|---|
| **A. 需求**（我要什么） | "我需要有人帮我把这批 PDF 转成带锚点的记录" |
| **B. 提议**（我想做什么） | "我想做一个 XX 方向的整理，有人一起来吗" |
| **C. 两者都有，分开记** | 需求板和项目板两个列表 |

**我的建议：C，但先只做 A。** 因为**需求天然比提议容易成交**——提议要说服别人相信它值得做，需求只要有人有空就能接。**先做容易的，验证"陌生人能不能对接"这个核心假设。**

### Q10 申请和接单记录里，最少要记什么？

我建议六个字段（和知识包同构，便于将来合并成同一种记录）：

```
提出人 / 时间 / 内容 / 期望的产出 / 接单人 / 结果（完成 / 未完成 / 撤回）
```

**★ 这里有个必须你定的：失败和撤回要不要记？**

- 记 → 能看出"谁老是提了不做"，但会让人不敢提
- 不记 → 干净，但无法识别空转

**我的建议：记，但只在统计层公开，不挂人名。**

### Q11 申请能不能匿名？

匿名能让人敢提敏感需求（比如"我想找个懂 XX 的人帮我评估一个我不方便公开的东西"），但**匿名和"可查的记录"直接冲突**。

**我的建议：实名，但允许"需求内容公开、提出人只对维护者可见"。** 折中方案，且可随时收紧。

## 四、记账层（2 条）

### Q12 贡献值的认定标准

上一轮定了两种账（贡献值 / 结算额）。**结算额先不动（因为 Q1 选 A 就没有）。贡献值需要标准：**

哪些算贡献？候选：
- 语料整理（行数 / 条目数）
- 工具代码
- 复核别人的产出
- 回答智库的问题
- 提供算力/资金
- **★ 提出一个好问题算不算？**

**我的建议：算，而且要单独一类。** 理由：这个仓库的整个价值建立在"好问题"上（39 个主题档案都是问题驱动的）。**如果提问不算贡献，这个池子会变成只生产答案不生产问题——而问题才是稀缺的。**

### Q13 衰减怎么记（我上一版提的休眠衰减，需要落到规则）

- 半衰期多久（我默认 180 天，首个周期 365 天试跑）
- 是**时间衰减**（不看活动）还是**活跃度衰减**（有产出就重置）
- 衰减到零之后，记录还在不在（我建议在，只是不计入席位）

**我的建议：活跃度衰减。** 时间衰减会误伤"歇了半年但一直在做的人"；活跃度衰减只惩罚"真的停了的人"。

## 五、还有一件我必须直接问（不是设计问题）

### Q14 你想当维护者吗？还是你只是想让它存在？

这两件事听起来一样，其实差很远：

- **想当** → 那要谈你怎么退出、怎么被约束、做多久
- **只想让它存在** → 那要想的是"谁能当"，以及**你为什么现在非要拉人**

**我上一轮的读法（一个人 4 个月 260 个提交、206 个在最后一个月）暗示的是：那 206 个提交里有一种"必须赶紧做完"的紧迫感。** 紧迫感的来源决定了这个平台该怎么设计——**如果是"怕它随我消失"，那第一优先级是备份和接续；如果是"想找人一起做"，那第一优先级是招人；如果是"想验证这个方法"，那第一优先级是公开。三条路完全不同。**

**这个问题没有标准答案，但你不答，我给不出对的建议。**
