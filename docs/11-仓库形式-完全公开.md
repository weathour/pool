# 回顾初心，重看仓库形式

> 新前提：**完全公开，不分层，内部没有版权。**
> 这一轮的结果是**系统大幅简化**——因为 git 本来就干了我们手工搭的一大半。

---

## 零、先说一件必须说的（只说一次，不劝）

你说内部没有版权，我照你说的做。但有一个事实必须摆在明处：

**仓库是公开的，等于 363 篇 B 站转写是"重新发布"，而不只是"自己看"。**

这不影响你们自己用，也不影响开发。**但它是一个已经做出的选择，不是没发生的事。**

我记得你 09-16 说过"好像人多了得备案……那也是小事，又不造反"。**这个判断的逻辑和这里是同一个：** 你们按自己的判断承担，我照做。**我只负责让这个选择是"知情的"，不负责替你决定。**

## 一、这一轮最大的发现：整套东西塌缩成"一个带规则的 git 仓库"

这是好消息，而且是**大幅简化**。

因为 git 已经原生提供了我们前面手工搭的一大半：

| 我们前面手工设计的 | git 本来就有 |
|---|---|
| 哈希链（`prev` 串上一条） | **commit 链** —— 每个 commit 的 SHA 覆盖整棵树的当前状态 |
| 不可篡改的历史 | git 历史 + `git fsck` |
| 多人持有的独立副本 | **每次 clone 都是完整镜像** |
| 分发与同步 | `clone` / `fetch` / `push` |
| 周期快照 | **签名 tag** |
| 提案与评审 | **issue / PR / review** |
| 谁改了什么 | `git blame` / `git log` |

**★ 结论：不需要发明协议，需要的是一个仓库 + 一份贡献指南。**

## 二、但 git 有两件事做不到（所以还需要签名）

| git 能做的 | git **做不到**的 |
|---|---|
| 证明**内容**没被改 | ❌ 证明**是谁**写的 |
| 证明**顺序** | ❌ 防抵赖 |
| 让副本互相验证 | ❌ 防止冒充 |

**原因：git 的 commit author 是自己填的字符串，随便写成谁都行。** 而且**改历史只需 `git commit --amend` + `push -f`**（在允许强推的仓库里）。

**所以签名不是可选项，而且它的作用变得更清楚了：**

> **git 负责"没被改"，签名负责"是谁写的"。**
> **两者加起来，才是"防篡改"。**

**★ 由此得出一个重要的简化：schema 里的 `prev` 字段可以去掉。**

因为 **git 的 commit 链就是那条链**。`prev` 是我们为"没有 git 的世界"设计的，而你们的世界有 git。

（唯一保它的理由：数据脱离 git 单独存在时仍可自验。但既然完全公开、随时能 clone，这个理由不成立。）

## 三、修正后的文件清单：从六份降到四份

| 文件 | 状态 | 变化 |
|---|---|---|
| `requests.jsonl` | **保留** | 公告板。`prev` 去掉，`sig` 保留 |
| `deliverables.jsonl` | **保留** | 交付物。同上 |
| `credits.jsonl` | **保留** | 账本。同上 |
| `keyring.jsonl` | 原 `members.jsonl`，**改了性质** | 见下 |
| ~~`cycles.jsonl`~~ | **删除** | 周期结算改用**签名 git tag** |
| ~~`maintainer-log.jsonl`~~ | **保留但简化** | 就是一份 `MAINTAINERS.md` + git log，不需要独立文件 |

### 3.1 `cycles.jsonl` 为什么可以删

它原本的作用是"把六份文件当期状态钉成一个值"。**而一个签名 tag 打在某个 commit 上，已经做了这件事**——commit 的 SHA 覆盖整棵树。

**所以现在的周期结算是：**

```bash
git tag -s cycle-2026-Q4 -m "本周期 12 张单，成案 5 件，打回 3 件"
git push --tags
```

**一条命令，替代一整个文件。**

### 3.2 `members.jsonl` → `keyring.jsonl`：这是概念上的大变化

**完全公开之后，"成员"这个概念就没有意义了**——没有名单要维护，没有准入要审批。

**剩下的唯一需要记录的只有：哪个公钥对应哪个名字（或者说，哪个可以公开的名字）。**

```jsonc
{"pubkey":"ed25519:...", "handle":"雁", "since":"2026-09-16", "status":"active|retired"}
```

**注意：这不是"成员名单"，是"公钥目录"。** 区别很重要：

- 名单 = 有边界，要审批，进不去就用不了
- 目录 = 没有边界，**任何人加一条自己的记录就能开始干活**

**★ 而且"移除"也不需要：** 密钥丢了或人走了，加一条 `status: retired` 就行。**历史记录里的签名永远有效，因为它当时确实是他签的。**

### 3.3 修正后的四份文件

```
data/requests.jsonl       公告板：谁需要什么
data/deliverables.jsonl   交付物：交了什么、谁复核的
data/credits.jsonl        账本：谁该得多少
data/keyring.jsonl        公钥目录：谁是谁（不是成员名单）
```

**除了 git 和签名，不需要任何其他机制。** 这就是全部。

## 四、回忆初心，对照这个形式

先把初心摆出来（前面你认可的那句）：

> **把自己攒下的资料、经验、和处理资料的方法放进一个公共的地方，并且给"想一起做事的人"一个不用互相认识也能对接的入口。**

**两个半句，逐个对照：**

### 4.1 "放进一个公共的地方" —— ✅ 完全公开的 git 仓库，这是最彻底的解法

**而且它直接实现了前面说的那句话：**

> 拉人最有效的办法不是元老院投票，是把仓库挂出去，让方法本身成为筛子。

**现在它变成字面意思了。**

### 4.2 "不用互相认识也能对接" —— ⚠️ 这一半有个新问题

**★ 完全公开反而让"对接"更难了，不是更容易。**

理由很实在：**私人池子里三个人，谁需要什么一眼看得到。公开仓库里没人知道该看哪儿。**

**这就是"公共资源困境"的镜像版：东西全公开，但没人找得到入口。**

**所以仓库形式必须解决"入口"问题。我认为答案是：**

```
① README.md 的第一屏 = 当前公告板
   正在招人接的单 / 刚交付的东西 / 刚被采纳的结论
   ★ 这一屏必须自动生成（从一个脚本产出），不能手写 —— 手写的一定会过期

② 每个结论都带着"它还缺什么"
   ★ 结论里的"反证条件""停止条件"字段，
     本身就是"这里有个没解决的问题"的钩子
   —— 这是现成的、别人能接的入口

③ 经验单独有一个地方
   不是"我做了什么"，是"我踩过什么坑、为什么当时那样决定"
   ★ 这一层现在藏在 reviews/ 里，外部人看不到
   —— 而它恰恰是外部人最需要、也最能说明"这里值不值得来"的东西
```

**★ 第 ③ 条是我认为目前最被忽略的一块。**

你们仓库里有 194 个审查条目、70 对候选/决定——**那是四个月的真实判断过程**。它的价值不在于"结论对不对"，在于**"一个人是怎么在没把握的时候做决定的"**。

**而"资料"是可以复制的，"经验"不能。** 前面你自己说过这句，这里要把它落到仓库结构上：

> **资料在 `library/`（已经很好），经验要单独有一个明确的位置。**

### 4.3 一个新增的、之前没考虑过的点

**完全公开之后，仓库的"入库标准"要重新想。**

之前是内部池子，**入库标准 = "对我们有用"**。
现在是公开仓库，**入库标准 = "对陌生人有用"**。

**这两个标准不一样，而且后者严得多。**

**但这不一定是坏事**——因为"对陌生人有用"正好是"可验证"的自然结果：
- 能不能看懂？（锚点够不够）
- 能不能自己判？（反证条件写没写）
- 能不能接着做？（还缺什么写没写）

**所以入库标准可以简化成一句话：**

> **一份东西能不能进池子，看一个陌生人照着它，能不能自己往下走。**

**这句话同时是入库标准、是验收标准、也是公开的说明书。**

## 五、修正后的整体形式

```
一个公开的 git 仓库
├── README.md              ★ 第一屏 = 当前公告板（自动生成）
├── CONTRIBUTING.md        规则：怎么开单、怎么交、怎么复核
├── MAINTAINERS.md         谁能合并 PR（以及"能推快不能拖慢"的约束）
├── data/                  ★ 四份 JSONL，唯一的真相
│   ├── requests.jsonl
│   ├── deliverables.jsonl
│   ├── credits.jsonl
│   └── keyring.jsonl
├── library/               资料（已有的语料与整理）
├── experience/            ★ 经验（要新建：踩过的坑、当时为什么那样决定）
└── tools/
    ├── validate           校验器（唯一发号施令的地方）
    └── build-index        生成 README 第一屏
```

**循环是这样跑的：**

```
有人开 issue（= 开单）
      ↓
有人提 PR（= 交东西）
      ↓
CI 跑 validate（= 形式检查：签名有效吗？验收标准写了吗？）
      ↓
维护者合并（= 验收）
      ↓
★ 合并进 main = 入库 + 上账，一次完成
      ↓
build-index 重新生成 README 第一屏
```

**★ 注意最后两步：合并就是入库，也是上账。** 不需要第三个动作。

**这是"一切都公开"带来的最大简化：没有"内部资产"和"已发布"的区别，只有"在 main 上"和"不在 main 上"。**

## 六、那机器人还剩什么

**如果 CI 已经跑了 `validate`，机器人（那个定期报告的东西）的工作就只剩一部分：**

| 之前说的机器人功能 | 现在归谁 |
|---|---|
| 校验链、签名 | **CI**（每次 PR 都跑） |
| 过期单、堆积的复核 | **CI 做不到**（它只在有 PR 时触发）→ 机器人 |
| ★ **通过了但没人用的东西** | **CI 做不到** → 机器人 |
| 可能重复的单 | 机器人 |

**所以机器人只剩一件事：定期看那些"没人在动"的地方。** 它依然只需要 cron 一周一次。

**而它最有价值的那条告警（通过了但没人用）现在更重要了**——因为公开之后，**"自己人能验收、外部人不需要"是一个会被公开看见的事实。**

## 八、一句话

> **完全公开之后，整套东西塌缩成"一个带规则的 git 仓库 + 四份 JSONL + 一个校验器"。**
> **git 负责"没被改"，签名负责"是谁写的"——两个加起来才是防篡改。**
> **"成员"消失，只剩"公钥目录"；"周期结算"消失，只剩一个签名 tag。**
> **但公开也让"对接"更难了——所以仓库形式的第一要务不是存东西，是让人找得到入口。**
> **而入口的答案不在公告板，在于把"经验"单独放出来：资料可以复制，经验不能。**
