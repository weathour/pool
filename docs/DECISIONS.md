## 一、架构决策

### D1 · 数据用本地纯文本 JSONL，不用数据库

**决定**：五份 `.jsonl` 文件，append-only，git 管版本。

**为什么**：
- **可读** —— 记事本就能打开，一行一条
- **可搬** —— clone 走就是完整的，不依赖任何服务
- **可验证** —— 行内自带哈希与签名
- **不引入两份真相** —— 数据库最大的诱惑是"存一份算好的结果"，而那正是要避免的

**否掉的方案**：SQLite / Postgres。**否掉的理由**：加上数据库就有了"数据库是真相还是文件是真相"的问题，而且余额会被缓存进去。

**代价（认了）**：查询要全表扫描。**但池子小，扫描就是毫秒级。**

---

### D2 · 只追加，改错靠追加修正记录

**决定**：任何字段变更都是**追加一条同 `id` 的新记录**，并在 `supersedes` 里写被取代那条的哈希。删除 = 追加一条 `void`。

**为什么**：**"改"和"篡改"必须能被区分。** 代码库里 `git commit --amend` 无所谓；账本里它就是事件。

**★ 验证过它真的有用**：我手动编辑 `data/credits.jsonl` 给三条记录加字段，`tools/validate` **当场报 `hash 与内容不符`**。
**"只追加"这条规则第一次拦住的就是作者本人。**

---

### D3 · 签名只覆盖内容，不覆盖 `seq` / `prev`

**决定**：`hash = sha256(canonical_json(记录去掉 seq / prev / hash / sig))`

**为什么**：**这是为了让多人合并成为可能。**

两个人同时追加 → git 冲突 → 需要重排、重链。如果 `seq`/`prev` 参与哈希，重链就会让**所有签名失效**，每个人都得重新签。

**排除它们之后**：重链只改位置，不改内容 → **签名仍然有效，不需要任何人的私钥。**

**★ 实测**：合并冲突 → `tools/resolve --write` → 校验通过，**每条记录的签名都还有效**。

**否掉的方案**：让 `seq`/`prev` 参与哈希（更"严格"，但一旦合并就要全员重签）。

---

### D4 · git 层用默认哈希（SHA-1），不用 SHA-256

**决定**：`git init` 不加 `--object-format=sha256`。

**为什么**：**实测发现 SHA-256 仓库推不到任何主流 forge。**

| 平台 | SHA-256 仓库 |
|---|---|
| GitHub | ❌ 不支持 |
| Gitea | ❌ 报 `接收端不支持这个仓库的哈希算法` |
| GitLab | ❌ 不支持 |
| 裸 git 仓库 | ✅ 支持 |

**用了它就没有 issue、没有 PR、没有 Pages —— 整条协作链断掉。**

**★ 关键判断：信任链不依赖 git 的对象格式。**

```
记录级 = sha256(记录内容) 串成链   ← 仍是 SHA-256
归属级 = Ed25519 签名             ← 仍是 Ed25519
把 data/ 拷到 git 之外，两者照样成立
```

**SHA-1 的安全性**：碰撞已被实证攻破（2017 SHAttered），但**第二原像仍不可行**（约 2¹⁶⁰）。
**碰撞能让你"伪造一对新东西"，不能让你"改动已经存在的东西"。** 而我们的防线在记录层。

**加固**：`transfer/fetch/receive.fsckObjects` 全开 + 记录级 SHA-256 + 周期签名 tag。

---

### D5 · 不上区块链

**决定**：不上链、不发代币。

**为什么**：区块链只提供四样东西，三样不需要，一样是红线。**唯一真正更强的（全局时间戳）已用签名 tag 解决。**

详细论证见 [`02-credit.md` 第四节](02-credit.md)。

**★ 一个具体教训**：我最初设计时想把 `cycles.jsonl` 里记 `merkle_root`，**但签名 tag 本身是提交，会被追加进账本 → 改变链尾 → tag 里记的哈希立刻失效。这是自引用死循环。**
**修法**：tag 不是账本记录，它不改变 `data/`，所以不会使自己失效。

---

### D6 · 治理抄 Linux 的形态，不设元老院

**决定**：`MAINTAINERS.md`（权威）+ `CODEOWNERS`（派生）+ **"能推快不能拖慢"**。

**为什么否掉元老院**：元老院管"谁能进来"，而"进不来人"的真正原因是**没人看得见需求、没人信得过对方** —— 那是**匹配问题，不是审批问题**。

**核心约束**：

| 维护者可以单独做 | 必须第二人 |
|---|---|
| 确认交付物、推进状态、回应异议 | 关单 · 推翻已通过的复核 · 改 credit 认定 |

**★ 为什么这么设计：一个人掌权时最常用、最难防的手段不是乱做事，是不回应。**
所以异议必须 7 天内回应（`p-007`），不回应自动升级。

**没有清退程序** —— 不产出就自然衰减，**让位置自然空出来，而不是把人赶出去。**

---

### D7 · 完全公开，不分层

**决定**：整个仓库公开（67 个文件），只不公开私钥和 `gitea.db`。

**为什么**：**"任何人 clone 就能验证"的前提是校验器和规则也在公开仓库里。**
只公开数据、藏起规则和校验器，等于说"相信我" —— 而那正是整套设计要避免的。

**★ 为什么这没踩版权**：那 363 篇 B 站转写语料在**另一个仓库**（`~/文档/ismism-system`），不在池子仓库里。

---

### D8 · 前端只读，配置不进 `data/`

**决定**：
```
data/*.jsonl       池子发生的事（要签名、要复核）
config/ 或代码      怎么显示（走 PR）
tools/             怎么渲染
```

**为什么**：**如果前端配置也进 `data/`，就成了自指循环** —— 显示的规则来自显示的内容，而内容又要通过显示来管理。

**更实际的后果**：改个配色也要签名 + 复核 + 两个人确认，荒谬。

**判据**：**`data/` 只放"池子里发生的事"。凡是不需要签名的东西（显示设置、布局、样式）都不许进 `data/`。**

**★ 还有一条更隐蔽的纪律**：`data/` 的 schema 只由"什么算一条记录"决定，**不由"前端要显示什么"决定**。
违反它的症状是：想加个 `priority` 字段，而理由是"前端想排序"。

## 二、技术选型

| 项 | 选择 | 为什么 |
|---|---|---|
| 签名算法 | **Ed25519** | 密钥短（能塞进 JSONL 一行）、**没有随机数陷阱**（ECDSA 随机数有偏会直接泄露私钥） |
| 哈希 | **SHA-256**（记录级） | 通用、库成熟 |
| 时间戳 | **签名 tag + `.allowed_signers`** | 密钥不在别人手里就伪造不了；且证明与 git 对象格式无关 |
| 镜像方式 | **本地 `pre-push` 钩子** | 见 L4 |
| 容器化 | **不用**（Gitea 用二进制） | **Docker Hub 在这台机器上连不上** |
| 加密 at rest | **不做** | 数据本来就是公开的；配额成本大于收益。**丢了设备再说** |

## 三、教训（踩过的坑）

### L1 · "事件流里最后一条记录" ≠ "实体当前状态"

**这是最容易踩的一个，我踩了三次。**

| 场景 | 症状 | 修法 |
|---|---|---|
| 开单后被 claim | 标题变成空字符串（claim 记录里没有 title） | `pool.project()` 做累计字段投影 |
| 交付物被 review | ID 生成重复，后一件覆盖前一件 | 计数时按去重后的 id 集合 |
| 交付物被 amend | `links` 读不到（改了之后 `op` 变成 `amend`） | `derive_reuse` 改用 `project()` |

**结论：凡是需要"实体字段"的地方，一律用 `pool.project(records)`，不用 `latest_per_id()`。**

`latest_per_id` 只在两种情况下可以用：**取事件（如"最后发生了什么"）、计数。**

---

### L2 · `--set 'links=["d-x"]'` 被存成字符串

`tools/sign amend --set` 最初直接把值当字符串存。**结果 `links` 变成 `"[\"d-x\"]"` 而不是列表。**

**这种 bug 最阴：不报错，就是静默失效** —— 后续所有依赖 links 的逻辑算不出来，但没人知道。

**修法**：`--set` 先尝试 JSON 解析；`derive_reuse` 加类型防护（**宁可不算，不用脏数据算错**）。

---

### L3 · 环境变量在工具链里会丢

**症状**：`POOL_KEYDIR` 没传进子 shell → `deliver` 用了默认目录里的另一把私钥 → **记录内部自洽，但身份是错的**，旧校验器毫无反应。

**修法**：
1. `p-003` 增加检查：**记录签名者必须与 `deliverer` 是同一把公钥**
2. `tools/sign` 支持仓库根目录 `.env` 兜底
3. `whoami` 报出**身份来源**与私钥路径；`deliver` 前打印"以谁的身份交付"

---

### L4 · git 没有 `post-push` 钩子

**我写了个 `.githooks/post-push`，它永远不会被调用 —— 而且 git 不报错。**

git 的钩子：服务端是 `post-receive`，客户端只有 `pre-push`、`pre-commit` 等。**没有 `post-push`。**

**修法**：改用 `pre-push`（推送前顺手把同一批引用也推给 GitHub）。

**★ 这条教训已经变成检查项**：`tools/verify-meta` 现在验证 `core.hooksPath` 里的钩子名是 git 真认的，测试里专门放了 `post-push` 作反例。

**★ 以及一个连带发现**：**目录不存在时，git 会静默跳过钩子。** 所以 `bootstrap.py` 必须同时建目录**并**设 `core.hooksPath`。

---

### L5 · Gitea 的镜像机制在这台机器上不工作

试了三种，都失败：

| 机制 | 结果 |
|---|---|
| Gitea 的"推送镜像"功能 | 配得起来，但 **`task` 表为空、`last_update` 一直 0**；同步端点返回 405。后来发现它**真的跑过**，但 **Gitea 服务没有代理环境变量 → 连不上 GitHub** |
| Gitea 仓库的 `post-receive.d/` 钩子 | 手动能跑，**真实推送时不触发** |
| **本仓库的 `.githooks/pre-push`** | ✅ **可用**（实测 SHA 一致） |

**★ 顺带清掉一个隐患**：那条失败的推送镜像**把 GitHub token 明文写进了裸仓库的 `config`**。已删除记录并清掉令牌。

**结论：最可靠的镜像点是你自己的推送动作 —— 因为那个动作一定发生在本机。**

---

### L6 · 我自己造的测试污染了真仓库

`selftest.py` 早期直接改 `data/` 里的文件，跑完靠"恢复备份"。**有一次备份没恢复干净，测试数据留在了真仓库里，还被合并进了 main。**

**修法**：`selftest` 结束时**逐字节比对四份文件**，确认完全恢复 —— 不恢复就报错。

---

### L7 · 检查器"永远说一致"和"真的在检查"看起来一样

`tools/verify-meta` 第一版无条件对普通 clone 报警（"没设 core.hooksPath"），**结果每个外部 clone 都会看到一个无意义的警告。**

**★ 而"总是报警"的检查很快就会被无视 —— 那比没有检查更糟。**

**修法**：只在"这台机器负责镜像"（配了 `github` 远端）且钩子文件存在时才报警。

**配套纪律**：`tests/test_rules.py` 与 `tests/test_meta.py` 都是**为每条规则造一个故意违规的仓库**，确认它真的被抓住。
> **"实现了 11 条规则"这句话无法验证。只有"每条规则都有一个能被抓住的反例"才是证据。**

---

### L8 · GitHub API 的 `size` 字段会误导

`gh api repos/... --jq .size` 对一个刚推送的仓库返回 `0`。**当时我一度以为推送失败了。**

**修法**：用 `commits` 端点核对 SHA，不用 `size`。

## 四、数据与边界

### 三种状态放在三个地方

| | 是什么 | 在哪 | 冗余 |
|---|---|---|---|
| **内容** | `data/*.jsonl` + 代码 + 文档 | 本地 + Gitea 副本 + GitHub | ✅ 三份 |
| **协作过程** | 账号、issue、PR、评论 | **只在 `gitea.db`** | ❌ 一份 |
| **身份** | 私钥 | **只在 `~/.pool/keys/`** | ❌ 一份，且不可还原 |

**★ 内容有冗余，"协作过程"和"身份"没有。**

### 已知的边界（不遮掩）

1. **校验器能防"伪造记录"，防不了"敷衍了事"** —— 签名证明"某人说过"，证明不了"他真的看过"
2. **11 条规则只覆盖形式条件** —— 复核者是否真的独立判断过，机器查不了
3. **时间戳依赖 git tag 签名，不是区块链**
4. **Gitea 是单点** —— 你的机器关了，协作就停摆（内容还在）
5. **镜像不是实时的** —— 它等于你最后一次 push 时的状态

## 五、被否掉的方案（一览）

| 方案 | 为什么否掉 |
|---|---|
| 数据库（SQLite/PG） | 会引入两份真相，且余额会被缓存 |
| 区块链 / 代币 | 四个好处三个不需要、一个是红线 |
| SHA-256 git 仓库 | 三个 forge 全不支持，整条协作链断 |
| 元老院审批制 | 解决的是不存在的"审批问题"，而真正的问题是"匹配" |
| 清退程序 | 衰减就够了，不需要审判 |
| 分层公开 | 只公开数据等于说"相信我" |
| 前端配置进 `data/` | 自指循环，且改配色要两人签字 |
| Gitea 的推送镜像 | 实测不工作（缺代理） |
| `post-receive.d/` 钩子 | 实测不触发 |
| Docker 部署 Gitea | Docker Hub 连不上 |
| 自建数据 API | `data/` 是纯文本，clone 就能读，比 API 更直接 |
| 给前端写权限 | 前端只读，所以它不可能绕过校验 |
