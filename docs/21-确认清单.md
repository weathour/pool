### 2. ★ 签名密钥的算法与格式

**为什么阻塞：** `tools/sign` 和 `tools/validate` 都按这个写。定错了以后所有历史记录都要重签。

| 项 | 默认 |
|---|---|
| 算法 | **Ed25519** |
| 私钥存哪 | `~/.pool/key`（**绝不在仓库里**），权限 `600` |
| 私钥格式 | 原始 32 字节，base64 存文件 |
| 公钥 | 在 `keyring.jsonl` 里，`ed25519:<base64>` |
| 签名 | 对 `hash` 的 Ed25519 签名，`ed25519:<base64>` |
| 需要密码保护私钥吗 | **不要**（会让人每次签名都输密码，劝退）。**用 Shamir 备份代替** |
| 密钥丢了怎么办 | `keyring.jsonl` 追加一条 `retired` + 新公钥。**旧签名永远有效** |

**★ 最后一行是我加的：不用 `key_rotate` 这种操作，只需要追加新公钥并标记旧的 retired。因为旧记录里的签名当时确实是他签的，永远成立。**

### 4. ★ 用 Gitea Actions 还是别的方式跑校验

| 选项 | 说明 |
|---|---|
| **A. Gitea Actions** | Gitea 内置，兼容 GitHub Actions 语法。**PR 自动跑 validate** |
| B. 手动跑 | 每次你本地 `tools/validate` 一下 |
| C. GitHub Actions | 但那是镜像仓库，**PR 发生在 Gitea，所以不合适** |

**建议 A。** 理由：**校验必须发生在"合并之前"，而且是自动的**——否则维护者要手工记得跑，一定会漏。

**代价：** Gitea Actions 需要一个 runner（也是一个 Docker 容器，常开）。

**★ 备选：如果不想跑 runner，可以在 Gitea 里配一个 pre-receive hook 直接调 `tools/validate`。** 更轻，但报错信息不如 CI 友好。**我建议先上 Actions。**

### 5. ★ 第一个提交（genesis）里放什么

**为什么阻塞：** 它是整套东西的起点，后面所有记录都链在它后面。写错了不能改（只能追加）。

**建议内容：**

```
提交信息：genesis: 池子 v1 初始化
签名者：雁（第一把密钥）

文件：
  data/keyring.jsonl      只含雁一条 {"pubkey":..., "handle":"雁", "status":"active"}
  data/requests.jsonl     空
  data/deliverables.jsonl 空
  data/credits.jsonl      空
  policies.jsonl          十一条规则
  MAINTAINERS.md          雁 = 全部板块
  CODEOWNERS              从上一份生成
  CONTRIBUTING.md         新人指南
  README.md               说明这是第 0 号提交
```

**★ README 里必须写一句：** "本仓库的第一个提交是 genesis，之后所有记录都链在它后面。校验方式：`python3 tools/validate --all`。"

**这样任何人 clone 后跑一条命令，就能验证整个仓库。**

### 6. ★ 三个人时，"开单"到底要不要人批

你说"看情况"——**这一条我只需要一个字的答复，因为它直接决定 `validate` 怎么写。**

**三个选项：**

| 选项 | 行为 | 后果 |
|---|---|---|
| **A. 完全自动合入** | 开单 PR 不需要任何人批准，CI 过了就进 main | **摩擦最小。开单不产生 credit，没有作弊动机** |
| B. 维护者审 | 每张单都要你点一下 | 慢，而且开单本身没风险 |
| C. 本人自批但要留痕 | 开单人自己合，但记录里公开显示"自批" | 折中 |

**我建议 A。** 理由：**开单只是"我需要什么"的声明，不产生 credit、不影响任何人。** 卡它没有任何收益，只会让人不想提。

**（对比：交付物和 credit 必须第二人批——因为那两个会产生 credit。）**

## 一个我建议现在就写、而且现在就要用到的东西

### ★ `CONTRIBUTING.md` —— 它是这套东西的真正门槛

前面定了很多纪律，但**新人看到的只有这一份文件**。它必须在 5 分钟内让人完成第一张单。

**它要回答的只有四件事：**

```
1. 怎么装 tools/sign 并生成自己的密钥        （3 条命令）
2. 怎么开一张单                              （1 个 issue 表单）
3. 怎么交一份东西                            （跑一条命令 + 提 PR）
4. 别人怎么复核你                            （不用你管，但你要知道有这个环节）
```

**★ 我的判断：这份文档的质量，比校验器的质量更能决定这个池子能不能活。**

因为校验器挡住的是坏人，而这份文档决定的是**好人会不会留下来**。

**而这也正是下一个验证点：找一个真人，只给他这份文档，看他能不能在 5 分钟内开出第一张单。**

## 最后：还有一件事必须现在决定（不算技术）

**你在群里说的是"后续我肯定是要再拉人的"。**

**那么第一个真人是谁、什么时候？**

因为：
- **三个人以内，这套东西的复杂度和收益是不匹配的**——你和雁两个人用 git + 聊天就够了
- **它真正开始有价值，是在第 4～5 个人进来的时候**
- 而"第 4 个人"不会自己出现——**需要有一次真实的邀请，或者一次公开的展示**

**所以最该确认的其实是这一条：第一步是"把技术搭起来"，还是"先想清楚公开之后给谁看、怎么让人找到"。**

**如果是后者，那 Cloudflare Pages 那个站点的内容（不是形式）才是最该先想的东西。**
