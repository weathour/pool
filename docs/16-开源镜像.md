# 公共可克隆镜像：这改变了什么

> 新要求：**仓库本身和记录都防篡改的开源，可以克隆镜像。**
> 这不是加一个功能，是**换了整个系统的性质**。下面说清换了什么、什么被推翻、什么反而变得更简单。

---

## 一、最重要的理解转变：防篡改 ≠ 防复制

**这个区别是全部问题的钥匙。**

| | 防复制（传统"防篡改"的意思） | **防篡改（你真正要的）** |
|---|---|---|
| 目标 | 别人不能改**我的**副本 | 别人改了**自己的**副本，**能被立刻发现** |
| 手段 | 权限、加密、服务器控制 | **签名 + 哈希链** |
| 结果 | 闭源、中心化 | **开源、可克隆、可镜像** |

**你不可能阻止别人克隆后改自己的那份**——那在技术上不存在。**你能做到的是：任何被改过的副本，一眼就能看出来。**

**而这两个机关你早就有了：**

- **签名** → 改了就验不过
- **哈希链** → 改一条，后面全对不上

**★ 所以：开源和防篡改不矛盾，它们是同一件事的两面。** 越多人克隆，越多人手里有原始副本，**改账越难**。

---

## 二、被推翻的三个前提（必须重新处理）

### 2.1 ★ "内部使用"没了 —— 这是最大的一处

前几轮所有的法律简洁性，都建立在这一句上：

> **内部使用** → 不需要备案、不需要处理版权、不需要注册主体。

**开源之后，这一句直接失效。**

| 之前说"不是问题"的 | 现在的状态 |
|---|---|
| B 站转写原文可以进池子 | ❌ **不能公开分发** |
| 不需要 ICP 备案 | ⚠️ 若挂在自己域名下对外可访问，**又回到备案问题** |
| 不需要法律主体 | ⚠️ 一旦有公开的义务与回报约定，性质就变了 |

**★ 但这里有个关键解法，不必放弃任何东西：分层公开。**

```
public/   （开源镜像这一层）
  data/requests.jsonl        公告板 —— 本来就设计成不含人名
  data/deliverables.jsonl    交付物 —— 本来就不含人名
  data/cycles.jsonl          周期结算 + Merkle root
  结论与锚点                  ★ 你们自己的东西，可以公开
  tools/ docs/ policies.jsonl 全部开源

private/  （永不公开）
  data/members.jsonl         成员身份
  data/credits.jsonl         账本（含人名）
  data/maintainer-log.jsonl  维护者操作
  corpus 原文                ★ B 站转写，只在本机
```

**★ 注意这个分层几乎是免费的——因为前面定"单子上不写人名"的时候，public 层就已经天然准备好了。**

**当时那个决定是为了"谁产出谁说话"，现在它顺便解决了开源合规问题。** 这是那一轮最值钱的一个副产品。

**而且这不削弱可验证性：** public 层里的 `cycles.jsonl` 带着每期的 **Merkle root**，而那个 root 是由**全部六份文件**算出来的。**任何人拿到 public 层，都能验证"这一期的完整状态是那个哈希"——只是他们看不到 private 层的内容。**

**这叫"可验证但不公开"**，是标准做法。

### 2.2 credit 里有人名

credit 连着 `member`。**两个选择：**

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. credit 不公开**（建议） | 只公开每期的**汇总结算**（总数、占比分布），不公开明细 | 外部无法核验单条 credit |
| **B. credit 公开但用假名** | 公开 alias 与数额 | 假名在长期行为下**会被推断出身份**（谁写的东西风格很明显） |

**建议 A。** 因为 credit 是**内部记账**，它的作用是"决定谁掏钱"，**外部人不需要看明细**。

**而"防篡改"这个需求，靠 `cycles.jsonl` 里的 root 就够了**——root 覆盖了 credit 文件，所以**内部人能验、外部人能验"这一期没被改"，但看不到具体数额。**

### 2.3 谁说了算

**开源之后，"权威仓库"这个概念变得危险**——因为你不能既说"人人可克隆"，又说"以我这份为准"。

**正确做法：不设权威，设证明。**

```
每期结算 → 维护者发布一个【签名的 Merkle root】
         → 任何镜像持有者验证：我的副本算出来的 root 对得上吗？
         → 对得上 → 这份副本是可信的
         → 对不上 → 这份副本被改过（或者结算后又被追加了东西）
```

**关键：信任的对象从"仓库"变成了"那个签名的 root"。**

- 谁的仓库是权威？**都可以，只要 root 对得上**
- 谁改过？**改了 root 就对不上**
- 维护者能不能偷偷改？**能改自己的副本，但所有镜像的 root 会对不上**

**★ 这就是"多人持有副本"真正的价值所在：** 不是技术上的不可改性，**而是任何篡改都会在多个独立副本之间产生可见的不一致。**

## 三、新出现的问题：谁有写权限

**开源了，但账本不能人人可写**——否则任何人都能追加一条 credit。

**这是本架构里唯一真正需要"权限"的地方，必须说清：**

| 层 | 谁可写 | 机制 |
|---|---|---|
| **代码 / 文档 / 规则** | **任何人** | 开源仓库的标准做法：提 PR，维护者合并 |
| **`data/` 六份文件** | **单写者**（或少数几个签名者） | 每条记录必须有有效签名，**未签名/签名无效的追加直接判失败** |
| **镜像** | **任何人** | 克隆即镜像，无需许可 |

**★ 注意这里有个漂亮的对称：**

> **代码是开放的（谁都能提），数据是受控的（只有签名者可写），验证是开放的（谁都能算）。**

**三者互不冲突，而且各自用了最合适的机制。**

**而"数据受控"不需要任何权限系统——签名本身就是权限。** 只有持有私钥的人能写出有效记录，**不需要服务器、不需要账号、不需要白名单。**

## 四、镜像机制怎么落地（零成本）

### 4.1 主要载体：git

**git 本身就是内容寻址的**——commit 的 hash 由内容算出。**所以 git 天然是一个可验证的镜像系统，不需要额外发明任何东西。**

```
① 主仓库放一个公开平台（GitHub / Gitee / 自建 Gitea）
② 任何人在任何地方 git clone --mirror → 得到完整副本
③ 每期结算时，维护者打一个【签名 tag】并 push
④ 镜像持有者 git fetch 后验证：tag 的签名有效吗？内容对得上吗？
```

**风险与对策：**

| 风险 | 对策 |
|---|---|
| GitHub 国内访问不稳 | 同时推 Gitee；或自建 Gitea；**多镜像本身就是目的，不是妥协** |
| 平台封号 / 删库 | **镜像越多越安全**——这是开源的核心优势 |
| 只有一个镜像 | **那就不是镜像**。至少 2～3 个独立位置 |

### 4.2 要更强的防篡改：保留上链选项

**这不冲突。** 你们的 `data/` 是本地文件，**它的哈希可以随时锚到任何地方**：

- 签名 git tag（零成本，v1）
- 免费 RFC 3161 时间戳服务（零成本）
- **公共链锚定 root**（¥0～40/年）

**★ 注意：这里上链和之前否掉的那个"上链"是两件完全不同的事：**

| | 之前否掉的 | 现在这个 |
|---|---|---|
| 上链的是什么 | **数据本身**（含人名、明细） | **32 字节的 root** |
| 隐私 | 永久公开明细 | **零暴露** |
| 代价 | 改错永久留痕、schema 冻结 | 无 |
| 法律 | 性质模糊 | **纯存证** |

**开源之后，第 2 行和第 4 行的理由都不成立了（数据本来就要公开），所以上链的门槛比之前低了。但第 3 行依然成立——所以还是建议只锚 root。**

## 五、理解上的其他变化

### 5.1 仓库的性质：从"私人图书馆"变成"公共设施"

| | 之前 | 现在 |
|---|---|---|
| 谁能看 | 成员 | **任何人** |
| 谁能用 | 成员 | **任何人**（按开源许可） |
| 谁能镜像 | 不能 | **任何人** |
| 权威在哪 | 我的机器 | **在签名和 root 里，不在任何机器里** |
| 最大风险 | 数据被看 | **数据被改**（而且"被看"已经接受了） |

**★ 最后一行是真正的转变：威胁模型从"保密"换成了"完整性"。**

**这意味着前面那份加密选型文档的结论要更新：机密性彻底不是需求了，而完整性和真实性变成了全部。**

### 5.2 招人这件事，逻辑变了

前面说"拉人最有效的办法是把仓库挂出去，让方法本身成为筛子"。

**开源把这句话变成了字面意思：**

- 不需要邀请制——**代码和数据摆在那里，能读懂、愿意接着做的人自然会出现**
- 不需要元老审核——**贡献本身就是门槛**
- 不需要宣传——**镜像和引用会自己扩散**

**★ 这直接解释了为什么"元老院"一直感觉不对：它假设了一个封闭的边界，而开源把这个边界取消了。**

### 5.3 单写者的地位更关键了

**开源之后，"谁签的"变成了公开可见的事实。**

- 好处：**谁动过账，链上一目了然**
- 风险：**单写者成了显眼的攻击目标**（社会工程、胁迫、私钥窃取）

**对策（按重要性）：**

1. **单写者的私钥离线保管**（不放在联网机器上）
2. **签名操作可以离线做**：算出 root → 拷到离线机器签 → 拷回来
3. **多签名**：超过某个规模后，关键操作要求 2 个签名
4. **镜像持有者互相监督**：任何一份副本对不上 root，就是事件

## 六、修正后的整体结构

```
┌─────────────────────────────────────────────┐
│  公开层（可克隆、可镜像、可 fork）             │
│    requests · deliverables · cycles          │
│    结论与锚点 · 工具 · 文档 · 规则             │
│    ★ 每期带签名的 Merkle root                 │
└────────────────┬────────────────────────────┘
                 │ root 覆盖全部六份文件
┌────────────────┴────────────────────────────┐
│  私有层（永不公开）                            │
│    members（身份）· credits（明细）            │
│    maintainer-log · corpus 原文               │
└─────────────────────────────────────────────┘

外部可信度 ← 签名 + 哈希链 + 每期公开的 root
外部可参与 ← 代码提 PR、镜像、引用
内部可控   ← 签名即权限（无权限系统）
```

**一句话：公开层给人验证和参与，私有层保住合规和隐私，root 把两层钉在一起。**

---

## 七、需要你确认（这一次比较关键）

1. **★ 接受分层公开吗**（public: 公告板+交付物+root；private: 身份+账本+原文）——这是唯一能同时满足"开源"和"不碰版权"的路
2. **credit 是公开明细还是只公开汇总**（我建议只公开汇总）
3. **镜像放几个位置**（建议至少 2～3 个独立位置，别只放一个平台）
4. **是否给公开层加开源许可**（要，否则镜像没有法律依据；建议 MIT 或 CC-BY-SA，看你们对"署名"和"传染性"的取舍）
5. **签名是否改离线操作**（公开之后单写者变成显眼目标，建议离线签）
6. **是否重新考虑锚 root 到公共链**（现在门槛低了，¥0～40/年）

---

## 八、一句话总结

> **防篡改 ≠ 防复制。你能做到的不是"别人改不了"，是"改了就被发现"。**
> **而这两件事你早就有了——签名和哈希链。**
> **开源把威胁模型从"保密"换成了"完整性"，于是机密性彻底不再是需求。**
> **但"内部使用"这个法律前提没了——解法是分层公开：公告板公开，身份和账本私有，用每期的 root 把两层钉在一起。**
> **而信任的对象从"仓库"变成了"那个签名的 root"——谁的副本都行，对得上就行。**
