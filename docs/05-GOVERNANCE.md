## 一、核心约束：能推快，不能拖慢

**维护者可以单方面推进，不能单方面阻止。**（已实现）

**权威链**：`data/keyring.jsonl`（身份 = 公钥）→ `MAINTAINERS.md`（**权威**）→ `CODEOWNERS`（**从它生成**，绑定平台用户名，换平台重新生成即可）。`CODEOWNERS` 里出现的人必须能在 `MAINTAINERS.md` 里找到，`tools/verify-meta` 查这条。

| 维护者**可以**单独做 | 维护者**不能**单独做（必须第二人） |
|---|---|
| 确认交付物、推进状态 | **关单**（含"决定不做"） |
| 回应异议（哪怕回应是驳回） | **推翻已通过的复核** |
| 合并 `requests` / `deliverables` 的常规提交 | **修改 credit 认定**（`credits.jsonl`） |
| | **修改 `MAINTAINERS.md` 或 `policies.jsonl`** |

**维护者的约束**（`02` 的落地版，全部已实现；`02` 原文的第 6、7 条在这里合并为一条，第 10 条并入下面的"最后一个维护者"）：

| # | 约束 |
|---|---|
| 1 | **只追加不删除**：修订写 `amend`，保留原记录。**维护者不能删任何东西** |
| 2 | **必须写理由**：每个 `closed` / `expired` / `review_fail` / credit 调整都要有理由字段 |
| 3 | **不能单独阻止**：关 `open` 单、驳回已 `pass` 的复核、改 credit 认定 —— 都要第二人同意 |
| 4 | **可以单独推进**：确认交付物、推进状态、回应异议 —— **推快不受限，推慢受限** |
| 5 | **操作单独成账**：维护者的操作记 `maintainer-log.jsonl`，每期公示 |
| 6 | **异议必须回应**：任何成员可对任何决定提异议（挂号制），**7 天内**回应，哪怕回应是驳回；7 天未回应即自动升级为"待共同裁"，由其他维护者共同处理 |
| 7 | **公示失效**：连续两期未公示，维护权限自动失效，直至完成公示（`p-010`） |
| 8 | **缺席接管**：连续 **30 天**未响应，由其他维护者中最先响应者接管并公示 |
| 9 | **退出自由**：随时可退，退出时**必须**完成 **账本交接 + 交接演练 + 公示** |

**第 3 条和第 6 条是这套约束的真正骨头**：其余是形式要求，这两条保证**维护者无法靠"不回应"卡住任何东西** —— 而那是一个人掌权时最常用、也最难防的手段。配套事实：
- **最后一个维护者离开会怎样**：记录不失效（任何人 clone 后跑 `python3 tools/validate` 都能验证），持钥者仍可提 PR，**但无人能合并**（规则：**只有现任维护者能添加新维护者**）→ 板块**冻结，不是腐烂**。
- **缺席接管的前提**：只有一名维护者时第 8 条不适用 —— 当前正是这种情况（`MAINTAINERS.md` 里只有一个人）。
- **扩展路径**：任何板块都可拆出去给新维护者，这是防止单点的唯一办法；`policies.jsonl` 这块**必须两名维护者共同持有**（`CODEOWNERS` 已这么写，但因只有一名维护者暂时退化为一人）。
- **credit 与决策权严格分离**：credit 只兑换资源，不兑换治理权；**不得由"某人贡献多"自动推出"他说了算"**。credit 是什么、值多少、为什么不上链 → [`02-credit.md`](02-credit.md)。

## 二、申请单的语义约定（不含字段表）

**字段表与实现去读代码**（`lib/pool.py`、`tools/sign`、`tools/validate`、仓库根 `policies.jsonl`）。**原子单位：一条申请单 = 一个可验收的、尚不存在的产物。** 不是"一个任务"，不是"一个帖子"。申请单是"池子里缺什么"（进口），交付物是"池子里多了什么"（存货）—— **只有产物能验收，只有能验收的东西才谈得上完成和 credit。**

| 语义约定 | 内容 |
|---|---|
| **① 单上不写人名** | 公开层（`requests` / `deliverables`）没有人名字段；身份只在账上（`credits` / `keyring` / `maintainer-log`）。**"不管人"不是不记，是分层记**；两层靠 `id` 关联，不靠人名关联。★ 现在两层都公开，所以分层的意义是**单不承载身份**，不是"藏起来" |
| **② 验收标准必须可判定** | `acceptance` 不得为空（`p-004`）。**写不出可判定的验收标准，就不算一条合格的申请单** —— 整套记账的可信度全压在这一点上：标准清楚，谁来判都一样；不清楚，就只能靠人品 |
| **③ 状态靠推导** | 状态由事件推导（`pool.request_status` / `pool.project`），不采信手填的声明字段。**"事件流里最后一条记录" ≠ "实体当前状态"**；凡是要实体字段，一律用 `project()`（`DECISIONS.md` L1） |

- **一种单，用 `type` 区分三类**：`need`（我需要什么）/ `offer`（我想做什么，缺人手）/ `challenge`（我认为已有产物是错的）。三者共享同一套状态机、验收字段、记账规则，所以不拆三个列表（会各自漂移）。**`challenge` 必须 `links` 非空**（`p-009`）："指出一个已有产物错了"是最高价值的贡献，也最容易没有归口。
- **`question` 是独立产物形态，与 `answer` 平级**：既然"问题也算贡献"，就必须在形态里给它身份，否则它永远被当成"没有交付物的申请单"结不了案。成案条件：**被采纳为独立主题，或被 ≥2 条产物引用**。<!-- 缺口：这条成案阈值目前只在文档里，代码中未见对应校验 -->
- **状态机**：`open → claimed → delivered → accepted`；打回回到 `claimed`；另有 `withdrawn`（提出人撤回）、`closed`（结案）、`expired`。**`closed` 允许"决定不做"，而且这是正常结案、不是失败**（照搬 ismism 的 `no-asset-needed` 纪律："本期不产出任何东西"是成功的决定）。**没有自动过期关单**：`open` 超 30 天只是"该有人决定：关掉，还是改验收标准重开"的信号 —— 关单是判断，必须第二人同意（`p-006`）。
- **开单不需要任何人批准**（CI 过了就进主干）：它只是"我需要什么"的声明，**不产生 credit、不影响任何人**，卡它没有收益，只会让人不想提；需要第二人的是**交付物与 credit**。**一条 credit 入账必须同时满足四条**：有交付物、复核通过且复核者 ≠ 交付者、需求方确认可用、有哈希且链上接得住 —— 缺一不入账。**★ 关键推论：自问自答自交付不产生 credit**，所以"刷单"在结构上不成立，**不需要任何稽查**。
- **"效果"分三类记，不许合并**：① 复核结果（通过/打回，**机器可判**）② 需求方验收（人判，**不能作为唯一门槛**，否则互相捧场）③ 复用次数（客观、滞后、**最可信**）。合成一个"好评率"立刻变成人情分；分开记才能看出**"通过了但没人用"**的产物。**失败、放弃、打回要记，但不挂名**：打回次数 / 撤回次数 / 过期数只出汇总数字，公开层不点名 —— **不记就识别不出空转；挂名就没人敢提。**
- **单一来源上限**：任一来源在单周期内计入的 credit 不超过总量 **60%**（`p-008`）。这是唯一一条**不需要任何人做判断**的反寡头机制；活跃成员少于 3 人时**只记录不执行**。`02` 原建议 40%，落地取 60% 并加了三人豁免。

## 三、十一条规则

细节在 `policies.jsonl`（原文 + 判据表达式）。**每条都有校验器实现，而且每条都有一个能被抓住的反例测试**（`tests/test_rules.py`）。

| 规则 | 一句话 | 级别 |
|---|---|---|
| `p-001` 链完整 | `prev` 必须等于上一条的 `hash`；`seq` 连续；`hash` 与内容相符 | error |
| `p-002` 签名有效 | 每条记录签名有效；`by` 必须是 keyring 中 `active` 的公钥 | error |
| `p-003` 复核者不得是交付者 | 复核者 ≠ 交付者本人（自问自答格式合规，但不产生 credit） | error |
| `p-004` 验收标准必须可判定 | `acceptance` 不得为空 | error |
| `p-005` 改账需第二人联署 | credit 人工调整必须带 `cosign`，且 `cosign` ≠ 被记账的人 | error |
| `p-006` 越权检测 | 关单 / 推翻已通过的复核 / 改 credit 认定，单方面执行即越权 | error |
| `p-007` 异议必须回应 | 7 天内回应，哪怕回应是驳回；未回应自动升级 | warn |
| `p-008` 单一来源占比上限 | 单周期单来源 ≤ 60%；活跃成员 < 3 人只记录不执行 | warn |

| `p-011` 拉人不产生 credit | 邀请不是产出。**credit 从记录贡献滑向招募工具，是堕落的开始** | error |

## 四、为什么否掉元老院（已作废）

**最终形态是抄 Linux 的**：`MAINTAINERS.md`（权威）+ `CODEOWNERS`（派生）。不设元老院、不设两院、不设日落。

**被否掉的方案长什么样**（保留，以便看清否掉的到底是什么）：

| 曾经的方案 | 内容 |
|---|---|
| 两院制 | **元老院**管准入、清退、章程修改、争议终审；**全员大会**管对外内容、公摊额度、公开立场。理由：判断"某个人行不行"需要小、需要慢、需要有人担声誉；判断"我们对外说什么"需要大，因为一个人说话代表所有人。混在一起就会出现"三个人决定对外说什么"或"三十个人投票开除谁" |
| 日落条款 | 元老席位 12 个月自动失效，到期重新表决续期；目的是让"元老"从身份变成职责 |
| 准入三改 | 提案公示 7 天（任何人可提异议）、不要求全票（2 人提名 + 简单多数）、新人 90 天观察期（无资产权限，credit 标 `provisional`） |
| 成员三态 | `provisional` / `active` / `suspended`，各有明确进出条件 |
| 名称之争 | "元老院"的语料色彩是贵族共和 / 寡头（`corpus/bilibili-asr/BV1kG411n7Yi__68106ef006.txt` 对元老院式政治想象的评价是"很糟糕的棋手势……肮脏的、反动的"）。结论是二选一：改中性名（创始院/议院/管理组），或者就叫元老院并**对外明说我们是邀请制的** |

**否掉的理由（一条就够）：**

> **元老院管的是"谁能进来"；而"进不来人"的真正原因是"没人看得见需求、没人信得过对方" —— 那是匹配问题，不是审批问题。**

审批解决不了"没人来"，只会给来的人再加一道门。实现上的对应：`keyring.jsonl` **是公钥目录，不是成员名单** —— 名单有边界、要审批、进不去就用不了；目录没有边界，任何人加一条自己的记录就能开始干活，移除也只需追加一条 `status: retired`（历史签名永远有效，因为它当时确实是他签的）。**所以"准入"在实现上不是一个审批环节。** 随之一起作废的：日落条款、90 天观察期、`provisional`/`suspended` 三态、两院分权、清退程序（见第五节）—— 实现里只剩 `keyring` 的 `active` / `retired`。

## 五、没有清退程序：靠衰减（设计，未实现）

**决定：不写清退程序。** 不产出就衰减，**让位置自然空出来，而不是把人赶出去** —— 没有审判、没有投票、没有申诉程序，也不需要"谁提、几票"那套阈值。**为什么衰减能替代清退**：权力依赖**可损失的担保**，休眠衰减就是那个可损失的东西，而且**不需要任何人来没收，时间自己会完成**；同理，加速上升通道不需要给新人特权，**只需要让老人自然减速**。

**参数（设计值，尚未拍板）**：**活跃度衰减**，非时间衰减（有产出即重置计时 —— 时间衰减会误伤"歇了半年但一直在做的人"）；半衰期 **180 天**，首个周期设 **365 天**试跑；衰减到零之后**记录仍在**，只是不计入席位与权重。

**★ 实现状态：没有实现。** `tools/` 里没有任何衰减计算（`tools/status` 等只是认得 `decay` 这个 `op` 名，不会去算）；`data/requests.jsonl` 里已经开了一张单（"credit 的衰减应该按时间还是按活跃度"），没有落地代码；参数也还没拍板（见第八节）。与分摊的关系：**不产出 → credit 衰减 → 分摊比例上升**，这是一个自动的、不需要任何人裁决的机制（信用部分见 [`02-credit.md`](02-credit.md)）。★ 这条不是 row 288 那条判断的反例 —— 它靠的正是"**在制度里埋自动失效机制**"，而不是"这个机制没毛病"。

## 六、定时器（设计，未实现）

> **★ 全文唯一一处"设计好了但没写"。** 下面每一条都还没有代码：`tools/` 里没有定时器，`state/` / `digest/` 目录不存在。

**机器人是这套系统的"钟" —— 它负责让"没人看的东西"变得可见。** 核心问题是**记录会积累，但看记录的人不会**：申请单过期、异议没人回、复核堆着、产物通过了但没人用 —— **这些都不是错误，是没人注意到**。机器人不修这些，它只是让这些变得刺眼。**唯一功能：定期产出"该做什么"的清单。**

**九条告警（全部纯机械）：**

| # | 告警 | 判据 | 为什么这条重要 |
|---|---|---|---|
| 1 | **单子快过期** | `open` 超 7 天未 claim | 需求方会以为没人理 |
| 2 | **单子已过期** | `open` 超 30 天 | 需要人决定：关掉，还是改验收标准重开 |
| 3 | **复核堆积** | `delivered` 超 3 天未 review | 交付者的动力全靠这个 |
| 4 | **等确认** | `review pass` 但需求方未 confirm | 差一步就成案，最容易被忘 |
| 5 | **异议未回应** | 超 7 天无 `responds_to` | 直接对应维护者约束第 6 条 |
| 6 | **维护者日志未公示** | 周期结束未公示 | 直接对应维护者约束第 7 条 |
| 7 | **★ 通过了但没人用** | `review pass` 且 `reuse = 0`，且已过一个周期 | **最有价值的一条，见下** |
| 8 | **问题提了没人接** | `artifact_kind = question` 且无引用 | 问题是最稀缺的，不能让它沉底 |
| 9 | **可能是重复的** | 两条 `open` 单的 title/spec 相似度高 | 重复会让同一件事没人做 |

**★ 第 7 条值得单独说："通过了但没人用"是这套系统里唯一能自动发现的真问题。** 因为：复核通过 → 说明有第二个人看过，形式条件满足；需求方确认 → 说明提出的人满意了；**但复用 = 0 → 说明它对别人没用**。**三者同时成立，就是一个信号：我们在生产"自己能验收、别人不需要"的东西。** 这个信号不会自己浮现 —— 因为每个人都在做自己那一环，没人看整体。只有机器人会问：**"上周期通过的 5 件，有几件被引用过？"** **这是机器人存在的全部理由，其他八条都是它可以顺便做的。** **部分已实现**：这条判据已经在 `tools/status` 里（`make status` 会打印"★ 通过了但没人用"）；**没实现的是定时把它推给你。**

**它绝对不能做什么（三条硬边界）：**

| 边界 | 规则 | 为什么 |
|---|---|---|
| **1. 不能改状态** | 只能读 `data/`，只能写 `state/` 和 `digest/` | 一旦它能改状态，**判断就从"写下来"变成了"隐含在代码里"** —— 而我们要的是前者 |
| **2. 不能判交付物** | **不能做复核者** | 见下（和 `p-003` 的冲突） |
| **3. 不能自动关单** | 过期只报告，不自动 `expire` | 关单是判断。**"自动关掉"等于把判断藏在定时任务里** |

**第 2 条和一条已有规则冲突，需要拍板**：`p-003` 是"复核者 ≠ 交付者"。如果交付者是人、复核者是模型 → **形式上满足**（不同主体）；但如果这套模型和当初**生成**这份产物的模型是同一个 → **实质上是自审**。两个选项：**A. 只有人能复核**（v1 建议用这个；代价是慢，三五个人时是瓶颈）｜ **B. 模型可复核，但必须不同源**（复核模型 ≠ 生成模型家族；代价是复杂，且"不同源"很难验证）。**建议 v1 走 A，B 留到活跃成员 > 3 人之后** —— 现在**最缺的不是产能，是"这条记录值不值得信"**；人复核是唯一能让"可信"站得住的东西。**等到产能真的成为瓶颈，再引入模型复核，那时你已经有足够多的"人复核"样本来校准模型复核的准确率。顺序不能反。**

<!-- 缺口：代码里没有一条规则写死"复核者必须是人"。当前只是靠"只有持钥者能签名"间接保证（keyring 里没有模型密钥），p-003 也只检查复核者 ≠ 交付者。选项 A 尚未成为可执行的规则。 -->

**它跑出来的东西长什么样：**

```
digest/2026-09-23.md

# 本周该做的事

**卡住的**
- r-0004 已等待复核 5 天  ← 交付 d-0009
- r-0002 已 open 12 天无人接

**★ 上周期通过了但没人用（3 件）**
- d-0003  术语辨析：无对价行动
- d-0005  锚点校验脚本 v1
- d-0008  英译对照表（前 20 条）
  → 这三件都有第二人复核、需求方也确认了，但没有任何产物引用。
  → 要么是我们需要的东西和别人不一样，要么是它们没被看见。

**需要人决定的**
- r-0006 已过期 33 天：关掉，还是改 acceptance 重开？
- 异议 obj-0003 已 9 天未回应（维护者：请回应，哪怕驳回）

**可能重复**
- r-0007 和 r-0009 的 spec 相似度 0.81，建议合并
```

**★ 注意最后那段的措辞：它不下结论，它提出两种可能。** 机器人永远只描述状态，不做判断 —— **它报告"3 件产物没人用"，不说"所以我们做错了"。判断留给人。**

**"自发运行"是什么情况**：手动跑（✗，会忘，但只要一周一次就够）· **本机 cron（✓，v1 用这个，零成本）** · git hook（半，有人 push 才触发，只能补漏、不能当主调度）· 服务器常驻（✓✓，**这就是"自发运行"的真实代价**）。

> **"机器人自发运行" ≈ "租服务器"** —— 因为"自发"需要的不是机器人，是**一台不关机的机器**。

**v1：cron 一周一次，产出 `digest/` 下的一份 markdown**，它就是"本周该做什么"。**一周一次就够**：所有告警阈值都是天级的（3 天、7 天、30 天），**每天跑和每周跑结果几乎一样**；而每天跑会让人麻木 —— **告警的价值来自稀缺，不来自频率**。**★ 前提已变（相对 08 写作时）**：Gitea 现在就常驻在这台机器上（`06-OPERATIONS.md`），机器本来就是常开的，所以"cron 一周一次"**不再需要为此额外租服务器**；原设计里"它和'什么时候才租服务器'是同一个决定、并多出一个触发条件：需要机器人自发运行"这条约束，现在不构成门槛。

**机器人要不要进账本：不要。** 它不产出 `deliverable`，它不拿 credit，它**不该有 `member` 记录** —— **它是一段定时运行的代码，不是一个成员**。理由：一旦机器人有身份，就会有人问"它能不能复核""它的 credit 归谁" —— **这两个问题都没有好答案，且都是自找的**。**唯一例外**：将来某个模型真的产出了被采纳的产物（经人复核），**那时它是"工具"，credit 归操作它的人**；v1 就按工具算，别给身份。

**曾经的最大技术担忧：多写者（已有答案）。** `08` 当时的判断是：六份 JSONL 虽然 append-only，但 `seq` / `prev` 让它们成为**单写者结构**；两人同时 append，合并后要重编 `seq`、重链 `prev` → **`hash` 变了 → 签名全失效**，而"重链会摧毁签名"。**因此当时建议 v1 用单写者节点（其他人交提案，由写者落账），并把"每人一份日志、周期合并"列为将来人多时的方向（那需要改 schema：去掉 `prev` 链，只保留签名）。** **★ 这个前提已经被推翻**：实现把 `hash` 定义成**只覆盖内容、不覆盖 `seq`/`prev`**（`lib/pool.py`），于是重排重链**只改位置、不改内容 —— 签名仍然有效，不需要任何人的私钥**；`tools/resolve --write` 已实测（`DECISIONS.md` D3，`CONTRIBUTING.md` 的冲突处理也是这么写的）。**所以现在既不需要单写者节点，也不需要"服务器 + API 串行化"** —— 一个共享文件 + `tools/resolve` 重链就够，冲突是正常现象，不是故障。被否掉的两个方案及理由保留在上面，因为它们正是"为什么 hash 不覆盖 `seq`/`prev`"这条设计的来源。

## 七、账号与资产归属（托管，部分实现）

**"归属暂与元老相关"这种说法必须有约束，否则"暂"会变成"永远在一个人名下"。**

- **立刻要做的**（下列全部 ⬜ 未做）：域名 / VPS / 仓库 / 机器人账号**统一用组织邮箱注册**，不用任何人的私人邮箱；凭据进共享密码库，**恢复码/2FA 备份由 3 人各持一份**（如 3-of-5 Shamir 分片；共享密码库本身是单点，主密码别只存在一个人脑子里）；写一页纸**托管声明**（写明这些账号"系团队共有资产，登记人仅在任期内代持，**无权处置、转让、抵押**"，写明日期、资产清单、三方签字）；任何人退出，48 小时内完成凭据轮换，登记人退出时强制移交，不移交视为违约。
- **交接演练**：**上线后做一次真实交接演练**（临时把 root 交给另一人，走完整流程再交回）—— **没演练过的交接流程等于没有**。`MAINTAINERS.md` 已把"接手者实际做一次合并"写成退出必做项，但**还没演练过**（部分实现）。
- **不要把所有资产挂在一个人名下**：一个人的意外就能让整个基建归零 —— **这是纯粹的风险管理问题，跟理念无关**。⚠️ 现状就是一个人（row 288 讲的"一个创始元老……被干掉了"是历史必然性，不是操作手册）。
- **什么时候该立主体**（出现任一条就考虑注册实体：境外 LLP / 基金会，或境内个体户/公司）：有对外收款或付款；credit 出现**对外**负债（有人能从外部兑换）；需要签合同、持有商标、承担侵权责任；成员超过约 10 人。**在立主体之前，一切"归属"都只是君子协定** —— 所以托管声明要写得像那么回事：法律效力有限，但**在人心里的效力很大**。

## 九、边界：机器能保证什么、不能保证什么

| 能保证 | 怎么保证的 |
|---|---|
| **防伪造** | Ed25519 签名 + `keyring`（`p-002`）；签名证明"这句话是你说的" |
| **防篡改、防抵赖** | 文件内哈希链（`p-001`）；改一个字段、删中间一条，`tools/validate` 当场报出来 |
| **脱离 git 也能自证** | 链与签名都在记录内；把 `data/` 拷出仓库照样成立 |
| **合并后签名仍有效** | `hash` 不覆盖 `seq`/`prev`；`tools/resolve` 重链（D3，已实测） |
| **外人可独立验证** | clone 公开仓库 → 跑 `tools/validate` → 签名 tag 用 `.allowed_signers` 验时间锚点 |
| **结构上不可刷单** | 自己闭环不产生 credit（`p-003`）；复用次数从 `links` **推导**，不由任何人自报 |

| 不能保证 | 说明 |
|---|---|
| **防不了敷衍 / 规则只覆盖形式** | 签名证明"某人说过"，**证明不了"他真的看过"**；11 条规则也只覆盖形式条件 —— 复核者是否真的独立判断过，**机器查不了**。"复用"补一半：它让敷衍留下痕迹。这也是复核权问题的根源 |
| **"通过了但没人用"只给信号、不给结论** | 它可能意味着"我们需要的东西和别人不一样"，也可能意味着"它们没被看见" —— **判断留给人** |
| **时间戳不是区块链** | 靠签名 tag + `.allowed_signers`，不是全局共识 |
| **Gitea 是单点，镜像不是实时的** | 机器关了协作就停摆（内容还在）；镜像等于最后一次 push 时的状态 |
| **三种状态里有两种没有冗余** | 内容三份（本地/Gitea/GitHub）；**协作过程只在 `gitea.db`**、**私钥只在个人机器** |
| **对外分发是另一回事** | `02` 曾以"内部使用"为整套设计不需要法务的支点；后来改为**完全公开，但语料不进本仓库**（`DECISIONS.md` D7）。**硬约束仍然成立：对外分发任何产物之前，必须先过版权与合规复核** |
