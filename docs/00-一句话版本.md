# 一句话版本

> 更简洁的通俗解释。可以直接当 README 的开头。

---

## 你的问法基本对，只要改一个词

你说：**"一个 git 仓库 + 一个机制 + 管理的规则，然后机制和管理本身也归 git 仓库？"**

**对，但"机制和管理"不是两样额外的东西——它们就是仓库里的文件。**

所以最准确的说法是：

> **就是一个 git 仓库。里面装着三种东西：数据、规则、机制。**
> **仓库之外只有一样：每个人自己的私钥。**

---

## 仓库里装的三种东西

| 类型 | 是什么 | 具体文件 |
|---|---|---|
| **数据** | 发生了什么事 | `requests.jsonl`（谁需要什么）<br>`deliverables.jsonl`（交了什么）<br>`credits.jsonl`（谁该得多少）<br>`keyring.jsonl`（谁是谁） |
| **规则** | 怎么算合规 | `policies.jsonl`（十一条规则） |
| **机制** | 按规则跑的程序 | `tools/validate`（校验器）<br>`tools/build-index`（生成首页）<br>issue 模板、CODEOWNERS |

**加上治理的两个文件：**

| 文件 | 说清什么 |
|---|---|
| `MAINTAINERS.md` | 谁管哪个板块 |
| `CODEOWNERS` | 谁的批准算数 |

---

## ★ 关键的一点：这三样东西走的是同一套流程

**这是整个设计最漂亮的地方。**

```
改数据（提一张单）  → 开 issue → 提 PR → 校验 → 复核 → 合并
改规则（改一条门槛）→ 开 issue → 提 PR → 校验 → 复核 → 合并   ← 同一套
改机制（改校验器）  → 开 issue → 提 PR → 校验 → 复核 → 合并   ← 同一套
```

**规则自己也是被这套流程管的。机制自己也是。**

**所以"规则怎么改"这个问题的答案，和"怎么交一份东西"是同一个答案。**

**而且规则和机制的每一次改动都留在 git 历史里，带理由、带签名。** 将来有人问"这条规则为什么是这样"，`git log` 里有答案。

---

## 仓库之外只有一样：私钥

```
你的私钥          只能在你自己的机器上
                  ★ 不在仓库里，不能托管，丢了就丢了
                  （所以要用 Shamir 分片备份）
```

**为什么它必须在外面：** 因为"签名证明是你写的"这件事，前提是**只有你能签**。**私钥一旦进了仓库，签名就没有意义了。**

---

## 那"机器人"算什么

**它不算一样东西。** 它就是一段定时跑的小程序，跑完把结果写进一个文件：

```
digest/2026-09-23.md    ← 本周该做什么
```

**它不拿 credit、不改数据、没有身份。就是闹钟。**

---

## 一句话

> **一个 git 仓库，装三样：数据、规则、机制。**
> **三样走同一套流程：开单 → 提交 → 校验 → 复核 → 合并。**
> **签名代替权限——没有账号、没有白名单、没有管理员。**
> **仓库外面只有一个东西：你自己的私钥。**

**而这就是全部。** 前面十几份文档讲的所有东西，都是这句话的展开。

---

## 那"防篡改"是怎么来的

**就两条，加起来：**

| 谁提供 | 保证什么 | 为什么够 |
|---|---|---|
| **git（SHA-256 仓库）** | 内容没被改 | 每次改动都有哈希，改了就对不上 |
| **签名** | 是谁写的 | 没私钥就签不出来 |

**再加上一条使用纪律：镜像的人定期拉一次。**

**如果有人偷偷改了账**：他自己的副本变了，但别人的副本没变——**一比就露。**

**★ 所以"防篡改"不是靠某个技术，是靠"副本不止一份，而且每份都能自己验"。**

---

## 还有一件必须说清的

**这套东西能防"伪造记录"，防不了"敷衍了事"。**

- ✅ 能验：签名对不对、链接不接得上、复核的人是不是交付的人本人
- ❌ 验不了：复核的人是不是真的读了、估的工时公不公道

**因为 "复核的人 ≠ 交付的人" 这条是机器能查的，但"他有没有认真看"机器查不了。**

**补一半的办法**是那个闹钟：**定期报出"通过了但没人引用"的东西。** 它不阻止敷衍，**但让敷衍留下痕迹。**
