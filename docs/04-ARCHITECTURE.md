> **现状一句话：本地仓库是真相源 → Gitea（本机 systemd 常驻，端口 3000）是协作层 → GitHub 是公开只读镜像。**

## 一、三层，各管一件事

**① 本地仓库（真相，`data/*.jsonl` + git）→ push → ② Gitea（工作台：issue / PR / CODEOWNERS / 校验）→ ③ GitHub（橱窗：公开只读镜像）**

| 层 | 管什么 | 不管什么 |
|---|---|---|
| **① 真相层**（本地磁盘） | 存记录、跑校验、生成网站；所有改动的最终落点 | **不接受别人的 push** |
| **② 协作层**（本机 Gitea，单二进制 + systemd 常驻） | issue（开单）、PR（交付）、CODEOWNERS（谁批）、评审 | 不做展示（自带 web 很朴素） |
| **③ 公开镜像层**（GitHub `weathour/pool`） | 只读副本、被 clone、被引用 | 不接受 PR / issue；**推给它的 PR 不会被处理** |

**"本地是真相"不等于"你直接在本地改"**：改动的唯一入口是 Gitea 上的 PR，本地只做校验、看状态、生成网站；cron 每 10 分钟 `git fetch origin && git merge --ff-only origin/main`，所以**本地同时也是另一份副本**——和"镜像越多越难改账"是同一件事。

| 三种状态 | 在哪 | 冗余 |
|---|---|---|
| **内容**：`data/*.jsonl` + 代码 + 文档 | 本地 + Gitea + GitHub | ✅ 三份 |
| **协作过程**：账号、issue、PR、评论、CODEOWNERS 配置 | 只在 Gitea 数据目录 | ❌ 一份，要单独备份 |
| **身份**：私钥 | 只在 `~/.pool/keys/` | ❌ 一份，且不可还原 |

**★ 内容有冗余，"协作过程"和"身份"没有**——两份备份要分开做、分开放。

## 二、一次协作的完整数据流

**①** 开单（Gitea issue，ISSUE_TEMPLATE 强制填"缺什么 / 怎么算做完了"）→ **②** clone 后跑 `tools/sign` 追加一行到 `data/requests.jsonl`，**用他自己的私钥签** → **③** 提 PR 到 Gitea → **④** CI 跑 `tools/validate`（链接得上吗、签名有效吗、acceptance 非空吗）→ **⑤** CODEOWNERS 要求第二人批准（deliverables / credits 必须）→ **⑥** 合并进 main → **⑦** 推送动作触发本地 `.githooks/pre-push`，同一批引用镜像到 GitHub → **⑧** 本机 cron `git fetch origin && git merge --ff-only origin/main`

**★ 第 ⑧ 步的方向：本地也在拉取。** 本地不是发布源，是另一个副本，所以 `--ff-only` 是关键：如果本地被直接改过，它会失败，**这正是要的**——一旦本地能直接改，就出现两份真相。例外只有一类：重建 `site/` 这种纯推导产物。

<!-- 缺口：本地只读纪律的那条 cron（git fetch && merge --ff-only）尚未安装；现在每 10 分钟跑的 cron 是 tools/gitea-home-data（刷新 Gitea 主页数据）。 -->

**"自动"与"必须走 PR"的判据只有一条：有没有"人签名说过某句话"。**

| 内容 | 有人的签名吗 | 处理 |
|---|---|---|
| 所有记录（requests / deliverables / credits / keyring / maintainer-log） | ✅ 有 | **必须走 PR** |
| `policies.jsonl` | ✅ 有（改动要签名） | **必须走 PR + 两人批准** |
| `tools/*` 工具 | ❌ 没有 | 可以自动（CI 过即合） |
| `site/`、`INDEX.md`、`digest/` 等纯推导产物 | ❌ 没有 | 可以自动 |

**★ 理由：如果 CI 能自动写 `credits.jsonl`，credit 就不再是"某人的认可记录"，而变成了一段代码的输出——代码不可复现，不可抵赖也就不成立。**

| 档 | 内容 | 谁批 |
|---|---|---|
| **自动** | `site/`、`INDEX.md`、`digest/` | 不用人，CI 过就合并 |
| **本人自批** | 开一张申请单（"我需要什么"就是我的声明） | 开单人自己合，**但验证器必须过** |
| **他人复核** | `deliverables`、`credits`、关单、改 credit | **必须第二人**（CODEOWNERS 强制） |

**★ 中间那档是优化：开单不产生 credit、不影响任何人，卡它没有收益；但"关单"和"改 credit"必须第二人。** 配套两条：`validate --changed-only`（只校验本 PR 碰到的文件加它的链尾，避免全量校验随仓库增长越来越慢）；`site/` 与 `INDEX.md` 不进仓库、构建时生成（仓库干净，也少一个给 CI 写权限的安全隐患）。

**账本不是代码库**：`git commit --amend` 在代码库里无所谓，在账本里它就是事件——所以**只追加**（改一条 = 追加一条 + 引用旧的），**合并必须用 merge commit，禁止 rebase 和 force push 已发布的 main**；镜像持有者定期 fetch，任何 force push 立刻表现为历史分叉；`data/` 每次改动必须带 `reason`。另一条纪律：**只报告不判断的定时器**——CI 只在有 PR 时触发，看不到"某张单已经两周没人动"，那是 cron 的活。

**JSONL 必须对 git 友好**：一行一条永不跨行（git diff 以行为单位）、字段顺序固定（否则每次序列化都产生无意义 diff）、不用数组包整份文件（否则整个文件是一个巨大 hunk）、时间戳用 ISO 8601 带时区、**永远在文件末尾追加**。最后一条的直接好处：两个人的追加在 git 里几乎不会冲突（它能自动合并"你在末尾加一行、我在末尾加另一行"），**多写者问题因此大幅缓解**——前提是 `prev` 和 `seq` 可后补。

**从开源惯例直接抄的七件**：声明式维护者文件（`MAINTAINERS.md` + `CODEOWNERS`，每个板块维护者只写自己那块，"能推快、不能拖慢"）、线性历史禁 rebase/force push、**签名 tag 当"发布"**（内核唯一的权威锚点）、每个改动带理由（`reason` 字段）、CI 门禁、issue 模板当入口（**不用开发任何前端**）、DCO 的形态但换掉内容（见第四节）。维护者的决定要落在 `data/maintainer-log.jsonl` 里并带理由——这是 git 本身不提供的语义。

**★ 两个真正的验证点**：本地空跑一张真单子（**判不了 = acceptance 写得不合格 → 回去改，不要往下走**）；找一个真人、只给他 `CONTRIBUTING.md`，看他能不能在 5 分钟内开出第一张单（卡住就是这套东西的真实瓶颈）。

## 三、git 层为什么用 SHA-1

**决定（2026-09-16）：git 层用默认的 SHA-1，不用 `git init --object-format=sha256`。** 先分清两种攻击——**这个区别决定 SHA-1 能不能用**：

| 攻击 | 难度 | 含义 |
|---|---|---|
| **碰撞**（造两个不同输入、哈希相同） | **已被实际做到**：2017 SHAttered，约 2⁶³ 次运算，当时约 11 万美元 GPU 成本；学界后来进一步降低 | 攻击者能造出"一对"内容不同但哈希相同的对象 |
| **第二原像**（给定一个已有哈希，造另一个输入匹配它） | **仍然不可行，约 2¹⁶⁰** | **没法**针对一个已存在的特定哈希造出匹配输入 |

**一句话：SHA-1 能让你"伪造一对新东西"，但不能让你"改动已经存在的东西"。** git 自 2005 年至今默认 SHA-1；2017 年后它做了三件事：改用带碰撞检测的 `sha1dc`、拒绝含已知碰撞特征的对象、加 `transfer.fsckObjects`。git 已支持 SHA-256 仓库，但**没有迁移时间表，生态没跟上**：

| 平台 | SHA-256 仓库 |
|---|---|
| GitHub | ❌ 不支持 |
| Gitea / Forgejo | ❌ 不支持（实测推送直接断开，报 `fatal: 接收端不支持这个仓库的哈希算法`） |
| GitLab | ❌ 不支持 |
| 裸 git 仓库（ssh / 本地） | ✅ 支持 |

**用了 SHA-256 就没有 issue、没有 PR、没有 Pages——整条协作链断掉。** 这也是它被推翻的原因：`10-具体实现方案` 第 0 步曾写 `git init --object-format=sha256`，`06` 也曾建议 SHA-256，**实测后两条都作废**。

**★ 决定性判断：git 层不是我们的信任边界**（见第四节）。代价说清：commit 哈希只有 SHA-1 的抗碰撞强度，**git 层不是密码学意义上的强证据**——但它不需要是，它是运输工具。

| 什么时候重新考虑 | 那时做什么 |
|---|---|
| 主流 forge 支持 SHA-256 | 迁过去（要重写全部历史）；`data/` 里的记录**不需要重签**——签名覆盖记录内容，不覆盖 git 对象 |
| 有人开始用碰撞攻击实际作恶 | 立刻迁，或改成"只锚裸 git 仓库 + forge 只做协作" |
| 池子值钱到值得攻击 | 重新评估（现在它值钱的地方是内容，不是 commit 哈希） |

## 四、四层防护各管什么

先把混在一起的五个目标分开——**混了就会装一堆没用的东西**：**完整性**（哈希链）★必需 · **真实性**（Ed25519 签名）★必需 · **时间戳**（签名 tag，可选加 RFC 3161 TSA）★需要，因为本地时间戳可伪造 · **机密性**（age / AES-GCM）**设计上不是需求**，数据本来就公开 · **可用性**（Shamir 分片 / 备份）★需要，且最常被忽略。

| 机制 | 管什么 | 谁提供 | 少了它会怎样 |
|---|---|---|---|
| **git commit 链** | 发布与分发层面的顺序 | git | 无法可靠地分发和同步 |
| **文件内哈希链**（`prev` + `seq`） | 文件**脱离 git** 时仍能自证 | 我们自己 | 单看一个 JSONL 文件无法验证完整 |
| **Ed25519 签名** | 是谁写的 / 防抵赖 | 我们自己 | 无法归属；`author` 只是自填字符串 |
| **签名 tag** | 周期性的时间锚点 | git + 我们的密钥 | 无法证明"那时就是这样" |

**四者管四件不同的事，不重复。** `prev` 曾被建议去掉（"git 已经有链"），**结论是保留**：数据一定会和 git 分离——别人会引用某一段、复制某几行、贴在别处；行本身能连成链，搬到哪儿都可验证。**成本一行代码。** git 做不到的四件事：证明谁写的（commit author 任意伪造）、防 force push 改历史、对数据文件的语义校验（它只知道字节变了，不知道"这条 credit 的 amount 不该是负数"）、两方对账。

| 攻击场景 | 结果 |
|---|---|
| **A. 造两个不同 commit、SHA-1 相同** | 他能做到。但两个 commit 都是他自己带来的：记录里没有他的有效签名 → `p-002` 失败；他也改不了别人的记录（改了签名失效）。**无害** |
| **B. 针对已存在的 commit 造同 SHA-1 的替换品** | 需要第二原像 → **不可行（2¹⁶⁰）**，没法替换已有历史 |
| **C. 同一作者（有合法私钥）造两份 commit 哈希相同的内容，先提无害的、事后换有害的** | **唯一真实的攻击路径**。堵法：两份记录的记录级 SHA-256 哈希不同；有害那份的 `hash` 与 `sig` 对不上 → `p-001`、`p-002` 都失败，`prev` 链也会断。**即使 git 层被骗过，记录层仍会拆穿。** 而且这已不是密码学问题——他本来就有合法签名权，是人的问题 |

**★ 结论不是"SHA-1 还安全"，而是：git 层不是信任边界。** 真正的边界是记录级 `sha256(记录内容)` 串成的链加 Ed25519 签名，**任何人 clone 后跑 `python3 tools/validate` 就能独立复算，不依赖任何平台、不依赖 git 的哈希方案。**

**加固（零成本或低成本）**：① `transfer.fsckObjects` / `fetch.fsckObjects` / `receive.fsckObjects` **全部打开**，用 git 自带的碰撞检测在传输时拒绝坏对象。② **周期签名 tag**：`git tag -s cycle-2026-Q3`，tag 说明里写入各份文件的 **sha256 链尾哈希**——这是**独立于 git 哈希的时间锚点**，即使 git 的 SHA-1 被完全攻破，篡改者也没法伪造 tag 签名（密钥不在他手里）。早期文档写"四份文件"，现在是五份：requests / deliverables / credits / keyring / maintainer-log。③ tag **不是**账本记录，它不改变 `data/`——所以不会出现"tag 把自己算进去、导致自己失效"的循环引用。

**签名形态**：A. 每条记录内嵌 Ed25519 签名（跨平台、脱离 git 也能验，但要写个小 CLI 帮人签）· B. git commit 签名 GPG/SSH（平台原生显示 "Verified" 徽章，但门槛高：生成密钥、配置 git、上传公钥）· C. 两者都要（最强，**新人会被劝退**）。**★ 结论：A 必需，B 鼓励但不强制**——A 已给了全部需要的性质，B 的额外收益只是一个徽章，却会拦住一半想参与的人。配套必须有 `tools/sign` 一条命令搞定（生成密钥 / 签名 / 追加）——**它必须在 5 分钟内跑通，否则整套东西只是三个人的玩具。**

**为什么是 Ed25519**：公钥 32 字节、签名 64 字节，**能塞进 JSONL 一行不撑爆文件**；签名与验证都快；**没有随机数陷阱**（ECDSA 实现若随机数有偏会直接泄露私钥，Ed25519 是确定性的）。**SHA-256 的用处不是"防碰撞"，是防篡改**——现实中要防的是"有人手改了 JSON 里一个数字"，对它这是绝对过剩的。

**签名保证"你确实签了这句话"，不保证"这句话是真的"——签名防赖账，不防敷衍。** 这也是为什么贡献定价不能自己声明：自证在零和的分配语境下必然虚报，所以定价权在复核者手里，改 `credits.jsonl` 的提交不能由被记账的人单独完成。语料里同一条教训：

> 当一种科学话语透支它的信用度的时候，科学话语会透支信用度……在现代，就完全可以操控，完全可以通过大型的宣发机器去操控的什么信用度循环。
> —— `<ISMISM>/corpus/clean-markdown/1_实在论/1-1_复习课/1-1-2_建构论/1-1-2-1_科学知识社会学/0010_1-1-2-1_科学知识社会学_p214.md:75,83`

**时间戳三个方案**（问题：本地时间戳是自己写的，时钟可改，可以事后补一条"昨天"的记录）：**① 签名 git tag**（每周期 `git tag -s cycle-XXXX` 并 push，成本 0，防本地改历史——远端有独立时间，**主方案**）· **② 内部 TSA**（起一个只做时间戳的小服务，成本 0 但需一台常开机器，防某成员单方面改）· **③ 免费公共 TSA**（RFC 3161，如 freetsa.org / DigiCert 免费额度，成本 0，防全部——第三方时间，**加强项**）。③ 的全部做法：算出版本周期的 merkle root → `openssl` 发 RFC 3161 请求（`.tsq`）→ POST 给 TSA 拿 `.tsr` → 存进 `data/cycles/` → `openssl ts -verify -in xxx.tsr -data merkle_root.txt`。**时间戳这件事就到头了，不需要区块链。** **⚠️ 免费公共 TSA 的长期可靠性不能保证**：① 的证明永远在你自己手里，③ 的证明依赖一个可能消失的服务。

**身份必须独立于平台**：邮件地址可伪造（`git commit --author` 随便填），平台账号绑死一家公司。身份是 `data/keyring.jsonl` 里的公钥——**公钥是身份，平台只是入口**。所以换托管不改变任何一条记录的有效性；一个人可以有几个邮箱、几个账号，但签名密钥是他。**密钥丢失 = 身份丢失，所以 Shamir 备份私钥不是可选项。**

## 五、镜像机制（含三种方案的实测结果）

**为什么要有镜像：防篡改 ≠ 防复制。** 你不可能阻止别人克隆后改自己那份；你能做到的是"改了就被发现"。副本越多，改账越难——**任何一份对不上，就是事件**；国内访问 GitHub 不稳，平台封号/删库也是真实风险，所以**镜像越多越安全，这不是妥协，这就是目的。** 方向单向：**Gitea → GitHub**，权威永远在 Gitea，GitHub 那份是只读副本。

| 机制 | 实测结果 |
|---|---|
| Gitea 自带的"推送镜像"功能 | ❌ 配得起来，但 `task` 表为空、`last_update` 一直 0，同步端点返回 405。后来发现它**真的跑过**，但 **Gitea 服务没有代理环境变量 → 连不上 GitHub** |
| Gitea 仓库的 `post-receive.d/` 钩子 | ❌ 手动能跑，**真实推送时不触发** |
| **本仓库的 `.githooks/pre-push`** | ✅ **可用**（实测镜像后 SHA 一致） |

**★ 结论：最可靠的镜像点是"你自己的推送动作"——因为那个动作一定发生在本机。** 钩子只在推给 `origin`（Gitea）时镜像、不递归；凭据在 `~/.pool/github-credentials`，日志在 `~/.pool/github-mirror.log`。**顺带清掉一个隐患**：那条失败的推送镜像**把 GitHub token 明文写进了裸仓库的 `config`**，已删除记录并清掉令牌。

**三个连带教训（已变成检查项）**：**git 根本没有 `post-push` 钩子**——服务端是 `post-receive`，客户端只有 `pre-push`、`pre-commit` 等；写了个 `post-push`，它永远不会被调用，**而且 git 不报错**（`tools/verify-meta` 现在验证钩子名是 git 真认的，测试里放 `post-push` 当反例）。**目录不存在时 git 会静默跳过钩子**，所以 `bootstrap.py` 必须同时建目录**并**设 `core.hooksPath`。**别用 GitHub API 的 `size` 字段验证镜像**（刚推的仓库返回 `0`，容易误判成失败）——用 `commits` 端点核对 SHA。

**展示层：Cloudflare Pages 拉不到你本地的 Gitea**——它的 Git 集成支持 GitHub / GitLab / **自建 GitLab**，**不支持任意自建 Gitea**；另一条路是 Direct Upload（本地 `wrangler pages deploy`，不依赖任何 git 托管）。**它只从 git 构建网站，不接受 `git push`。** **方案 A（推荐）：Gitea → GitHub 镜像 → Pages 从 GitHub 构建**——一石三鸟：Git 集成零配置可用、顺带拿到第二份镜像（防篡改核心）、不额外花钱。**方案 B：Direct Upload**——完全自主、不要 GitHub 账号，代价是每次手动（或 cron）跑一次部署。**两个都做成本也是零。**（展示用 Pages，不用 Workers：Pages 更简单，够用。）

## 六、承载形式的选择（本地 / VPS / 域名 / App）

**先把三样东西的作用分开**：**仓库** = 记录与流程（申请单、交付物、复核、账本），现在就需要、现在就能用；**服务器** = 访问控制与常驻（谁能看、能否自动化），有这两类需求时才需要；**域名** = 入口与身份（一个稳定地址），服务器上线时一起。**服务器不是"仓库的升级版"**——只是"放上去大家一起看"的话，仓库的 issue / PR / review 流程天然就是申请单和复核流程。

**公网可达的三种做法：** ① **本机 + Cloudflare Tunnel**（✅ 零成本，不需要公网 IP、不需要开端口；本机跑 `cloudflared` 主动建隧道，外面通过域名进来）— 这是唯一能同时满足"本地自建"和"公网可达"的路，且和 Pages 共用一个 Cloudflare 账号；② 本机直接开端口（⚠️ 常常不行，家宽多数是 CGNAT，80/443 常被封）；③ 境外 VPS（✅ 最稳，¥30～80/月，但不叫"本地"了）。

**但四件事必须摆明**：**★ 机器必须常开**——关机 = 别人打不开 = **PR 提交不了**，这不是"偶尔"，是"这个服务不存在"；**家宽不稳**——断电、掉线、运营商维护都会让协作中断；**★ 法律边界**——本机对外提供服务**性质上仍然是"公网服务"**，没备案的域名提供 web 服务，和"自己服务器自己用"不是一回事；**单点**——你的电脑挂了权威仓库就挂了（内容还在）。第三行单独说：你此前的判断"自己服务器自己用"对**自己用**成立，但对外提供服务是另一回事；Cloudflare Tunnel 绕过了端口封锁和 CGNAT，**但不改变法律性质**。不劝你，只要求这个选择是知情的。

**迁到 VPS 的触发条件**（建议写进规范）：别人抱怨访问不稳 / 你不想让机器常开 / 参与人数超过 3～5 人 / 数据量超出本机舒适区。**迁移成本极低，因为 Gitea 的数据就是一个目录——换机器 = 拷目录 + 改 DNS。**

**备案**：只要有一个 DNS 可解析、能被访问的站点，大陆服务器就需要 ICP 备案——**哪怕只给成员看**，这和"内部使用"无关。A. 境外 VPS（推荐）：不备案，¥30～80/月，缺点是访问速度与国内部分网络不稳；B. 境内 + 备案：需 1～3 周、需主体材料，而**现在没有主体**会卡住，且一旦备案就等于对外声明"这是对外站点"；C. 不租，先用仓库 + 本机 Gitea：不备案、零成本，缺点是没有成员制访问控制。**建议：先 C，需要时再 A；不要碰 B。**

**域名与服务器必须分离**（弄混以后很难拆）：注册商选能随时转出的（Cloudflare / Namecheap / Porkbun / 阿里云都行）；**DNS 放 Cloudflare**；服务器独立于域名商挑，**不要用"域名商送的服务器"或"服务器商送的域名"**；**所有账号用组织邮箱注册，不用私人邮箱**。**理由很实际：换服务器商是常事，换域名商是灾难**；账号归属一旦用私人邮箱，迁移成本随时间上升，现在改是零成本。

**关于 App：先别用"App"这个词**——"加 App"之前必须先回答"哪个功能在手机上做不到"。手机上提单看单 → **响应式网页（PWA 即可）**；收到通知 → 邮件 / 群机器人；离线看资料 → 不必要，资料在服务器上；独立身份感 → 品牌，最贵也最没用。**原生 App 的真实代价不是开发，是持续维护**：上架、签名、系统升级适配、双端各一份——**三五个人维护不了一个 App。** 顺序必须是：服务器 + 网页 → 用满一个周期 → 再看要不要 App。

**硬边界：三层分离，agent 只能提案。** ① **数据层（唯一真相）**：`data/*.jsonl`，append-only + 哈希链，只有它能改状态，且只能通过签名的写入接口；② **应用层（读写逻辑）**：成员认证、提单、认领、复核、账本追加，不保存任何私有状态，随时可以重建；③ **代理层（agent / 模型）**：整理、撮合建议、初筛、生成草稿，**只能产出「提案」，不能直接落账**。**★ 第 ③ 层的规则是关键**：原因不是保守，而是**账本是唯一的真相来源，而 agent 的输出不可复现**（同一提示词两次结果不同）——**一个不可复现的写入者，不能是真相来源的写入者。** **运维纪律：账本每天自动备份到另一个供应商**（不是同一家的对象存储）；**账本是唯一不可重建的东西**，代码和界面都能重写。

## 七、为什么不做某些事

| 不做 | 为什么 |
|---|---|
| **加密 at rest（age / SOPS / GPG）** | 数据本来就公开，**机密性在设计中不是需求**；本地 `chmod 700 data/` 加全盘加密就够。只担心 `alias_salt` 的话用 SOPS 加密那一个字段；上服务器时再上 age。**只在丢设备时才重新考虑** |
| **Docker 部署 Gitea** | **Docker Hub 在这台机器上连不上**；改用单二进制 + systemd 常驻 |
| **数据库（SQLite / Postgres）** | JSONL 用 git 管就够；加了数据库就有"数据库是真相还是文件是真相"的问题，而且余额会被缓存进去。代价是查询要全表扫描——池子小，毫秒级 |
| **自建数据 API** | `data/` 是纯文本，clone 就能读，比 API 更直接 |
| **区块链 / 代币** | 它提供四样：免信任防篡改（不需要，防的是"事后改账"）、全局时间戳（**已用签名 tag 解决**）、公开可验证（不需要，完全公开反而多一层暴露）、可转让凭证（**不需要且有害，可转让 = 触碰合规红线**） |
| **硬件密钥（YubiKey）** | 三五个人阶段是过度投资。**但它确实是"私钥不被偷"的最优解**，人多可考虑 |
| **任何第三方加密 / 备份 SaaS** | **数据出去就不再是内部使用**——会打破那个让整套设计不需法务的前提 |
| **自研密码学** | **永远不要。** 用库，不要自己写算法 |
| **给前端写权限** | 前端只读，所以它不可能绕过校验；配置也不进 `data/`（否则改配色都要两人签字，且成自指循环） |

**依赖越少越安全**：每个依赖都是供应链攻击面，加密方案里最可能出问题的**不是算法，是某个包的某次更新**。所以要么 `cryptography` 一个包（已含 Ed25519 / SHA-256 / Argon2 / AES-GCM），要么 `age` + `minisign` + `ssss` 三个单二进制、零运行时依赖、加起来不到 2 MB。

**最小可行组合（约 100 行，覆盖四个目标）**：① Ed25519 + SHA-256 哈希链（完整性 + 真实性，~30 行）② git（事务 + 异地备份）③ 每周期 `git tag -s`（时间戳，~10 行）④ `chmod 700 data/`（访问控制，0 行）⑤ Shamir 分片备份仓库远端凭据（灾难恢复，~20 行）。**Shamir 的典型用法**：把恢复密钥分成 5 份，任意 3 份可恢复，5 个成员各持一份。**注意**：Argon2id 只用于从"人记得住的密码"派生加密密钥；**成员签名私钥不要用密码派生**，直接随机生成后用 Shamir 备份。

**威胁 → 工具的对应**：有人事后改日志 / 改余额 → 哈希链 + Ed25519；"这条不是我提的" → 签名（签名就是防抵赖）；"这条是后来补的" → 签名 git tag（v1）→ 可选加 TSA；笔记本丢了、数据被看到 → 全盘加密（最省事）或 age；某人私钥丢了无法恢复 → Shamir 分片；主力机器挂了 → `git push` 到私有远端（1 行）；**怕被胁迫 → 超出技术范围。** 当初的代码量估量：`tools/sign` ~80 行（**新人唯一的门槛**）、`validate` ~200 行、`build-site` ~60 行。

**最后一条认真的边界**：任何本地加密方案都挡不住有人逼你说出密码。**如果被胁迫是真实威胁，技术不是答案。**

## 八、可替换性清单

| 层 | 现在选 | 能换吗 | 怎么保证能换 |
|---|---|---|---|
| **记录格式（schema）** | JSONL + `docs/02-credit.md` / `policies.jsonl` 里的字段 | ❌ **唯一不可替换** | 工具围着它转，不是它围着工具转 |
| git 托管 | 本机 Gitea →（触发条件后）境外 VPS | ✅ | Gitea 数据就是一个目录；换机器 = 拷目录 + 改 DNS |
| 公开镜像 | GitHub（可再加 Gitee / 另一个账号） | ✅ | 都只是同一套提交的副本 |
| 展示 | Cloudflare Pages（A 或 B） | ✅ | 静态站点产物，换托管不影响数据 |
| 数据库 | 先不上 | ✅ | JSONL + git 就够 |
| 认证 | 本机 Gitea 账号 / 服务器账号 | ✅ | 身份在 `keyring.jsonl` 的公钥里，不在某个平台的用户体系里 |
| 域名 / DNS | Cloudflare（DNS 与服务器分离） | ✅ | 独立于服务器商 |
| Agent / 模型 | 任意 | ✅ | 账本只记模型 ID 与版本 |

**★ 唯一的不可替换件是 schema，其余全部可换。判断标准：任何时候删掉除 `data/` 以外的一切，系统必须能完全恢复。** 所以优先级一直很清楚：**先把字段定死，再谈挑服务器。**

**"租服务器"是一个感觉在做实事、其实可能什么都没推进的动作**——它花钱不多，但会让人产生"基建搞好了"的满足感，而池子里可能一条申请单都没有。

> **organization for practice by itself**（把组织本身误当实践）
> —— `library/themes/governance-law-bureaucracy/governance-law-bureaucracy-synthesis.md:15`

**只有出现下面任一条，才租服务器 + 域名**：需要成员制访问控制；需要常驻自动化（bot、定时校验、自动备份）；仓库在国内访问不可靠；资料量超出仓库舒适区。**这几条建议写进规范，而不是凭感觉。** 而在此之前，先把流程跑满一个周期（**90 天**），只看三个数：**成案数 / 打回率 / 复用次数**。

## 九、边界与风险

| # | 边界 | 说清 |
|---|---|---|
| 1 | **签名防赖账，不防敷衍** | 校验器能证明"复核者是谁"，不能证明"他真的读了" |
| 2 | **11 条规则只覆盖形式条件** | 复核者是否真的独立判断过，机器查不了。3～5 人互相认识的阶段可以接受；"复用"是唯一无法伪造的加成项，它让敷衍留下痕迹 |
| 3 | **时间戳不是区块链** | 依赖 tag 签名（可选 TSA）；免费 TSA 的长期可靠性不保证 |
| 4 | **Gitea 是单点** | 机器关了协作就停摆（内容还在，GitHub 镜像还在）；镜像也不是实时的，等于你最后一次 push 时的状态 |
| 5 | **机器常开 + 家宽不稳** | 四条里最容易被低估的是"关机等于服务不存在"；对外提供服务的法律性质，Tunnel 绕不过 |
| 6 | **git 层不是强证据** | commit 哈希只有 SHA-1 抗碰撞强度；核心证据在记录层 |
| 7 | **agent 输出不可复现** | 所以它只能提案，不能落账 |
| 8 | **胁迫超出技术范围** | 不假装它不存在 |
| 9 | **协作过程与身份没有冗余** | Gitea 数据要单独备份；私钥丢了就是身份丢了 |

**未决 / 未落地**（见上方各处 `缺口`）：域名与 Tunnel、Pages 构建管线、Gitea Actions runner、异地备份与 Shamir、TSA。**这些都不阻塞现在的流程**——现在的流程是本地签署 + 本地校验 + 推送时镜像。
