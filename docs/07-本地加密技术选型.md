# 本地加密技术选型

> 已定：不上链。本文回答"本地几乎零成本能用的加密技术"。
> 核心提醒：**"加密"混了五个不同的目标，混了就会选错工具、装了没用的东西。**

---

## 一、先把五个目标分开（混了就白装）

| 目标 | 白话 | 对应技术 | 你需要吗 |
|---|---|---|---|
| **完整性** | 记录没被改 | 哈希链 / Merkle 树 | **★ 必需** |
| **真实性** | 是谁写的，不可抵赖 | 数字签名（Ed25519） | **★ 必需** |
| **时间戳** | 是那个时候写的 | RFC 3161 TSA / 签名 tag | **★ 需要**（本地时间戳可伪造） |
| **机密性** | 别人看不到内容 | 对称加密（age / AES-GCM） | **只有丢设备时才需要** |
| **可用性** | 丢了能恢复 | Shamir 分片 / 备份 | **★ 需要**（但常常被忽略） |

**★ 一个常见误区：以为"加密"= 机密性。**

你们的信用记录**本来就对全体成员公开**——所以机密性在**设计上不是需求**。它只在一种情况下变成需求：**设备丢失或服务器被他人控制。**

**所以你们真正要的不是"加密"，是完整性 + 真实性 + 时间戳 + 可恢复性。** 装一个加密软件解决不了这四个里的任何一个。

---

## 二、工具箱（全部免费、本地、无外部依赖）

### 2.1 完整性 + 真实性：Ed25519 + SHA-256

| 项 | 值 |
|---|---|
| 算法 | **Ed25519**（签名）、**SHA-256**（哈希） |
| 库 | Python: `cryptography`；Node: `@noble/ed25519`；CLI: `minisign` / `signify` |
| 成本 | **0**（都是标准库级别） |
| 代码量 | 约 30 行 |

**为什么是 Ed25519 而不是 RSA / ECDSA：**
- 密钥短（32 字节公钥、64 字节签名）→ **可以塞进 JSONL 一行，不撑爆文件**
- 签名快、验证快
- **没有随机数陷阱**（ECDSA 的实现如果随机数有偏会直接泄露私钥；Ed25519 是确定性的）
- 你们的 schema 已经定了用它

**SHA-256 的用处不是"防碰撞"**——是防篡改。**现实中你需要防的是"有人手改了 JSON 里的一个数字"，SHA-256 对这个是绝对过剩的。**

### 2.2 时间戳：三个方案，从零成本开始

**问题回顾：本地时间戳是你自己写的，时钟可改，可以事后补一条"昨天"的记录。**

| 方案 | 做法 | 成本 | 防谁 |
|---|---|---|---|
| **① 签名 git tag** | 每周期 `git tag -s cy-0002` 并 push | **0** | 防本地改历史（远端有独立时间） |
| **② 内部 TSA** | 起一个只做时间戳的小服务，把 root 发它，它签名返回 | 0（需一台常开机器） | 防"某成员单方面改" |
| **③ 免费公共 TSA** | RFC 3161，如 `freetsa.org`、`DigiCert` 免费额度 | **0** | 防全部（第三方时间） |

**建议：v1 用 ①，需要更强时加 ③。**

**③ 的具体做法（值得知道，因为它成本为零）：**

```
1. 算本周期的 merkle_root
2. 用 openssl 发一个 RFC 3161 请求（.tsq）
3. POST 到免费 TSA → 拿回 .tsr（带 TSA 签名的响应）
4. 把 .tsr 存进 data/cycles/ 目录
5. 验证：openssl ts -verify -in xxx.tsr -data merkle_root.txt
```

**这就是"时间戳"这件事的全部，不需要区块链。** 一个第三方（TSA）签名证明"这个哈希在某个时刻之前就存在"。

**⚠️ 但要注意：免费公共 TSA 的长期可靠性不能保证。** 所以 ① 是主方案，③ 是加强项——**而且 ① 的证明永远在你自己手里，③ 的证明依赖一个可能消失的服务。两个一起用最稳。**

### 2.3 机密性：age（我推荐）或 SOPS

**只在"设备丢失/服务器被他人控制"时才有用。**

| 方案 | 适用 | 成本 |
|---|---|---|
| **age** | **单文件加密，单二进制，无依赖，现代（X25519 + ChaCha20-Poly1305）** | 0 |
| **SOPS** | 加密 JSON/YAML 的**部分字段**（比如只加密 `alias_salt`），其余保持可读 | 0 |
| GPG | 功能全但**难用、易错**，不推荐新人 | 0 |
| 全盘加密（LUKS / FileVault） | 最省事，**开机后全明文** | 0 |

**★ age 的一句话评价：它是这十年里 GPG 唯一真正的替代品。** 用法就是 `age -r <公钥> -o out.age in.jsonl`，反向 `age -d`。支持多收件人（每个成员一个公钥）。

**建议：**
- **v1 不上加密。** 数据在你自己机器上，`chmod 700` 就够
- **上服务器时再上 age**，加密整个 `data/` 目录
- **如果只担心 `alias_salt` 泄露**，那用 SOPS 只加密那一个字段

### 2.4 可恢复性：Shamir 分片

**这一条经常被忽略，但它比加密重要得多——因为"数据丢了"比"数据被看了"后果严重得多。**

| 项 | 值 |
|---|---|
| 算法 | **Shamir's Secret Sharing**（k-of-n 门限） |
| 工具 | `ssss`（C，单二进制）、`secretsharing`（Python） |
| 成本 | 0 |
| 用途 | **私钥备份、恢复码分片** |

**典型用法**：把"备份仓库的加密密钥"分成 5 份，3 份可恢复。**5 个成员各持一份，任意 3 人凑齐就能恢复整个池子。**

**★ 这直接落地了前面文档里那条约束**：v2 里定的"恢复码由 3 人各持一份"——**Shamir 就是它的实现方式，不需要信任任何人，也不需要任何人单独持有完整密钥。**

### 2.5 密钥派生：Argon2id

| 项 | 值 |
|---|---|
| 用途 | 从**人类记得住的密码**派生出**加密密钥** |
| 库 | Python: `argon2-cffi`；CLI: `age` 自带 scrypt |
| 成本 | 0 |

**为什么不能直接用密码当密钥**：人会选弱密码。Argon2id 是**故意设计成慢且吃内存**的，让暴力破解代价极高。

**注意区分：** Argon2id 是给"人输入的密码"用的。**成员签名用的私钥不要用密码派生**——直接生成随机密钥，然后用 Shamir 备份。

## 三、按威胁场景给建议（别全装）

| 你担心的 | 用什么 | 代码量 |
|---|---|---|
| **有人事后改日志 / 改余额** | 哈希链 + Ed25519 签名 | ~30 行 |
| **有人说"这条不是我提的"** | 同上（签名就是防抵赖） | 0（同一个） |
| **有人说"这条是后来补的"** | **签名 git tag**（v1）→ 可选加 TSA | ~10 行 |
| **笔记本丢了，数据被看到** | **全盘加密**（最省事）或 `age` | 0 / ~5 行 |
| **某人私钥丢了，无法恢复** | **Shamir 分片** | ~20 行 |
| **主力机器挂了，池子没了** | **git push 到私有远端** | 1 行 |
| **怕被胁迫说出密码** | 这超出技术范围 | — |

**★ 最后一行是认真的。** 任何"本地加密方案"都挡不住有人逼你说出密码。**如果这是真实威胁，那技术不是答案。** 大多数情况下它不适用，但我不要假装它不存在。

## 四、最小可行方案（覆盖 90%，约 100 行）

```
① Ed25519 签名 + SHA-256 哈希链        ← 完整性 + 真实性
   Python: pip install cryptography
   ~30 行

② git（事务 + 备份）                    ← 可恢复性（异地）
   已有

③ git tag -s 每周期一次                 ← 时间戳
   ~10 行

④ chmod 700 data/                       ← 最基础的访问控制
   0 行

⑤ Shamir 分片备份"仓库远端访问凭据"       ← 灾难恢复
   pip install secretsharing
   ~20 行
```

**就这五条。** 全部免费、全部本地、全部无外部依赖（除了 git 远端）。

**加起来约 100 行代码，覆盖了完整性、真实性、时间戳、可恢复性四个目标。**

### v1 明确不装的

| 不装 | 为什么 |
|---|---|
| age / SOPS / GPG | 数据在自己机器上，**`chmod 700` 加全盘加密就够** |
| 区块链 / OpenTimestamps | 已排除；TSA 或签名 tag 已经够 |
| 硬件密钥（YubiKey） | 三五个人阶段是过度投资。**但它确实是"私钥不被偷"的最优解**，将来人多可考虑 |
| 任何第三方加密 SaaS | **数据出去就不再是内部使用**——这会直接打破那个让整套设计不需法务的前提 |
| 自研密码学 | **永远不要。** 用库，不要自己写算法 |

**★ 倒数第二条最重要。** 任何"把数据传给第三方做加密/备份"的服务，都会**打破"内部使用"这个前提**。整个设计的法律简洁性就建立在数据不出去这一点上。

## 五、一个容易被忽略的点：依赖越少越安全

**你们不需要"很多加密技术"。** 需要的是**很少几个、被广泛审计过、依赖极少的工具**。

理由：**每一个依赖都是供应链攻击面。** 一个加密方案里最可能出问题的不是算法，是**某个包的某次更新**。

| 选择 | 依赖数 |
|---|---|
| Python `cryptography` | 一个包，底层是 OpenSSL / BoringSSL |
| `age` | **单二进制，无运行时依赖** |
| `minisign` | **单二进制，无依赖** |
| `ssss` | **单二进制，无依赖** |
| 自己用 Node 拼一堆小包 | 几十个，每个都可能出事 |

**所以如果你们要一个"最干净"的组合：`age` + `minisign` + `ssss`，三个单二进制，零运行时依赖。** 三个加起来不到 2 MB，全平台可用，不需要 pip / npm。

**但既然你们已经要用 Python 写 CLI，那 `cryptography` 一个包就够了**——它已经包含了 Ed25519、SHA-256、Argon2、AES-GCM 全部。

---

## 六、一句话

> **你们需要的不是"加密"，是完整性 + 真实性 + 时间戳 + 可恢复性。**
> **Ed25519 + SHA-256 哈希链给前两个，签名 git tag（可选加免费 TSA）给第三个，Shamir 分片 + git 远端给第四个。**
> **约 100 行代码，全部免费本地。机密性在你们这个设计里根本不是需求——只在丢设备时才有意义。**

## 七、需要你确认

1. **是否接受"v1 不上加密，只用签名 + 哈希链 + git tag + Shamir"**（我建议接受）
2. **时间戳**：只用签名 git tag，还是一起用免费公共 TSA
3. **Shamir 分片备份什么**：仓库远端凭据 / 恢复密钥 / 两者都备
4. **是否要我把这四样写进第 1-4 步的代码**（`cryptography` 一个依赖就够）
