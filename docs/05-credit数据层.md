# credit 的数据层：本地还是区块链

> 澄清：上一份 `credit基于什么.md` 答的是"credit 值多少钱"。这一份答"credit 记在哪"。
> 结论先说：**本地 JSONL。不上链。**

---

## 一、你的四个选项

| 方案 | 数据在哪 | 谁维护 | 防篡改靠什么 |
|---|---|---|---|
| **A. 完全本地** | 你的磁盘 | 你 | 没有（只有文件权限） |
| **B. 本地 + 哈希链 + 签名 + git** | 你的磁盘 + 私有远端 | 你（单写者） | **链式哈希 + Ed25519 + git 历史** |
| **C. 公链** | 区块链 | 全网矿工/验证者 | 共识 |
| **D. 联盟链 / 自建链** | 几台机器 | 成员 | 共识 |

**我建议 B。** 下面说为什么。

---

## 二、区块链到底多给了什么

区块链在这件事上**只提供四样东西**，逐条对一下：

| 区块链提供的 | 你需要吗 | 为什么 |
|---|---|---|
| **① 免信任的防篡改** | **不需要** | 你们是熟人内部池子。**防的是"事后改账"，不是"互不信任的对手方"** |
| **② 全局共识时间戳** | **★ 有真实价值** | 见第五节——但**有零成本的替代方案** |
| **③ 公开可验证** | **不需要** | 你们是"对成员公开"。**公开上链反而违背内部使用的前提** |
| **④ 可转让凭证** | **不需要，且有害** | 你们已经定了 credit 不转让、不兑换。**可转让 = 触碰合规红线** |

**只剩第 ② 条它是真的更强。** 其余三条要么不需要，要么是负担。

---

## 三、上链的六个代价（都跟 credit 直接相关）

| # | 代价 | 说明 |
|---|---|---|
| **1** | **签名失效** | 记录上链后哈希不可变，但**你会需要改错**。你们的 schema 用 `amend` + `supersedes` 处理这个——上链之后只能**再发一条修正记录**，永远带着污点 |
| **2** | **隐私** | credit 连着人名。上链就是**永久公开谁拿了多少**。而且私钥和地址的关联性是公开的 |
| **3** | **成本与速度** | 每条记录一次交易 → 慢且贵。**批量锚定（只上 Merkle root）能解决，但那已经不是"credit 记在链上"了** |
| **4** | **法律** | 发行、交易、兑换是明确红线（94 公告 / 924 通知）。**"credit 上链"这句话本身就会让整件事的性质模糊化**——哪怕你只是记录不交易 |
| **5** | **可读性** | 你要能打开一个纯文本文件，从第一条读到最后一条，全部看懂。**链上做不到** |
| **6** | **依赖** | 链的共识、客户端、gas 市场、钱包——**这些都比你们的池子活得久或短，你无法控制** |

**第 2 条和第 4 条是决定性的。** credit 带着人名上链，等于永久公开每个成员的产出历史——**这和"内部使用"直接矛盾。**

---

## 四、为什么 B 够用：它在技术上已经等价

你现在的 schema 已经具备：

| 性质 | 靠什么实现 |
|---|---|
| **不可篡改** | 每条 `hash` 包含上一条 `hash`（链） |
| **不可伪造** | 每条 Ed25519 签名 |
| **不可抵赖** | 签名只有本人有私钥 |
| **可验证** | 任何人拿到文件就能重算全链 |
| **可回溯** | git 历史 + 周期 Merkle root |
| **可恢复** | `git push` 到私有远端 = 异地备份 |

**★ 一个容易被忽略的点：链上"不可篡改"和你的"只追加"是同一个性质。**

区块链用**分布式共识 + 经济激励**来实现"谁都不能改历史"。
你用**哈希链 + 签名 + 单写者**来实现同一件事。

**区别只在"防谁"：**
- 区块链防的是**互不信任的陌生人**
- 你防的是**事后想改账的自己人**

**对后者，"单写者 + 全员可验证"是完全够的**——因为**任何成员都能自己重算全链**，改一个字就露馅。**群体监督就够了，不需要共识。**

---

## 五、唯一值得借鉴区块链的地方：时间戳

**B 方案有一个真实弱点：时间戳是你自己写的。**

- 你的系统时钟可以改
- 你可以事后补一条"昨天"的记录
- 哈希链能证明**顺序**，但**不能证明那条记录真的是那个时候写的**

**这个弱点是真的**，而且它是唯一一个"上链确实更强"的地方。

### 三个替代方案（成本从 0 开始）

| 方案 | 做法 | 成本 | 可信度 |
|---|---|---|---|
| **① 签名 git tag** | 每周期打一个签名 tag 并 push 到私有远端 | 0 | 中（远端有独立时间） |
| **② 邮件自证** | 把 Merkle root 发到自己的邮箱 | 0 | 中（邮件服务器有独立时间戳） |
| **③ OpenTimestamps** | 把 Merkle root 锚定到比特币 | **≈0** | **高（真正的链级时间戳）** |

**★ 方案 ③ 值得专门说，因为它可能正好是你想要的东西：**

**OpenTimestamps 只把哈希（32 字节）锚到一个比特币交易里，不上传任何数据、不发币、不做金融。**

- 数据仍然完全在本地
- 只多了一个"这个哈希在某个时刻之前就存在"的证明
- **不碰发行、交易、兑换任何一条红线**
- 免费（聚合器把成千上万个哈希打成一个交易）

**这大概是"用区块链"这个直觉的正确落点：不用它存数据，只用它盖章。**

**建议：v1 先做 ①（签名 tag），等周期跑顺了再加 ③。** 因为 ① 零成本、零依赖，而 ③ 需要额外的工具链——**不值得在第一个周期就引入。**

## 六、一份明确不做的清单（防止范围蔓延）

| 不做 | 为什么 |
|---|---|
| credit 上公链 | 隐私 + 法律 + 无收益 |
| 发代币 | 明确红线 |
| 智能合约自动结算 | 规则是数据、写在本地；上合约等于**把规则冻结在不可改的代码里**，和"规则即数据"直接冲突 |
| 钱包 / 私钥托管 | 成员私钥只在自己机器上，**池子不托管任何人的私钥** |
| 自建联盟链 | 三五个人不需要共识，只需要**全员可验证** |

**★ "智能合约自动结算"那条值得多想一秒：** 它的诱惑是"规则不可改，所以可信"。**但你们的规则会变**——衰减参数、加成系数、阈值，这些第一个周期之后一定会调。**写进合约 = 永远调不了。** 而"规则是数据"意味着调规则是追加一条记录，全程留痕。**后者既灵活又同样可审计。**

---

## 七、落点：credit 存在哪（具体到文件）

```
本地磁盘（唯一真相）
├── data/credits.jsonl              ← ★ credit 唯一的存储位置
│     每条：seq / at / prev / sig / hash / member / amount / reason / refs
│     append-only，链式哈希，Ed25519 签名
└── .index/balances.json            ← 推导缓存，可随时删掉重建
                                     （余额不是存储的，是扫描算出来的）

异地（备份，非真相）
├── git 私有远端                     ← git push，含完整历史
└── 周期 Merkle root（将来）
      ├─ 签名 git tag               ← v1
      └─ OpenTimestamps             ← 将来可选
```

**★ 一条不能破的规则：余额永远不是存储的，是算出来的。**

一旦你把余额写进磁盘，就有了两份真相（事件日志 + 余额快照），它们迟早不一致。**这也是为什么数据库在 v1 里是多余的**——数据库最大的诱惑就是"存一份算好的结果"，而那正是要避免的。

**判断标准（前面定过，这里再确认一遍适用性）：任何时候删掉除 `data/` 以外的一切，系统必须能完全恢复。** `credits.jsonl` 满足这条，链上方案不满足——**因为链上数据不在 `data/` 里，你无法"完全恢复"到本地。**

---

## 八、一句话

> **credit 记在本地 `data/credits.jsonl`：append-only、链式哈希、Ed25519 签名、git 做备份。**
> **不上链——因为区块链多给的四样东西里，三样你不需要，一样（可转让）是红线。**
> **唯一值得借鉴的是时间戳。用签名 git tag，将来可选 OpenTimestamps——只锚哈希，不存数据。**
> **判断标准：删掉除 `data/` 之外的一切，必须能完全恢复。链上方案过不了这一条。**

---

## 九、需要你确认

1. **确认走 B**（本地 + 哈希链 + 签名 + git），还是仍要上链（若上链，我建议只锚 Merkle root）
2. **时间戳方案**：v1 只用签名 git tag，还是直接上 OpenTimestamps
3. **备份时机**：每周期 push 一次，还是每次操作都 push（后者更安全但更吵）
