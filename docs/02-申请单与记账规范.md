# 申请单与记账规范 v1

> 依据：本轮确认的六条
> ① 平台只提供接触面和规则，不经手钱 ② 对成员全公开 ③ 内部使用，不考虑版权 ④ 核心人共同维护，维护者必须被约束 ⑤ 接单只记事情、credit、效果，不管人 ⑥ 实名；问题也算贡献；维护者开头是雁雁（或以雁雁为主的核心）
> 本文解决你留的那件：**协作申请 / 知识需求申请的原子单位。**

---

## 零、先说一个结论

**"不管人"这条不是简化，是把设计做对了。** 因为它逼出一个更好的原子单位：

> **原子单位是一条「申请单」，而申请单描述的是一个「还不存在的产物」。**
> **人被记在账上（内部），不记在单上（公开）。**

这样仓库层和协作层就接上了：**申请单是"池子里缺什么"的记录，交付物是"池子里多了什么"的记录。** 一个是进口，一个是存货。

---

## 一、原子单位：申请单（Request）

### 1.1 定义

**一条申请单 = 一个可验收的、尚不存在的产物。**

不是"一个任务"，不是"一个帖子"，是**一个产物**。因为只有产物能验收，而只有能验收的东西才谈得上完成和 credit。

| 要素 | 说明 |
|---|---|
| **产物形态** | 必须是**某个池子里能放的东西**（见 1.3） |
| **验收标准** | 写出"怎么算做完了"。**没写就不算一条合格的申请单** |
| **关联** | 挂在哪个板块 / 哪个主题 / 哪个已有产物上 |

### 1.2 字段（公开层，不含任何人名）

```jsonc
{
  "id": "r-0001",                    // 单号，唯一的身份
  "type": "need | offer | challenge",// 三类，见 1.4
  "title": "一句话说清缺什么",
  "artifact_kind": "knowledge_pack | answer | tool | curation | translation | question",
  "spec": "产物长什么样（形态、范围、精度要求）",
  "acceptance": "怎么算做完了（可判定的）",
  "links": ["关联的板块/主题/已有产物 id"],
  "status": "open | claimed | delivered | accepted | closed | expired",
  "deliverable_id": "d-0007",        // 关闭时回填
  "created_at": "2026-09-16",
  "notes": []
}
```

**注意这份字段里没有人。** 谁提的、谁接的、谁复核的，全部在 2.x 的内部账里。**这就是"不管人"的落地方式——不是不记，是分层记。**

### 1.3 产物形态（`artifact_kind`）——六种就够

| 形态 | 是什么 | 例子 |
|---|---|---|
| `knowledge_pack` | 带证据链的结论单元 | 一个概念在语料里的义项辨析 |
| `answer` | 对某个问题的回答（**可以很短**） | "无对价行动和交易的分界线在哪" |
| `tool` | 能跑的代码/脚本 | 一个锚点校验脚本 |
| `curation` | 整理、校对、补锚点 | 给某个主题补 20 条引文锚点 |
| `translation` | 跨语言或跨术语体系的对照 | 术语英译对照表 |
| **`question`** | **一个好问题本身** | "为什么制度化必然形式主义化" |

**★ `question` 是独立形态，而且和 `answer` 平级。** 你确认了"问题等都算贡献"——那就必须在形态里给它身份，否则它会被当成"没有交付物的申请单"，永远结不了案。

**给问题定 credit 的依据**：一个问题被采纳为**独立主题**或被**≥2 条产物引用**，即成案。

### 1.4 三类（`type`）

| 类型 | 语义 | 谁提 |
|---|---|---|
| `need` | **我需要什么** | 需求方 |
| `offer` | **我想做什么，缺人手** | 提议方 |
| `challenge` | **我认为已有产物是错的** | 任何人 |

**我建议合并成一种单、用 `type` 区分**（而不是三个列表）。理由：三者**共享同一套状态机、同一套验收字段、同一套记账规则**，只有 `type` 不同。三个列表会让三套东西各自漂移。

**`challenge` 必须有独立类型**——因为"指出一个已有产物错了"是**最高价值的贡献**，而它在任何系统里都最容易没有归口。你们语料自己把这件事定为纪律：决定必须携带反证。

### 1.5 状态机

```
open ──claim──> claimed ──deliver──> delivered ──review_pass──> accepted
  │                │                     │                        │
  │                │                     └──review_fail──> claimed（打回重做）
  │                └──withdraw──> open（接单人放弃）
  └──expire（30 天无人接）──> expired
```

| 状态 | 含义 | 谁能改 |
|---|---|---|
| `open` | 开着，等人接 | — |
| `claimed` | 有人接了 | 接单人 |
| `delivered` | 交付了，等复核 | 交付人 |
| `accepted` | 复核通过 + 需求方确认 | 维护者确认 |
| `closed` | 结案（含"决定不做"） | 维护者 |
| `expired` | 30 天无人接 | 自动 |
| `withdrawn` | 提出人撤回 | 提出人 |

**★ `closed` 允许"决定不做"，而且这是正常结案，不是失败。** 直接照搬 ismism 的 `no-asset-needed` 纪律：**"本期不产出任何东西"是成功的决定。**

## 二、交付物与记账（内部层）

### 2.1 交付物（Deliverable）

一条申请单可以对应**多个**交付物（拆单做），一个交付物只属于一条申请单。

```jsonc
{
  "id": "d-0007",
  "request_id": "r-0001",
  "artifact_kind": "knowledge_pack",
  "content": { /* 六字段，同 v3 的知识包 schema */ },
  "contributors": ["..."],           // 内部层才有人名
  "review": { "by": "...", "result": "pass", "at": "..." },
  "accepted_by_requester": true,
  "reuse_count": 0,                  // 被其他产物引用几次
  "effect": "见 2.3",
  "hash": "..."
}
```

### 2.2 ★ credit 的确认条件（"完成 credit 的形式过程"具体化）

一条 credit 入账，**必须同时满足四条**：

1. **有交付物**（不是"我做了"，是"东西在这儿"）
2. **复核通过**，且**复核者 ≠ 交付者**
3. **需求方确认可用**（能判定 `acceptance` 字段）
4. **有哈希**，且哈希链上接得住

**缺任何一条，不入账。**

**★ 关键推论：自问自答自交付不产生 credit。**

这条是整套设计的防作弊核心——一个人可以自己提需求、自己交付、自己确认，但**因为第 2 条要求复核者不同，这个闭环不产生 credit**。所以"刷单"这件事在结构上不成立，**不需要任何稽查**。

（人可以自己接自己的单，只要走完流程。区别只是：**自己闭环的不算贡献。** 这正好对应"接单只记事情和 credit 和效果，不管人"——因为管人的部分已经被规则自动处理掉了。）

### 2.3 "效果"怎么记（三类，分开记，不许合并）

| 类 | 怎么判 | 性质 |
|---|---|---|
| **复核结果** | 通过 / 打回 | **机器可判**（形式条件） |
| **需求方验收** | 确认 / 未确认 | 人判，但**不能作为唯一门槛**（否则会互相捧场） |
| **复用次数** | 被其他产物引用几次 | **客观、滞后、最可信** |

**为什么要分三类：** 如果把三者合成一个"好评率"，它立刻会变成人情分。**分开记，就能看出"通过了但没人用"的产物——那是最值得注意的一类。**

### 2.4 失败、放弃、打回要不要记？

**记，但不挂名、只在统计层公开。**

| 记什么 | 公开层 |
|---|---|
| 打回次数 / 撤回次数 / 过期数 | 汇总数字 |
| 具体是谁 | **不出现在公开层** |

**理由**：不记就识别不出空转；挂名就没人敢提。**汇总数字能看出"这个池子在空转"，这就够了。**

### 2.5 防寡头：单一来源的 credit 占比上限

**建议加一条硬上限：任何一个来源（一个人 / 一个模型）在任一周期内计入的 credit 不超过总量的 40%。**

理由：这是**唯一一条不需要任何人做判断的反寡头机制**。它不针对任何人、不需要指认谁，只是把单点依赖自动限住。超出部分不销毁，转存到"待计"池，后续周期释放。

### 2.6 衰减（沿用上一版，标注为待你确认）

- **活跃度衰减**，非时间衰减（有产出即重置计时）
- 半衰期 180 天；首个周期设 365 天试跑
- 衰减到零后**记录仍在**，只是不计入席位与权重

## 三、★ 维护者的约束（你要求"必须被约束"，这是可执行的版本）

原则一句话：**维护者可以单方面推进，不能单方面阻止。**

| 约束 | 具体规则 |
|---|---|
| **1. 只追加不删除** | 所有记录 append-only。修订写 `amend`，保留原记录。**维护者不能删任何东西** |
| **2. 必须写理由** | 每一个 `closed` / `expired` / `review_fail` / credit 调整，都要有理由字段 |
| **3. 不能单独阻止** | 维护者**不能**单方面：关闭 `open` 单、驳回已 `pass` 的复核、修改 credit 认定。**这些都要第二人同意** |
| **4. 可以单独推进** | 维护者**可以**单方面：确认交付物、推进状态、回应急议。**推快不受限，推慢受限** |
| **5. 操作单独成账** | 维护者的全部操作记 `maintainer-log.jsonl`，每期公示一次 |
| **6. 异议必须回应** | 任何成员可对任何决定提异议（挂号制）。维护者须在 **7 天**内回应，**哪怕回应是驳回** |
| **7. 不回应即升级** | 维护者 7 天未回应，异议自动升级为"待共同裁"，由核心人共同处理 |
| **8. 公示失效** | 连续两期未公示 `maintainer-log`，维护权限自动失效，直至完成公示 |
| **9. 缺席接管** | 维护者 30 天未响应，由核心人中最先响应者接管并公示 |
| **10. 退出自由** | 维护者可随时退出，退出时**必须**完成：账本交接 + 交接演练 + 公示 |

**第 3 条和第 7 条是这套约束的真正骨头。** 其余都是形式要求；这两条保证了**维护者无法靠"不回应"来卡住任何东西**——而那是一个人掌权时最常用、也最难防的手段。

**这 10 条现在是"核心人共同维护"的具体含义。** 你说维护者必须被约束，这 10 条就是约束的内容。

## 四、公开性的落地：两层记录，同号关联

你确认了：对成员全公开、申请记录也全公开、实名。**但"不管人"又要求单上没有人。** 这两条合起来只有一种解法：

| 层 | 文件 | 含人名 | 谁可见 |
|---|---|---|---|
| **公开层** | `requests.jsonl`（申请单）<br>`deliverables.jsonl`（交付物，不含 contributors 字段） | ❌ | 全部成员 |
| **内部层** | `ledger.jsonl`（credit 收支 + 签名）<br>`members.jsonl`（成员状态）<br>`maintainer-log.jsonl`（维护者操作） | ✅ | 全部成员（内部使用，所以也是公开的） |

**"公开"在这里的含义是：全部成员可见，包括内部层。** 因为内部使用，没有对外的顾虑。**"不管人"的含义是：申请单这个协作单位本身不承载身份**——身份只在账上，账是查得到的，但单是干净的。

**两层靠 `id` 关联，不靠人名关联。**

## 五、一个必须提前说的失效条件

现在这套设计成立，**建立在"内部使用"这个前提上**。你确认了这个前提，所以：

- ✅ 版权问题不成立（不分发）
- ✅ 备案问题不成立（不面向公众）
- ✅ 版权原文可以直接进池子

**但有一条要记下来：一旦这个池子开始对外分发任何产物，前面两条同时失效。**

所以建议在规范里写一行硬约束：

> **本池内容仅供成员内部使用。对外分发任何产物之前，必须先过版权与合规复核。**

这一行字现在的成本是零，将来能省一次事故。**不是我给你留后路，是因为"内部使用"这个边界是唯一让整套设计不需要法务的支点——它值得被写下来，而不是靠记忆维持。**

## 六、还差你定的（就四条，其余我已按上面落地）

1. **单类型还是三类**：我建议**一种单 + `type` 字段**（1.4）。若你要三个独立列表，规则要写三遍、容易漂移
2. **40% 上限**要不要（2.5）。这是唯一不需要指认任何人的反寡头机制，但如果你觉得现在只有三五个人，40% 会误伤，可以改成 60% 或先 "只记录不执行"
3. **衰减参数**（2.6）：活跃度衰减 / 半衰期 180 天 —— 确认或改
4. **`question` 成案条件**（1.3）：我写的是"被采纳为独立主题，或被 ≥2 条产物引用"。这条直接决定"提问算贡献"能不能落地，需要你认可阈值

## 七、落地顺序（几乎零成本）

```
第 0 步  把这六份 JSONL 的字段定死（本文档 1.2 / 2.1 / 四节）
第 1 步  建一个私有仓库，用 issue 模板承载申请单
          提出人开 issue → 接单人认领 → 交付走 PR → 复核走 comment
          —— GitHub 私有仓库 / 自建 Gitea，两者都能承载同一套 schema
第 2 步  先自己走通一遍：提一条真申请单，自己接，找第二个人复核
          —— 验证的是"复核者能不能只靠 spec + acceptance 判定"
第 3 步  拉第一个真人进来走一遍
第 4 步  跑满一个周期（建议 90 天），看三个数：
          成案数 / 打回率 / 复用次数
          成案数 = 0 → 池子在空转，别加功能，先找原因
```

**第 2 步是关键**：它验证的是**"验收标准写得够不够清楚"**。如果第二个人只看 `spec` + `acceptance` 判定不了，那就是字段设计有问题，回去改 schema，**不要往下走**。因为整套记账的可信度全压在"验收标准可判定"这一点上。

---

## 八、一句话总结

> **申请单描述一个还不存在的产物；交付物把它变成存在的。**
> **单上没有人，账上有人。人靠产物说话，不靠身份说话。**
> **维护者能推快，不能拖慢；能做事，不能删事；必须回应，必须公示。**
