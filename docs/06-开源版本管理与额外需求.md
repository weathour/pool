# 开源版本管理的实现方式，与我们的额外需求

> 问题分两半：**别人怎么做的**（可以照搬）、**我们缺什么**（必须自己加）。
> 结论先说：**我们其实同时需要 git 和链，两者管不同的事。**

---

## 一、开源版本管理怎么运作（四种模式 + 五个成熟件）

### 1.1 四种工作流

| 模式 | 代表 | 怎么运作 | 谁有写权限 |
|---|---|---|---|
| **邮件列表 + 补丁** | **Linux 内核**、Git 本身、PostgreSQL | `git format-patch` 发邮件，维护者 review 后 `am` 应用 | 只有维护者能 push |
| **PR / MR** | 大部分 GitHub/GitLab 项目 | fork → 开 PR → CI → 维护者合并 | 只有维护者能 push 到 main |
| **Gerrit** | Android、Chromium、OpenStack | 每条改动一个 Change-Id，代码审查打分（+1/+2）后提交 | 有 +2 权限的人 |
| **信任分层** | **Debian**、Fedora、Rust | 上传者 → 赞助者 → DD/DM；或团队共管 | 分层授权 |

**★ Linux 内核那套最值得我们看，因为它解决了同样的问题：多人贡献 + 质量把关 + 身份可追溯。**

### 1.2 Linux 内核的四个具体机制

**① 维护者层级（MAINTAINERS 文件）**

内核根目录有一份 `MAINTAINERS`，**每个子系统列出维护者、审阅者、邮件列表、代码范围**。补丁流程是：

```
贡献者 → 子系统维护者 → 上游维护者（Linus）
```

**每一级都能说"不"，每一级都对自己的门负责。**

**★ 这正好对应你说的"板块维护者"。** 而且它已经有一个跑了三十年的实现方式：**一份声明式的文件，不是一套审批系统。**

**② Signed-off-by 链（DCO）**

每个补丁的提交信息里有一行：

```
Signed-off-by: 张三 <zhangsan@example.com>
```

**语义不是"版权归我"，而是一句法律声明**：

> "我证明这个改动是我做的，或者是我从一个标明来源的开源项目里拿的，并且我有权按当前许可提交它。"

**多层传递会形成一条链：**

```
Signed-off-by: 贡献者
Reviewed-by:   审阅者
Acked-by:      子系统维护者
Signed-off-by: Linus
```

**★ 这是一条"责任链"，不是"版权链"。** 每一层都对上一层背书。

**③ 不可变的历史 + 不要 rebase**

内核要求**线性历史、不要 rebase 已推送的提交、不要 force push**。原因很实在：

> **改了历史，所有下游的 clone 和 fork 都会对不上。**

**不要低估这一条**——kernel 的权威性有一半来自于"它的历史从 2005 年到现在一条没断过"。

**④ 签名 tag 用于发布**

维护者用 GPG 签名打 tag（`v6.12` 之类）。**这是内核唯一的"发布"概念，也是唯一的权威锚点。**

### 1.3 法律与归因的两种做法

| | **DCO** | **CLA** |
|---|---|---|
| 谁在用 | Linux、Git、Docker | Apache 基金会、Google、大部分公司项目 |
| 做什么 | 每个 commit 一行 `Signed-off-by` | 签一份协议，把版权授予/转让给组织 |
| 成本 | 零 | 要签字、要存证 |
| 适合 | 贡献者保留版权 | 组织需要统一版权 |

**★ 我们要的是 DCO 的形态，但不能用它的内容**——见第三节 R2。

### 1.4 ★ 一个必须提的技术事实：git 的哈希

| 项 | 事实 |
|---|---|
| git 默认哈希 | **SHA-1**（自 2005 年起） |
| SHA-1 现状 | **碰撞已被实证实现**（2017 年 SHAttered，之后有更省成本的构造） |
| git 的应对 | 加了碰撞检测；**并已支持 SHA-256 仓库**（`git init --object-format=sha256`） |
| 现状 | 绝大多数仓库仍是 SHA-1 |

**含义**：**如果你的"防篡改"要建立在 git 的内容寻址上，那就应该用 SHA-256 仓库。** 这是 2026 年做新仓库时一个几乎没有成本的选择——**但只在新建时能选，转过去很麻烦。**

**★ 这一条我建议现在就定，因为它是不可逆的。**

### 1.5 git 做不到的四件事

| git 做不到 | 为什么 |
|---|---|
| **证明谁写的** | commit author 是自己填的字符串。任意伪造 |
| **防 force push 改历史** | 有权限就能改，`git log` 之后看起来一切正常 |
| **对数据文件的语义校验** | 它只知道字节变了，不知道"这条 credit 的 amount 不该是负数" |
| **两方对账** | 它记录"什么被合并了"，不记录"双方都同意这个数字" |

## 二、★ 所以答案是：git 和链是两个不同的东西，都需要

前面一轮我说"git 已经有链，可以去掉 `prev`"。**那句话只对了一半。** 更准确的说法是：

| 机制 | 管什么 | 谁提供 | 少了它会怎样 |
|---|---|---|---|
| **git commit 链** | **发布与分发层面的顺序** | git 本身 | 无法可靠地分发和同步 |
| **文件内的哈希链** | **文件脱离 git 时仍能自证** | 我们自己 | 单看 JSONL 文件无法验证完整 |
| **Ed25519 签名** | **是谁写的 / 防抵赖** | 我们自己 | 无法归属 |
| **签名 tag** | **周期性的时间锚点** | git 本身 | 无法证明"那时就是这样" |

**四者管四件不同的事，不重复。**

**★ 但这里有个真实的取舍，取决于一个选择：**

| 如果你们… | 那么 |
|---|---|
| **信任 git 作为唯一载体**（任何人 clone 就是完整副本） | `prev` **可以去掉**，简化写入 |
| **希望数据本身自证**（单个 JSONL 文件被单独传播时也能验） | `prev` **应该保留** |

**我倾向保留 `prev`**，理由是：**你们的数据会和 git 分离**——别人会引用某一段、复制某几行、贴在别处。**如果行本身能连成链，那它被搬到哪儿都还是可验证的。**

**成本只有一行代码。**

## 三、我们的额外需求（九个，前四个是核心）

### R1 ★ 这是一个**账本**，不是代码库

**这是最根本的区别。**

| | 代码库 | 账本 |
|---|---|---|
| 记录什么 | 代码变成什么样 | **判断和承诺** |
| 错了怎么办 | 改掉，历史里留个 bug fix | **改掉就是"改账"** |
| 利益冲突 | 少 | **有**（信用就是利益） |
| 目标 | 能跑 | **可信** |

**推论**：**"改"和"篡改"必须能被区分。** 代码库里 `git commit --amend` 无所谓；账本里它就是事件。

**所以需要：**

- **只追加**：改一条记录 = 追加一条新记录 + 引用旧的
- **合并必须用 merge commit，禁止 rebase 和 force push 已发布的 main**
- **镜像持有者定期 fetch，任何 force push 立刻表现为历史分叉**
- **`data/` 目录的每次改动必须有一个可验证的理由**（即新记录里带 `reason`）

### R2 ★ 贡献归因不能自己声明

内核的 `Signed-off-by` 是**自证**——它在版权语境下够用（你得为虚假声明负法律责任）。

**但 credit 不一样**：

- 它是**分配**（谁掏多少服务器钱）
- 而且**它是零和的**——一个人多分，等于别人少分
- **自证在这种语境下必然虚报**

**所以我们的"DCO"要换内容：**

| | 内核 DCO | 我们的规则 |
|---|---|---|
| 谁声明 | 贡献者自己 `Signed-off-by` | **交付者声明 + 复核者独立声明** |
| 声明什么 | "这代码我有权提交" | **"这个东西值多少"（复核者估）+ "这确实能用"（需求方确认）** |
| 谁能改数字 | — | **不能是拿钱的人** |

**★ 这一条前面已经定了"定价权在复核者手里"，这里要把它落到 git 层面：**

> **改 `credits.jsonl` 的那次提交，不能由被记账的人单独完成。**
> 要么提交里有复核者的签名，要么它是脚本按规则自动生成的（且脚本的规则在 `policies.jsonl` 里可查）。

### R3 ★ 数据文件必须"对 git 友好"

代码文件天然对 git 友好（一个函数一个 hunk）。**JSONL 也友好，但有几个具体约束：**

| 约束 | 为什么 |
|---|---|
| **一行一条记录，永不跨行** | git diff 以行为单位。跨行记录会让 diff 无法读 |
| **字段顺序固定** | 否则每次序列化都产生无意义的 diff |
| **不用数组包整份文件** | `[...]` 形式会让整个文件成为一个巨大 hunk |
| **时间戳用 ISO 8601 带时区** | 排序和比较 |
| **永远在文件末尾追加** | 这样 diff 永远是"最后多了一行"，冲突概率极低 |

**★ 最后一条的直接好处：如果严格末尾追加，两个人的追加在 git 里几乎不会冲突**——git 能自动合并"你在末尾加了一行、我在末尾加了另一行"。**多写者问题因此大幅缓解。**

（前提是 `prev` 和 `seq` 可后补——这正是"保留 prev"和"简化写入"之间那个取舍的具体表现。）

### R4 身份必须独立于平台

Linux 用邮件地址，GitHub 用账号，Gerrit 用邮箱。

**这两者都不行**：

- **邮件地址**：可伪造（`git commit --author` 随便填）
- **平台账号**：绑死在一家公司

**我们需要的是 `keyring.jsonl` 里的公钥**——**公钥是身份，平台只是入口。**

**推论：**

- 换平台（GitHub → Gitee → 自建）不改变任何一条记录的有效性
- 一个人可以有几个邮箱、几个账号，但**签名密钥是他**
- 密钥丢失 = 身份丢失（**所以 Shamir 备份私钥不是可选项**）

### R5 需要"锚点"而不只是"发布"

内核的签名 tag 是对的，**但我们还需要把 root 打到 git 之外**（免费 TSA 或公共链），因为：

> **git tag 的签名证明"这是维护者发的"，但不证明"这个 tag 是在那个时候发的"**——除非有独立的第三方时间。

**这一条是小工作量，但它是"时间戳"这件事的完整答案。**

### R6 需要分层写入权限（Linux 有，我们要抄）

Linux 的 MAINTAINERS 是**声明式的**——一份文件说清谁管哪块。

**我们对应的是：**

- `MAINTAINERS.md` 说清谁管哪个"板块"
- **约束是"能推快、不能拖慢"**（前面已经定过）
- **每个板块的维护者只能写自己那块**——这是 git 的 CODEOWNERS 机制天然支持的

### R7 需要投票与决定也进账本

内核的决策散在邮件列表里，**事后很难查**。

**我们的维护者决定必须落在 `maintainer-log.jsonl`（或提交历史）里，带理由。** 这是 git 本身不提供的语义。

### R8 需要 CI 做语义校验

**这是 git 时代开源项目的标配，但我们的校验器和它们不同：**

| 常规 CI | 我们的 CI |
|---|---|
| 测试能过吗 | **签名有效吗、链接得上吗、验收标准写了吗、复核者是不是交付者本人** |

**★ 这是整套系统里唯一"发号施令"的地方**——见 `policies.jsonl`。

### R9 需要"只报告不判断"的定时器

**CI 只在有 PR 时触发**，它看不到"某张单已经两周没人动"。**这是 cron 的活**（前面已定）。

## 四、可以直接照搬的七个成熟做法

| # | 做法 | 来源 | 我们怎么用 |
|---|---|---|---|
| 1 | **声明式维护者文件** | Linux `MAINTAINERS` | `MAINTAINERS.md` + `CODEOWNERS` |
| 2 | **线性历史，禁止 rebase/force push** | Linux | 保护 main，merge 用 merge commit |
| 3 | **签名 tag 作为发布** | Linux | 每周期打一个，写明关键数字 |
| 4 | **每个改动带理由** | Linux commit message | 记录里必须有 `reason` 字段 |
| 5 | **CI 门禁** | 所有现代项目 | `validate` 作为必需检查 |
| 6 | **issue 模板规范入口** | GitHub 生态 | 申请单走 issue 模板，字段固定 |
| 7 | **DCO 形态（不抄内容）** | Linux | 见 R2 |

**★ 第 6 条容易被忽略，但它就是我们的"公告板界面"。** GitHub / Gitea 的 issue 模板能让"开单"变成一个填表动作——**不需要开发任何前端。**

## 五、一句话对照表

| 需求 | 开源惯例能满足吗 | 我们怎么办 |
|---|---|---|
| 分发与镜像 | ✅ 完全满足 | 用 git |
| 顺序与完整性 | ✅ 满足 | git commit 链 |
| 内容自证（脱离 git） | ❌ | **保留 `prev` 哈希链** |
| 归属与防抵赖 | ❌ | **Ed25519 签名 + keyring** |
| 独立时间戳 | ❌ | **签名 tag + 免费 TSA** |
| 只追加、区分"改"与"篡改" | ⚠️ 部分（禁 rebase） | **书面规则 + 数据自带的 `supersedes`** |
| 贡献定价不能自证 | ❌ | **复核者估算 + 规则写在 policies** |
| 语义校验 | ⚠️ 需自己写 | **`validate` + policies.jsonl** |
| 守时提醒 | ❌ | **cron 脚本** |
| 身份独立于平台 | ❌ | **公钥即身份** |

**✅ 是"直接抄"，❌ 是"只有我们有这个需求"。**

## 六、需要你定（三个，都在这一轮新出现）

1. **★ git 用 SHA-256 还是 SHA-1**（`git init --object-format=sha256`）
   **只在新仓库时能选，转过去很麻烦。** 我建议 SHA-256
2. **保留还是去掉 `prev`**
   - 去掉：写入更简单，多写者更好合并
   - 保留：数据脱离 git 也能自证，**成本一行代码**
   **我建议保留**（因为你们的数据一定会被单独引用和传播）
3. **是否抄 Linux 的 MAINTAINERS + CODEOWNERS 形态**（我建议抄，零成本）

## 七、一句话

> **开源版本管理的成熟件可以直接抄七个：维护者文件、线性历史、签名 tag、改动带理由、CI 门禁、issue 模板、DCO 形态。**
> **但有四件事开源的惯例满足不了：内容自证、归属防抵赖、独立时间戳、以及"贡献定价不能自己声明"。**
> **所以最终答案是 git 与链并存——git 管发布分发，链管数据自证，签名管人，tag 管时间。**
> **而最根本的区别是：这是账本，不是代码库。代码库里改历史无所谓，账本里改历史是事件。**
