## 一、credit：名字对了，锚错了

### 1.1 为什么"credit"比"币"好

"credit" 在你们语料里有现成的理论位置，而且是**双义**的：信用 = 可信度 + 债权。它天然是**关系性、可记账、可核销**的，而"币"是**被物化的等价物**。

更关键的是：**credit 是记在账上的债权，不是可流通的一般等价物。** 这个区别决定了后面所有的合规判断。

### 1.2 "锚定模型 token"的真实含义与风险

先问：**锚定谁的 token？** 如果锚定 OpenAI / Anthropic / DeepSeek 的价目表，等于**把货币发行权让给一家外国商业公司**。它调价一次，你们全员的贡献计量就集体漂移一次。

这正是你们语料里那条判断的翻版：

> 共济会它是一个一小撮、极小一撮金融资本寡头组织起来的，这是它的形式……它的形式、它的组织模式是背叛它的内容的。……真理是站在它的形式上，而不是站在它这个第一人称的内容的，它的第一人称信条。
> —— `ev:governance-law:0083:01`（row 83，`library/close-reading/processes/process-0083-capitalism-imperialism-global-capital.md`）

你嘴上说"我们不定价"，实际上**定价权在外部的寡头手里**——形式背叛内容。

### 1.3 我的建议：不锚价格，锚资源

**把 credit 定义为"对公摊资源的提取权"，而不是"某种外部商品的价格等价物"。**

Dota 基地类比本来就是这个意思：基地里有补给，你在基地里能补血买装备。所以：

| 方案 | 定义 | 优点 | 缺点 |
|---|---|---|---|
| A. 锚模型 token 价 | 1 credit = 某厂商 X 个 token 的市价 | 直观 | 定价权外包、单一厂商风险、法律上更像"以货币计价" |
| **B. 锚资源量（推荐）** | 1 credit = 1 单位公摊资源提取权（折算为"标准算力单位"，如 1k 中端模型 token / 1 核时） | 物质基础清楚、天然可审计、不依赖外部价目 | 需要每月公布换算率 |
| C. 自浮动 | 每月月底由已发生的真实支出反推 credit 的购买力 | 最诚实 | 记账最麻烦 |

**推荐 B，并在每月结账时公布当月换算**（"本月公摊池 = 3 台机器 + X 元 API 额度 = 共 N 标准算力单位"）。这样 credit 的介质是**算力与带宽**，不是钱。

### 1.4 关键约束（比选哪个方案更重要）

> **credit 只兑换资源，不兑换治理权。**

这条是整份设计里最重要的一句。一旦 credit 能买投票权，元老院立刻退化成**金权寡头制**，你后面想做的一切"去中心化"都免谈。

- credit → 可以用算力、可以用存储、可以用 API 额度、可以抵扣分摊
- credit -/→ 不能投票、不能指挥人、不能换人民币、不能转给外部人

**credit 是消费权 / 债权，不是股权、不是政治权。**

### 1.5 "用加密原理"应该用到什么程度

要的是**防篡改和可核验**，不是**可交易**。所以：

- ✅ 账本**只追加**（append-only），每条记录签名（ed25519 / minisign 皆可）
- ✅ 每周把账本叶子算一次哈希，做条链（每条记录含上一条的哈希）——**哈希链，不是区块链**
- ✅ 每月把 Merkle root 钉在一个双方都能看到的公开位置（不需要上公链）
- ✅ 关键记录（准入、清退、credit 调整）要求 **2 人签名**才生效
- ❌ 不做代币发行、不做交易、不做链上合约、不做兑换

**合规边界（这条别绕）：** 在大陆，"自己记账"和"发行代币"的界线不在技术，在**实质**——是否发行、是否可转让、是否可兑换、是否有交易场所。94 公告 / 924 通知管的是这些实质。哈希链 + 不自称币 + 不转让不兑换，你们现在这个规模完全不碰线；一旦某个环节变成"可以买、可以卖、可以兑"，无论叫什么名字都一目了然。

## 二、元老院：可以留，但必须拆 + 日落

### 2.1 你们的语料对"制度化"给了一条很重的判断

"现实的本体论化"这一讲里，讲者反复说：把乌托邦**制度化、科层化的努力注定失败**，一定会**形式主义化、教条化**：

> 而且理论家自己是知道的这种本体论化，或者这种叫做把乌托邦现实化的这种努力是注定 dome to fail，注定失败（L384–386）
> 所以目的论这个四会显现出一种形式主义化，或者叫教条化，它一定会形式主义化，一定会教条化（L388–389）
> —— row 288，`corpus/raw-markdown/4_实践/4-1_复习/4-1-2_灌输/4-1-2-4_现实的本体论化/0288_4-1-2-4_现实的本体论化_p7468.md`（"一个创始元老，什么之父被干掉了"见 L384）

同一 row 稍前处（L370–374）还有一层更贴切的：理论家要不停建构、只能毛估、靠灵感和数据、大部分情况下是**历史逼着你这样做**；紧接着给的具体样态就是"**就是他负责做饭、他负责去开车、他负责去打扫卫生**"——也就是说，**连分工本身都已经是本体论化**。你们一确定"谁管服务器、谁管账"，这个过程就已经开始了，不必等到写章程。

这条判断不是叫你别做制度，而是说：**制度一定会从手段变成目的，从载体变成主体。** 对策不是"不写制度"，而是**在制度里埋自动失效机制**。

同一份语料还指出：**组织容易被误当成实践本身**——

> Diagnostic sequence … **Fantasy / misrecognition** — rule is mistaken for justice; legality for legitimacy; procedure for truth; security for liberation; **organization for practice by itself**.
> —— `library/themes/governance-law-bureaucracy/governance-law-bureaucracy-synthesis.md`

对你们的风险很具体：**"我们搭了平台、建了元老院"很容易被当成"我们做了事情"。** 平台不是事情，平台是打钱的地方。

而且语料明确说，**即使是要走替代性道路的形态，也必须设立制度性规则**：

> 这个 4224 和这个 4124 这 2 个对于真正的我们眼中的 D 的实现的方法，以一种 soviet 这种方式来实现的时候，也是要设立下来制度性规则的，多少天开一次什么，多少天怎么怎么样的。
> —— `ev:governance-law:0310:02`（row 310）

所以"去中心化所以不需要成文规则"是错的。**去中心化恰恰需要更明确的成文规则，因为它没有科层权威兜底。**

### 2.2 结构建议：两院制

雁雁自己说"不太喜欢元老审核这一套"。**这个不适感是对的，但要保留的是"少数人管准入"这个功能，不是它的随意性。** 拆成两院：

| | **元老院（议院 / 创始院）** | **全员大会（全体会）** |
|---|---|---|
| 构成 | 创始成员 + 后续按贡献与背书产生的席位 | 全体正式成员 |
| 管什么 | **准入、清退、章程修改、争议终审** | **一切对外内容、公摊额度、公开立场** |
| 不管什么 | 日常运营、具体项目怎么做 | 个别人的去留 |
| 决议要求 | 简单多数；**清退需 2/3** | 简单多数 |

理由：**准入/清退这种"对人的判断"需要小、需要慢、需要承担声誉责任**（三个人坐在一个屋里不容易随便点头）；**对外立场这种事"需要大"，因为一个人的对外发声会代表所有人**。两类事混在一个机构里，就会出现"三个人决定了对外说什么"或者"三十个人投票决定开除谁"这种明显错配。

### 2.3 日落条款（Serious 建议）

**元老院席位设 12 个月日落。** 到期自动全部失效，必须**重新表决续期**，续期时同时重新议定标准。

收益有三：
1. 强制复盘，避免 288 讲的"形式主义化、教条化"
2. 给后来者一个明确的"这个结构不是永恒的"信号，降低进入时的心理成本
3. 让"元老"这个头衔**从身份变成职责**——身份会腐化，职责会被审查

### 2.4 名称问题

"元老院"这个名字的语料色彩是**贵族共和 / 寡头**（`corpus/bilibili-asr/BV1kG411n7Yi__68106ef006.txt` 里对元老院式政治想象的评价是"很糟糕的棋手势……肮脏的、反动的"）。

这不是说不能叫，而是说：**如果对外叫"去中心化社区"，对内结构是元老院，那又是形式背叛内容。** 二选一：
- 要么改个中性名字（创始院 / 议院 / 管理组）
- 要么就叫元老院，并且**对外明说我们是邀请制的、由创始成员把关的**

我倾向第二个：**诚实比体面重要，而且诚实的人反而更容易招到对味的人。**

### 2.5 准入机制的改进（针对"不喜欢元老审核"）

保留 2 元老提名制，但加三条，把"审核"变成"程序"：

1. **提案公示期 7 天**：提名人写出"为什么拉他、他能提供什么、谁跟他共事过"，任何成员可提异议
2. **不要求全票**：2 人提名 + 元老院简单多数即可，避免熟人一票否决整个群体
3. **新人有 90 天观察期**：观察期内无资产权限、credit 记账但标注 `provisional`，期满转正需再次确认

这样"元老审核"就有了**留痕、有异议渠道、有时限**，而不是三个人的私下判断。

## 三、归属：暂与元老相关 → 必须配托管契约

"归属暂与元老有关"我理解是务实的（没有法律主体，只能用自然人身份注册）。但**"暂"必须有约束，否则它会变成"永久"**。

### 3.1 立刻要做的（不需要法律主体）

| 项 | 做法 |
|---|---|
| 域名 / VPS / 代码仓库 / 机器人账号 | **统一用组织邮箱注册**，不用任何人的私人邮箱 |
| 凭据保管 | 进一个共享密码库；**恢复码/2FA 备份由 3 人各持一份**（如 3-of-5 Shamir 分片） |
| 书面托管声明 | 一页纸：写明这些账号"系团队共有资产，登记人仅在任期内代持，无权处置、转让、抵押" |
| 交接演练 | **上线后做一次真实交接演练**（临时把 root 交给另一人，走完流程再交回）——没演练过的交接流程等于没有 |
| 退出处理 | 任何人退出，48 小时内完成凭据轮换；登记人退出时强制移交，不移交视为违约 |

> 顺带提醒：共享密码库本身是单点。它的主密码别只存在一个人脑子里，写下来分片存放。

### 3.2 什么时候该立主体

出现下面任一条，就该考虑注册实体（境外 LLP / 基金会，或境内个体户/公司，视用途）：
- 有对外收款或对外付款
- credit 出现**对外**的负债（即有人可以从外部兑换）
- 需要签合同、需要持有商标、需要承担侵权责任
- 成员数量超过 ~10 人，自然人代持已经无法覆盖

**在立主体之前，一切"归属"都只是君子协定。** 所以托管声明要写得像那么回事：写明日期、写明资产清单、三方签字——它法律效力有限，但**在人心里的效力很大**，而这正是现阶段最需要的。

### 3.3 一个反面提醒

**不要让全部资产挂在一个人名下。** 你们语料里那个 288 讲的句子——"一个创始元老，什么之父被干掉了，那没办法的"——讲的是历史必然性，不是操作手册。操作上，一个人的意外就能让整个基建归零，这是纯粹的风险管理问题，跟理念无关。

## 四、可直接照搬：ismism 仓库自己的策展流程

`~/文档/ismism-system` 这套流程已经在稳定运行，它本身就是一套**"多人协作 + 准入 + 留痕 + 可申诉"的治理实现**，而它的设计恰好避开了"元老随意拍板"的问题。

| ismism 的做法 | 对应的团队治理制度 |
|---|---|
| `reviews/` 下每个主题都有 **candidates** 和 **decisions** 两类文件 | 准入、清退、credit 调整都写成 **提案 + 决定**，两段留档 |
| **决定不删除**，修订走 amend | credit 记错了**不删记录**，写一条冲正条目，保留原记录 |
| validator 校验（`tools/ismism.py validate all`） | 每月跑一次账本一致性检查：credit 总和 = 公摊池总量，逐条对得上 |
| 证据精度显式标注 `V/non-exact`、不伪装成逐字 | credit 记录的置信度也分档：`exact`（有凭据）/ `estimated`（毛估），**不许把毛估写成精确** |
| 每个主题有 `known gaps` 字段 | 每个成员 / 每个项目有公开的"已知缺口"，不用猜 |
| **`不得由 route 或 segment 相交自动推出……行动处方`** | **不得由"某人贡献多"自动推出"他说了算"**——credit 与决策权严格分离 |
| `analysis-only` / `admit` / `reject` 三态 | 成员三态：`provisional` / `active` / `suspended`，都有明确进出条件 |

**其中最有价值的一条是这个思路：** 仓库里"决定"从来不是一个人的意志，而是**一条可追溯的、带 review 引用的记录**（"review: reviews/shuzhengxue-agent-text-review-20260815.md"）。你们的清退机制照抄这个形式，就能避免"元老说他不行"这种无法申诉的状态。

## 五、修订后的 MVP 顺序

```
第 0 步  一页纸章程（含：分摊上限、账号归属与托管声明、准入与清退、
                    两院职权、credit 定义与换算规则、日落条款）
第 1 步  基建（境外 VPS + 域名 + GitHub 组织 + 共享密码库），¥50～150/月
第 2 步  按 ismism 的形式建两个账本：
           members.jsonl   —— 成员状态与提案/决定历史（append-only）
           ledger.jsonl    —— credit 收支（append-only、哈希链、2 人签名）
         —— 先空跑 4 周，只记账不做任何分配
第 3 步  验证需求：4 周内智库提问数、有效回复数、招募板成单数
           提问 < 5 或有效回复 < 10 → 保持现状，不投基建钱
第 4 步  结账：第 1 次真实结算，公布当月 credit 换算率，并做一次交接演练
第 5 步  12 个月后：元老院日落，重新表决续期 + 重订标准
```

**第 2 步是关键改动**：不先搭平台，先搭**账本**。平台的界面会骗人，账本不会。而且账本用纯文本 JSONL 就能开工，零成本，跑不通就说明这事本身跑不通。

## 八、一页纸章程骨架（可直接填写）

```markdown
# <团队名> 章程 v1
生效日期：____    下次强制复审：____（不超过 12 个月）

## 1 定位
公摊成本建基建，基建成果共享。不做中心化管理。
打钱、逛街、参团各自决定；有收益的项目另行立项组织。

## 2 成员状态
- provisional：入伙后 90 天内。无资产权限，credit 记为 provisional
- active：转正。有资源提取权
- suspended：被暂停。保留申诉权
- 退出：随时可退，48 小时内凭据轮换

## 3 准入
2 名 active 成员提名 → 提案公示 7 天（成员可提异议）→
元老院简单多数通过 → 90 天观察期 → 转正确认

## 4 清退
提案人须写明事由与证据 → 被清退人有权书面申辩 →
元老院 2/3 通过 → 执行；被清退人可向全员大会上诉一次

## 5 义务
不捣乱、按时分摊、该出力时出力。分摊上限：____ 元/月/人

## 6 两院
元老院：准入、清退、章程修改、争议终审。席位 12 个月日落，到期重议。
全员大会：对外内容、公摊额度、公开立场。全体 active 成员一人一票。

## 7 credit
定义：对公摊资源的提取权。1 credit = 1 标准算力单位。
获得：按已确认的贡献记账（基建/开发/文档/答疑/资金五类）。
使用：提取算力、存储、API 额度；可抵扣分摊。
禁止：不转让、不兑换、不流通、不授予投票权。
记账：ledger.jsonl，append-only，哈希链，关键条目 2 人签名。
精度：exact（有凭据）/ estimated（毛估），不得把毛估写成精确。

## 8 归属
资产清单：____
登记人：____（仅代持，无处置权）
凭据保管：共享密码库 + 恢复码 3 人分片
交接：登记人退出时强制移交；每 12 个月做一次交接演练

## 9 日落
本宪法第 6、7 条于 ____ 自动失效，须重新表决。
```

## 九、可以直接发群里的话

> credit 这个改名我认，而且比我上次说的"台账"更准确——credit 本来就是"信用 + 债权"双义，是关系性的、记在账上的，不是被物化的等价物。名字对了。
>
> 但"锚定模型 token"这个锚要改一下。锚谁的 token？锚 OpenAI 或 DeepSeek 的价目表，等于把定价权交给一家外国公司，它调一次价我们全员的贡献计量集体漂移一次。这不就是共济会那个问题——嘴上说我们自己定价，形式上定价权在别人手里。
>
> 我建议不锚价格，锚资源：**1 credit = 1 标准算力单位**（比如 1k 中端模型 token / 1 核时），每月结账时公布当月换算。这样 credit 的介质是算力和带宽，不是钱，物质基础清楚，也不用求人。
>
> 还有一条比选哪个方案更重要：**credit 只兑换资源，不兑换治理权。** 一旦 credit 能买投票权，元老院立刻变金权寡头，后面所有去中心化都免谈。credit 是消费权、债权，不是股权、不是政治权。
>
> 元老院我觉得可以留，但拆成两院：元老院管准入、清退、章程、争议；全员大会管对外内容、公摊额度、公开立场。理由很实在——判断"某个人行不行"需要小、需要慢、需要有人担声誉；判断"我们对外说什么"需要大，因为一个人说话代表所有人。这两类事混一起，就会出现"三个人决定对外说什么"或者"三十个人投票开除谁"。
>
> 另外加个日落：**元老席位 12 个月自动失效，到时候重新表决续期**。不是不信任谁，是让"元老"从身份变成职责。你们那个语料里讲得很直接——把乌托邦制度化、科层化的努力注定失败，一定会形式主义化、教条化；对策不是不写制度，是在制度里埋自动失效。
>
> 准入那块，我加三条把"元老审核"变成"程序"：提案公示 7 天（任何人可提异议）、不要求全票（2 人提名 + 简单多数）、新人 90 天观察期。这样它有留痕、有异议渠道、有时限，而不是几个人的私下判断。
>
> 归属"暂与元老相关"我理解，但"暂"得有约束。现在就要做的：域名、VPS、仓库、机器人**全部用组织邮箱注册**，凭据进共享密码库，恢复码 3 人分片；写一页纸托管声明（登记人只代持、无处置权）；上线后**做一次真实交接演练**——没演练过的交接流程等于没有。
>
> "用加密原理"我建议用到哈希链为止：账本 append-only、每条签名、每周算一次链式哈希、每月把 Merkle root 钉在一个公开位置、关键条目 2 人签名。**不要做代币发行、不要可转让、不要可兑换。** 大陆那条线不在技术，在实质——是否发行、是否可转让、是否可兑换。哈希链 + 不自称币 + 不转让不兑换，我们现在这个规模完全不碰线。
>
> 落地顺序我建议改一下：**先搭账本，再搭平台。** 两个纯文本账本就够开工——`members.jsonl`（成员状态与提案/决定历史）和 `ledger.jsonl`（credit 收支），空跑 4 周只记账不分配。平台的界面会骗人，账本不会。而且这套形式你们 ismism 仓库已经在跑了：candidates → decisions 两段留档、决定不删除只 amend、关键条目带 review 引用。清退机制照这个形式写，就能避免"元老说他不行"这种没法申诉的状态。

## 十、可选：把治理流程直接跑在 ismism 的形式上

仓库里已有的工具与约定可以直接拿来建档，**零开发成本**：

- **成员与提案留痕**：仿 `reviews/` 的 candidates / decisions 两段式，建 `governance/reviews/`
- **一致性校验**：仿 `python3 tools/ismism.py validate all`，写一个 30 行的脚本每月跑一次
  - `sum(credit 收入) == sum(credit 支出) + 当前余额`
  - 每条记录有签名、有前一条哈希
  - 每个成员状态变更都有对应 decision 记录
  - 没有 `estimated` 记录被标成 `exact`
- **精度分层**照抄 `exact` / `non-exact` 的做法，落到 credit 上就是 `exact`（有凭据）/ `estimated`（毛估），并且**月度报告里两者必须分列**，不许合并成一个数
- **停止条件**照抄默认协议：每个有争议的决定必须写明"什么情况下这个决定会被推翻"

> 这一步的价值不在技术，在于**把"我们说好了"变成"账上是这么记的"**。前者靠记性，后者靠文件。

## 十一、我现在的判断（一句话版）

**credit 的名、元老院的实、归属的暂——三个都成立，但每个都缺一个约束条件：credit 缺"不换治理权"，元老院缺"日落"，归属缺"托管契约"。把这三个约束写上，这套设计就是自洽的；不写，它会在 12 个月内退化成三个人的私人俱乐部，而且没人会觉得哪里不对。**
