## 第一部分：整体设计（一页讲完）

### 1.1 它是什么

**一个带规则的公开 git 仓库 + 四份 JSONL + 一个校验器。**

三个功能：

| 功能 | 承载 |
|---|---|
| **公告板**：谁需要什么、谁想做什么 | `requests.jsonl` + issue 模板 |
| **账本**：谁做了、值多少 | `deliverables.jsonl` + `credits.jsonl` |
| **身份**：谁是谁 | `keyring.jsonl`（公钥目录，不是成员名单） |

### 1.2 四份文件

```
data/requests.jsonl       公告板
data/deliverables.jsonl   交付物与复核
data/credits.jsonl        账本
data/keyring.jsonl        公钥目录
```

每行的通用字段：

```jsonc
{
  "seq":  42,                  // 本文件内递增，不跳号
  "at":   "2026-09-16T14:03+08:00",
  "by":   "ed25519:ab12...",   // ★ 身份是公钥，不是账号
  "prev": "sha256:...",        // 本文件上一条的 hash；首条为 null
  "sig":  "ed25519:...",       // 对 hash 的签名
  "hash": "sha256:..."         // = sha256(canonical_json(本条去掉 hash 和 sig))
}
```

### 1.3 四层防护，各管一件事

| 层 | 管什么 | 谁提供 |
|---|---|---|
| **git commit 链（SHA-256 仓库）** | 发布、分发、顺序 | git |
| **文件内哈希链（`prev`）** | **数据脱离 git 也能自证** | 我们 |
| **Ed25519 签名** | 是谁写的、防抵赖 | 我们 |
| **签名 tag + 免费 TSA** | 独立时间锚点 | git + 外部 |

**★ 这四层不重复。** git 的分发能力和链的自证能力是两件事——因为你们的数据一定会被单独引用、复制、传播，**行本身能连成链，它被搬到哪儿都还成立。**

### 1.4 一次协作的完整流程

```
① 开 issue（= 开单）        issue 模板强制填：缺什么 / 怎么算做完了
② 提 PR（= 交东西）          改 data/deliverables.jsonl，末尾追加一行
③ CI 跑 validate            policies.jsonl 里十条规则，任一 error 即失败
④ 复核                      ★ 复核者 ≠ 交付者（p-003，机器校验）
⑤ CODEOWNERS 合并           ★ 合并 = 入库 + 上账，一次完成
⑥ build-index 重生成 README 第一屏
⑦ 周期末尾：签名 tag + 打 TSA
```

### 1.5 治理：抄 Linux 的形态

```
MAINTAINERS.md   谁管哪个板块（声明式，一份文本）
CODEOWNERS       把板块映射到"谁的批准算数"（GitHub/Gitea 原生机制）
```

**关键约束（来自前面定的"能推快不能拖慢"）：**

| 维护者可以单方面做 | 必须第二人 |
|---|---|
| 确认交付物、推进状态、回应异议 | **关单 · 推翻已通过的复核 · 改 credit 认定** |

**CODEOWNERS 在这里的作用很直接**：把 `data/credits.jsonl` 和 `policies.jsonl` 设成需要**两个 owner 批准**，约束就从"写在文档里"变成"平台强制"。

### 1.6 校验器：唯一发号施令的地方

| 规则 | 内容 | 级别 |
|---|---|---|
| p-001 | 每条记录的 `hash` 与 `prev` 链接得上 | **error** |
| p-002 | 每条记录签名有效，且公钥在 `keyring` 里 | **error** |
| p-003 | **复核者 ≠ 交付者** | **error** |
| p-004 | `acceptance` 为空或不可判定的 `open` 直接拒绝 | **error** |
| p-005 | `credits` 的 `adjust` 必须有第二人签名 | **error** |
| p-006 | 越权操作（单人做了需两人的动作） | **error** |
| p-007 | 异议 7 天未回应 | warn |
| p-008 | 单一来源 credit 占比超阈值 | warn |
| p-009 | `challenge` 类的 `links` 不能为空 | **error** |
| p-010 | 周期未公示维护者变更 | warn |
| **p-011** | **任何"拉人进来"的行为不得产生 credit** | **error** |

**★ 硬纪律：不得为了让校验通过而削弱校验（只能改事实，不能改检查）。**

### 1.7 credit 的算法

```
定基     = reproduce_minutes / 10        复核者估，不由交付者报
问题     = 它引发的产物 credit × 20%      上限待定
效果加成 = × (1 + min(reuse, 5) × 0.2)   复用是唯一不可伪造的加成项
门槛     = 复核通过（复核者≠交付者） + 需求方确认
衰减     = 活跃度衰减，半衰期待定
```

### 1.8 分阶段的现实地位

| 阶段 | credit 是什么 | 触发条件 |
|---|---|---|
| 现在 | **记分牌** | — |
| 池子开始分摊成本 | **分摊的分配键** | 开始付服务器钱 |
| 对外交付 | 劳动分配依据 | 有法律主体 |

**现在它什么都换不到，所以不要为它设计太多。**

## 第二部分：体检报告

### 2.1 真实矛盾（五处，都要修）

#### M1 ★★ 周期结算是循环引用 —— 我的设计错误

**症状：**

- `架构-v1` 说"周期结算时生成 `cycles.jsonl`，里面记 `member_chain_heads` 和 `merkle_root`"
- `仓库形式-完全公开` 说"删掉 `cycles.jsonl`，改用签名 tag"
- **但签名 tag 本身就是一个提交**——它会被追加进账本 → **改变了链尾 → tag 里记的哈希立刻失效**

**这是一个自我引用的死循环。** 我把两个方案拼在一起时没注意。

**修法（tag 记的是"上一状态"）：**

```bash
# 1. 先把本周期所有记录提交并推送
git commit -m "cycle 2026-Q4 records"
git push

# 2. 再打一个 tag，记录【当前链尾】，且这个 tag 本身不产生新记录
git tag -s cycle-2026-Q4 \
  -m "四份文件的链尾: requests=sha256:..., deliverables=..., credits=..., keyring=..."
git push --tags
```

**关键区分：tag 不是账本记录，它不改变 `data/`。** 所以它不会使自己的内容失效。

**同时明确一件事：tag 里的数字是"从日志推导出来的，不是独立存储的"。** 不要在 `data/` 里再存一份——那就是两份真相。

**并且由此确定：周期的边界 = 两个 tag 之间。** `cycles.jsonl` 确实删掉，**衰减按 tag 区间算**。

#### M2 `at` 字段语义不明（写入时间 vs 业务时间）

**症状：** 如果有人补录一条三天前发生的事，`at` 该写哪天？

**修法：两个字段，语义分开**

| 字段 | 含义 |
|---|---|
| `at` | **实际写入时间**（不可改，参与排序） |
| `effective` | **业务发生时间**（可选，缺省 = `at`；补录时才不同） |

**为什么必须分：** 不然"补录"就成了"伪造时间"的合法通道。

#### M3 `maintainer-log.jsonl` 是多余的

**症状：** `MAINTAINERS.md` + CODEOWNERS + git log 已经覆盖了它的功能。

**修法：删掉这份文件。** 维护者的操作本身就是 `data/` 或 `MAINTAINERS.md` 的提交——**提交信息里必须写理由**，而提交作者是签过名的。

**省下一份文件，而且约束不变。**

#### M4 `p-008`（40% 上限）对三人团队是错的

**症状：** 3 个人，一个人产出 60% 是**正常且应该被鼓励的**。40% 上限会惩罚最积极的人。

**修法：规则要随规模变。**

| 活跃成员数 | 单一来源上限 |
|---|---|
| 2～3 | **不设上限**（只记录，不执行） |
| 4～6 | 60% |
| ≥7 | 40% |

**★ 而且更该防的不是"某个人占比高"，是"某个人占比高且不产出"。** 后者已经由衰减机制处理了。**所以这条规则在三人阶段完全不必要。**

#### M5 CODEOWNERS 把身份绑回了平台

**症状：** 前面定了"公钥即身份，平台只是入口"。但 `CODEOWNERS` 里写的是 **GitHub 用户名**。

**这是真实冲突**——换平台（GitHub → Gitee → 自建）时，CODEOWNERS 需要重写。

**修法：明确分工，不要混淆权威性。**

| 文件 | 权威性 | 平台绑定 |
|---|---|---|
| **`keyring.jsonl`** | ★ **权威**：谁是谁 | 无 |
| **`MAINTAINERS.md`** | ★ **权威**：谁管哪个板块 | 无 |
| `CODEOWNERS` | ⚠️ **仅为审批路由的便捷机制** | 绑定平台 |

**写成一句规则：`CODEOWNERS` 是从 `MAINTAINERS.md` 生成的，换平台时重新生成即可，它不是身份来源。**

### 2.2 语义不清（四处）

| # | 问题 | 修法 |
|---|---|---|
| **M6** | `hash` 在 `canonical_json` 里被去掉——但"去掉两个字段再算"没说清要不要重排键 | **写死**：去掉后按键名字典序排列、无空格、UTF-8、不转义非 ASCII |
| **M7** | 状态推导规则和 `status_hint` 字段可能不一致 | **`status_hint` 改名 `status_declared`，且只作参考**。真实状态永远从事件推导，**两者不一致时以推导为准**（并且这本身就是一条 warn 规则） |
| **M8** | 校验器的权限边界没定：非维护者的 PR 必须过 validate；那维护者自己的提交呢？ | **维护者也要过。** 唯一例外是 `policies.jsonl` 和 `tools/validate` 的修改——**这两个文件的改动必须由两个 owner 批准**（否则就是"自己放宽检查"） |
| **M9** | 谁监督验证器本身 | **验证器是唯一发号施令的地方，所以它的改动是最敏感的操作。** 见 M8 的例外条款 |

### 2.3 没覆盖的（三处）

| # | 缺口 | 修法 |
|---|---|---|
| **M10** | 第一个提交怎么来（引导问题） | **第一次提交由雁的密钥签名，内容 = `keyring.jsonl`（只含雁）+ `MAINTAINERS.md` + `policies.jsonl` v1。** 这就是 genesis，**README 里写明"这是第 0 号提交，之后所有记录都链在它后面"** |
| **M11** | ★ **最后一个维护者离开了怎么办** | 写进 `MAINTAINERS.md`：① 仓库和记录**不因此失效**——任何人 clone 都能验；② 任何持钥者仍可提 PR，但**无人能合并**；③ 规则：**只有原维护者能添加新维护者**，所以维护者消失 = 该板块冻结（不是腐烂） |
| **M12** | 复核者能合并自己的复核 —— 复核与合并两个角色在三人团队里必然重合 | **承认它**。三人团队里无法分离"复核"和"合并"。**这是这套设计真实的信任边界**，见下 |

### 2.4 ★ 根本的信任假设（必须明说）

**校验器能证明的：**

- 签名有效、公钥在 keyring 里
- 链接得上（没被插入、没被删改）
- `acceptance` 非空
- 复核者 ≠ 交付者
- 需两人签名的操作确实有两人签名

**校验器不能证明的：**

- ❌ **复核者真的读了那份交付物**
- ❌ `reproduce_minutes` 估得公道
- ❌ 需求方真的确认过（而不是随手点通过）

**★ 也就是说：整套系统能防"伪造记录"，防不了"敷衍了事"。**

**在 3～5 人、互相认识的阶段，这个边界可以接受。** 但**它必须被写进文档**，不能假装系统能自动保证质量。

**而这个缺口正好由机器人补上一半**——"通过了但没人用"就是"敷衍了事"的**事后可见信号**。**它不阻止敷衍，但它让敷衍留下痕迹。**

### 2.5 内部一致性检查（通过的）

| 检查项 | 结果 |
|---|---|
| 数据模型 ↔ 政策（十条规则能不能都落在字段上） | ✅ |
| 政策 ↔ 治理（能推快不能拖慢） | ✅ CODEOWNERS 双人批准可强制 |
| credit 算法 ↔ schema（`reproduce_minutes` 记在哪） | ✅ 在 `deliverables.content` 里，随交付物签名 |
| credit 是推导的 ↔ 记账（不会有两份真相） | ✅ |
| 公开 ↔ 无版权顾虑（分层已取消） | ✅ |
| 本地优先 ↔ git 托管（不冲突） | ✅ git 就是本地仓库加远端 |

## 第四部分：一句话体检结论

> **骨架是通的：四份文件、四层防护、抄 Linux 的治理形态，各层职责不重复。**
> **但有三处必须修：M1（周期结算是循环引用，我写错了）、M3（`maintainer-log` 多余）、M4（40% 上限对三人团队是错的）。**
> **还有一处必须承认：校验器能防"伪造记录"，防不了"敷衍了事"。这个缺口靠"通过了但没人用"这个事后信号补一半——它不阻止敷衍，但让敷衍留下痕迹。**
> **★ 一个之前没说透的设计优点：因为数据是公开的，"信任"可以完全交给 git 的默认机制。任何人 clone 之后只需跑一次校验器——能跑通，整套东西就是可信的。**
