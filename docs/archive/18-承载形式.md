# 承载形式：服务器 / 域名 / App

> 承接本轮：仓库用私有仓库起步，后续租服务器和域名，后续可以加 App。
> 本文只谈**承载**（东西放在哪、怎么被访问），不谈制度和字段——那些已经定了。
> 核心主张：**先把 schema 定死，承载是可替换的。任何让 schema 绑死在某套工具上的选择都要避免。**

---

## 一、先把三样东西的作用分开（别当成一件事）

| 要买的东西 | 真实作用 | 什么时候才真的需要 |
|---|---|---|
| **私有仓库** | **记录与流程**：申请单、交付物、复核、账本 | **现在就需要，而且现在就能用** |
| **服务器** | **访问控制与常驻**：谁能看、能不能自动化、能不能跑代码 | 有 ① 访问控制需求 ② 自动化需求时 |
| **域名** | **入口与身份**：一个稳定的地址 | 服务器上线时一起 |

**服务器不是"仓库的升级版"，它解决的是另外两个问题：访问控制、常驻自动化。**

如果只是"把东西放上去大家一起看"，私有仓库已经做完了，而且做得更好——因为它的 issue / PR / review 流程**天然就是申请单和复核流程**。

---

## 二、★ 第一个必须由你定的：服务器放哪

只要有一个 DNS 可解析、能被访问的站点，**大陆服务器就需要 ICP 备案**——哪怕只给成员看。这一条和"内部使用"无关，**和"有没有域名、是不是公网可访问"有关**。

| 选项 | 备案 | 成本 | 缺点 |
|---|---|---|---|
| **A. 境外 VPS（推荐）** | 不需要 | ¥30～80/月 | 访问速度；国内部分网络不稳 |
| **B. 境内 + 备案** | 需要 | 时间 1～3 周，需主体材料 | **现在没有主体**，会卡住 |
| **C. 不租，先用私有仓库** | 不需要 | 0 | 没有访问控制、没有自动化 |

**我的建议：先 C，需要时再 A；不要碰 B。**

理由：B 需要主体（个人备案也要实名+托管商审核+网站内容合规），而且**一旦备案就等于向监管声明"这是一个对外站点"**，性质和你现在要的"内部使用"不一致。**A 用境外 VPS + 成员制访问（账号密码 / IP 白名单 / WireGuard）能达到同样的"只给成员看"，且不产生备案义务。**

---

## 三、★ 第二个必须定的：域名和服务器要分离

这是操作纪律，但**一旦弄混以后很难拆**：

| 项 | 规则 |
|---|---|
| **注册商** | 选一个能随时转出的（Cloudflare / Namecheap / Porkbun / 阿里云都行） |
| **DNS** | **放 Cloudflare**（免费、可随时改指向、不绑服务器商） |
| **服务器** | 独立于域名商挑。**不要用"域名商送的服务器"或"服务器商送的域名"** |
| **账号** | 全部用**组织邮箱**注册，不用私人邮箱（这条 v2 就定了，现在要执行） |

**理由很实际：换服务器商是常事，换域名商是灾难。** 两者绑在一起，将来搬家要同时动两件事。

---

## 四、关于 App：建议先别用"App"这个词

**"加 App"之前必须先回答：哪个功能在手机上做不到？**

| 你可能想要的 | 真实需求 | 最省的解法 |
|---|---|---|
| 手机上提单、看单 | 移动端能用的界面 | **响应式网页（PWA 即可）**，不需要原生 |
| 收到通知 | 推送 | 邮件 / 群机器人，不需要 App |
| 离线看资料 | 离线 | 不必要，资料在服务器上 |
| 独立身份感 | 品牌 | 最贵也最没用的一项 |

**原生 App 的真实代价不是开发，是持续维护**：上架、签名、系统升级适配、双端各一份。**三五个人维护不了一个 App。**

**建议：网页 / PWA 优先，App 只在"网页确实做不到"时才做。** 而且顺序必须是：**服务器 + 网页 → 用满一个周期 → 再看要不要 App。**

---

## 五、架构上的一条硬边界（这条比选哪家云重要得多）

一旦服务器上线，**必须有明确的三层分离**：

```
① 数据层（唯一真相）
   requests.jsonl / deliverables.jsonl / ledger.jsonl / members.jsonl / maintainer-log.jsonl
   —— append-only，哈希链，只有它能改状态
        ↑ 只能通过签名的写入接口
② 应用层（读写逻辑）
   成员认证、提单、认领、复核、账本追加
   —— 不保存任何私有状态，随时可以重建
        ↑ 提供受控接口
③ 代理层（agent / 模型）
   整理、撮合建议、初筛、生成草稿
   —— ★ 只能产出「提案」，不能直接落账
```

**★ 第 ③ 层的规则是这套架构的关键：agent 产出的任何东西都是提案，落账必须由人签名。**

原因不是保守，是**因为账本是唯一的真相来源，而 agent 的输出是不可复现的**（同一个提示词两次结果不同）。**一个不可复现的写入者，不能是真相来源的写入者。** 这直接对应前面定的"credit 最终确认权必须在人手里"。

**顺带一条运维纪律**：账本每天自动备份到**另一个供应商**（不是同一家的对象存储）。**账本是唯一不可重建的东西**，代码和界面都能重写。

---

## 六、可替换性清单（防止被任何一家绑死）

| 层 | 现在选 | 将来能换吗 | 怎么保证能换 |
|---|---|---|---|
| 记录格式 | **JSONL + 本文档的 schema** | ✅ | **schema 是唯一不能变的东西**，工具围着它转 |
| 承载 | 私有仓库 → 服务器 | ✅ | 都能承载同一套 JSONL |
| 数据库 | **先不上数据库** | ✅ | JSONL 用 git 管就够；上数据库反而丢版本历史 |
| 认证 | 私有仓库成员 / 服务器账号 | ✅ | 成员表在 `members.jsonl`，不在某个平台的用户体系里 |
| 域名 / DNS | Cloudflare | ✅ | 独立于服务器商 |
| Agent | 任意模型 | ✅ | 账本只记模型 ID 与版本，不记厂商锁定 |

**一句话：唯一的不可替换件是 schema，其余全部可换。** 所以**现在的第一优先级是把六份 JSONL 的字段定死，不是挑服务器。**

---

## 七、修订后的落地顺序

```
第 0 步  ★ 定死六份 JSONL 的字段（零成本，唯一不可替换的东西）
第 1 步  建私有仓库，用 issue 模板承载申请单
          现在就能跑，不花钱、不备案、不需主体
第 2 步  ★ 走通一遍：提一条真申请单 → 自己接 → 第二个人复核
          判不了 = schema 有问题 → 回去改，不要往下走
第 3 步  拉第一个真人进来走一遍
第 4 步  跑满一个周期（90 天），看三个数：成案数 / 打回率 / 复用次数
第 5 步  ★ 只有出现下面任一条，才租服务器 + 域名：
          · 需要成员制的访问控制（不想让记录放在第三方平台上）
          · 需要常驻自动化（bot、定时校验、自动备份）
          · 私有仓库在国内访问不可靠
          · 资料量超出仓库舒适区
第 6 步  服务器：境外 VPS + Cloudflare + 组织邮箱 + 三层分离 + 异地备份
第 7 步  用满一个周期后，再看要不要 App（网页/PWA 优先）
```

**第 5 步那四条"才租服务器"的触发条件，是我建议你写进规范的东西。** 因为"租服务器"是一个**感觉在做实事、其实可能什么都没推进**的动作——它花的钱不多，但它会让人产生"基建搞好了"的满足感，而**池子里可能一条申请单都没有**。

**这正是你们语料里那条判词：`organization for practice by itself`（把组织本身误当实践）。**

---

## 八、这一轮还差你定的（三条）

1. **服务器放哪**：境外 VPS（推荐，不备案）还是境内+备案（现在没主体，会卡）
2. **是不是先用私有仓库起步**（我建议是），还是直接一步到位上服务器
3. **域名打算用什么**，以及**用哪个邮箱注册**（这条现在就要定，因为它决定所有账号的归属，而账号归属是 v2 里那个还没落地的"托管契约"的核心）

**第 3 条最容易被当成小事，但它是最该现在定的一条**——因为账号一旦用私人邮箱注册，将来迁移的成本会随时间上升。**现在改是零成本。**
