# 具体实现方案

> 你的设想大体可行，但分工要改一处：**Cloudflare 不托管 git，它是展示层。**
> 托管还得靠 GitHub / Gitea，Cloudflare 负责"网站 + 镜像下载"。

---

## 一、五件事，分别归谁

| 要做的事 | 归谁 | 说明 |
|---|---|---|
| **存 git 仓库、收 PR / issue** | **GitHub**（或自建 Gitea） | Cloudflare **做不了**这件事 |
| **跑校验（CI）** | **GitHub Actions** | 免费 |
| **展示网站 + 镜像下载** | **Cloudflare Pages**（+ R2） | 这就是你说的"CF 公开" |
| **在你本地自动更新** | `git fetch` 定时任务 | 见第四节 |
| **决定哪些要你 merge** | 验证器 + CODEOWNERS | 见第三节 |

**★ 关键澄清：Cloudflare Pages 只能"从 git 构建网站"，它不接受 `git push`。**

```
本地仓库 ──push──> GitHub（权威，收 PR/issue）
                      │
                      ├──> GitHub Actions 跑 validate
                      │
                      └──> Cloudflare Pages 监听 → 构建静态站 → 公开可访问
                                                          ↑
                                            别人在这里看 + 下载镜像 zip
```

## 二、★ 自建 Gitea 是必要选项（不是因为 GitHub 不好）

**国内访问 GitHub 不稳。** 你 09-16 说过"自己服务器自己用"，这就是用它的场景。

| 阶段 | 托管 | 网站 | 成本 |
|---|---|---|---|
| **阶段 0（今天）** | GitHub 私有/公开仓库 | **先不要网站** | 0 |
| **阶段 1** | GitHub + Gitee 双推 | Cloudflare Pages 建站 | 0 |
| **阶段 2** | **自建 Gitea**（境外 VPS） | 同一个 Gitea（它自带 web） | ¥30～80/月 |

**★ 而且现在有个新理由让"自建"比之前更有价值：** 因为你们要**公开**，所以"平台封号/删库"就是真实风险。**镜像越多越安全——这不是妥协，这就是目的。**

## 三、★ "自动更新" vs "需要 merge"：正确的分界线在哪里

你说"有的部分自动更新，有的需要 merge PR"。**这条线不能随便划，有一条清晰的判据。**

### 3.1 判据：有没有"人签名说过某句话"

| 内容 | 有人的签名吗 | 处理 |
|---|---|---|
| **所有记录**（requests / deliverables / credits / keyring） | ✅ **有** | **必须走 PR** |
| **`policies.jsonl`** | ✅ 有（改动要签名） | **必须走 PR + 两人批准** |
| **`tools/validate`、`tools/build-index`** | ❌ 没有 | **可以自动**（CI 校验通过即可） |
| **`INDEX.md`、`site/`、`digest/`** | ❌ 没有，纯推导 | **可以自动** |

**★ 一句话：凡是有人的签名在上面的，都不能自动写；凡是纯粹从别人签名推导出来的，都可以自动。**

**理由很直接：** 如果 CI 能自动写 `credits.jsonl`，那 credit 就不是"某人的认可记录"了，**它变成了一段代码的输出**——而代码不可复现、不可抵赖不成立。

### 3.2 所以三档

| 档 | 内容 | 谁批 |
|---|---|---|
| **自动** | `site/`、`INDEX.md`、`digest/` | 不用人，CI 过就合并 |
| **本人自批** | **开一张 `requests` 单**（= 我说我需要什么，这就是我的声明） | 开单人自己合，**但验证器要过** |
| **他人复核** | `deliverables`（交付物）、`credits`（入账） | **必须第二人批准**（CODEOWNERS 强制） |

**★ 中间那档是我加的一个优化：** "我要什么"这件事**不需要任何人批准**——它就是一句声明。**让开单人自己合，可以把摩擦降到零，而且不损害可信度**（签名已经说明是谁声明的）。

**但"关单"和"改 credit"不行**——那两个必须第二人。

## 四、"自动更新到我本地"怎么做

**你要的是本地也有一份最新的。** git 本身就是干这个的：

```bash
# 一个 cron，每 10 分钟拉一次
cd ~/pool && git fetch origin && git merge --ff-only origin/main
```

**但有个重要细节：ff-only（只允许快进）。**

如果本地有人直接改过文件，`--ff-only` 会失败——**这正是你要的行为**，因为：
- 本地应该是**只读的**（所有改动都通过 PR 走远端）
- 一旦本地能直接改，就出现了两份真相

**所以纪律是：**

> **本地仓库只用来跑校验、看状态、生成网站。所有改动都在远端通过 PR 走。**

**"你这里 merge PR"其实不在本地做——在 GitHub/Gitea 网页上点一下就行。** 本地的 cron 只负责拉取。

## 五、验证器怎么在 PR 里跑（这是自动化的核心）

```yaml
# .github/workflows/validate.yml
on: [pull_request, push]
jobs:
  validate:
    steps:
      - run: python3 tools/validate --changed-only
```

**"changed-only" 是关键优化**：全量校验会随仓库增长越来越慢，**只校验这个 PR 碰到的文件 + 它的链尾**。

### 5.1 自动合并的两档实现

| 档 | 实现 |
|---|---|
| **自动**（`site/` / `INDEX.md` / `digest/`） | Actions 里生成 + 用 `GITHUB_TOKEN` 直接 commit。**或用 Cloudflare Pages 的构建钩子，根本不进仓库** |
| **本人自批**（开单） | PR 由开单人自己合，但**分支保护要求 validate 通过** |
| **他人复核** | CODEOWNERS 要求 `data/` 至少 1 个他人批准；`data/credits.jsonl` 和 `policies.jsonl` 要求 **2 个** |

**★ 建议：`site/` 和 `INDEX.md` 不进仓库，让 Cloudflare Pages 在构建时生成。** 这样仓库干净，而且不需要给 Actions 写权限（少一个安全隐患）。

## 六、★ 一个必须先定的技术选择：签名的形态

**这是最容易在实施第一天卡住的地方。**

`git commit -S` 支持 **GPG** 和 **SSH** 签名，但：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 每条记录内嵌 Ed25519 签名**（我们的 schema） | ✅ 跨平台、跨工具 | 需要写个小 CLI 帮人签 |
| **B. git commit 签名**（GPG/SSH） | ✅ 平台原生验证、显示"Verified" | ⚠️ 门槛高：生成密钥、配置 git、上传公钥 |
| **C. 两者都要** | 最强 | 门槛最高，**新人会被劝退** |

**★ 我建议：A 必需，B 可选。**

理由：
- **A 已经提供了全部需要的性质**（不可抵赖、防冒充、脱离 git 也能验）
- **B 的额外收益只是"平台上显示一个 Verified 徽章"**
- **但它会拦住一半想参与的人**——而你们现在最缺的是人

**所以：提交时必须带记录内签名（A），CI 校验它；git commit 签名（B）鼓励但不强制。**

**配套：写一个小工具帮人签，一条命令：**

```bash
python3 tools/sign data/requests.jsonl    # 生成密钥（首次）、签名、追加
```

**★ 这个小工具是"新人能不能进来"的关键。** 它必须在 5 分钟内跑通，否则整套东西就只是三个人的玩具。

## 七、仓库长什么样

```
pool/
├── README.md               ★ 第一屏 = 当前公告板（构建时生成）
├── MAINTAINERS.md          谁管哪个板块
├── CODEOWNERS              谁的批准算数（从上一份生成）
├── CONTRIBUTING.md         ★ 新人 5 分钟指南（最重要的一份文档）
├── policies.jsonl          十一条规则
├── data/
│   ├── requests.jsonl
│   ├── deliverables.jsonl
│   ├── credits.jsonl
│   └── keyring.jsonl
├── .github/
│   ├── ISSUE_TEMPLATE/     ★ 开单表单（不用开发前端）
│   ├── PULL_REQUEST_TEMPLATE.md
│   └── workflows/validate.yml
├── tools/
│   ├── validate            约 200 行
│   ├── sign                约 80 行（新人用这个）
│   └── build-site          约 60 行
└── (site/ 与 INDEX.md 不提交，构建时生成)
```

## 八、落地步骤（今天能做完前三步）

```
第 0 步  本地 git init --object-format=sha256
         写 policies.jsonl（十一条）+ keyring.jsonl（只含你自己）
         第一个提交用你的密钥签名 → 这就是 genesis
         ★ README 里写明"这是第 0 号提交"

第 1 步  写 tools/validate（先只做 p-001 / p-002 / p-003）
         ★ 这三条通过，地基就成了

第 2 步  ★ 本地空跑一张真单子：
           开单 → 自己接 → 交付 → 第二个人复核（可以就是另一个本地密钥）
         判不了 = acceptance 写得不合格 → 回去改，不要往下走

第 3 步  推 GitHub，开分支保护：
         · main 必须走 PR
         · validate 必须通过
         · data/ 需 1 人批准，credits 与 policies 需 2 人
         · 禁止 force push、禁止删除分支保护

第 4 步  Cloudflare Pages 接上仓库 → 构建 site/ → 得到公开网址

第 5 步  写 tools/sign，找个真人跑一遍（★ 卡住就是这套东西的真实瓶颈）

第 6 步  本机 cron：每 10 分钟 git fetch && merge --ff-only

第 7 步  镜像：Gitee 再推一份 / 别人自己 clone
```

**★ 第 2 步和第 5 步是真正的验证点。** 第 2 步验证"验收标准可判定"，第 5 步验证"新人能不能进来"。

## 九、需要你确认（六条）

1. **★ 托管选哪个**：先 GitHub（0 成本、今天能用），还是直接自建 Gitea（要 VPS，但国内可达）
2. **★ 签名形态**：只记录内签名（我建议），还是连 commit 签名一起要求
3. **自动合并的范围**：`site/` 和 `INDEX.md` 是否不进仓库、由 Cloudflare 构建时生成（我建议不进）
4. **开单是否本人自批**（我建议允许，因为它只是一句声明）
5. **Cloudflare 用 Pages 还是 Workers**（Pages 更简单，够用）
6. **镜像要不要现在就做第二份**（Gitee 或另一个 GitHub 账号）

---

## 十、一句话

> **git 托管在 GitHub（或 Gitea），Cloudflare 负责展示和下载——它不接受 push，别指望它托管仓库。**
> **"自动"和"要 merge"的分界线是：有没有人的签名在上面。有签名的走 PR，纯推导的可以自动。**
> **本地只读：cron 定时 `fetch --ff-only`，所有改动都在远端走 PR。**
> **而实施第一天最容易卡住的是签名——所以必须有一个"5 分钟能跑通"的签名小工具，否则这套东西就只是三个人的玩具。**
