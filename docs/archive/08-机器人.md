# 内部机器人：它是什么、不能做什么、靠什么自发

> 你在 09-16 的原话是"可以有域名之类的，**有机器人和资料保存和处理**"。
> 这一份回答"机器人是什么情况"，并且要说清一件事：**"自发运行"和"本地优先"是有张力的。**

---

## 零、先说清楚机器人是什么

**它不是客服，不是聊天助手，不是自动执行者。**

> **机器人是这套系统的"钟"——它负责让"没人看的东西"变得可见。**

理由和一整套设计一致：你们的核心问题是**记录会积累，但看记录的人不会**。申请单过期、异议没人回、复核堆着、产物通过了但没人用——**这些都不是错误，是没人注意到。**

**机器人不修这些，它只是让这些变得刺眼。**

**所以它的唯一功能是：定期产出"该做什么"的清单。**

---

## 一、它能做什么（九条告警，全部纯机械）

| # | 告警 | 判据 | 为什么这条重要 |
|---|---|---|---|
| 1 | **单子快过期** | `open` 超 7 天未 claim | 需求方会以为没人理 |
| 2 | **单子已过期** | `open` 超 30 天 | 需要人决定：关掉，还是改验收标准重开 |
| 3 | **复核堆积** | `delivered` 超 3 天未 review | 交付者的动力全靠这个 |
| 4 | **等确认** | `review pass` 但需求方未 confirm | 差一步就成案，最容易被忘 |
| 5 | **异议未回应** | 超 7 天无 `responds_to` | 直接对应约束第 7 条 |
| 6 | **维护者日志未公示** | 周期结束未公示 | 直接对应约束第 8 条 |
| 7 | **★ 通过了但没人用** | `review pass` 且 `reuse = 0`，且已过一个周期 | **最有价值的一条，见下** |
| 8 | **问题提了没人接** | `artifact_kind = question` 且无引用 | 问题是最稀缺的，不能让它沉底 |
| 9 | **可能是重复的** | 两条 `open` 单的 title/spec 相似度高 | 重复会让同一件事没人做 |

### ★ 第 7 条值得单独说

**"通过了但没人用"是这套系统里唯一能自动发现的真问题。**

因为：
- 复核通过 → 说明有第二个人看过，形式条件满足
- 需求方确认 → 说明提出的人满意了
- **但复用 = 0 → 说明它对别人没用**

**三者同时成立，就是一个信号：我们在生产"自己能验收、别人不需要"的东西。**

**这个信号不会自己浮现——因为每个人都在做自己那一环，没人看整体。** 只有机器人会问："上周期通过的 5 件，有几件被引用过？"

**这是机器人存在的全部理由。** 其他八条都是它可以顺便做的。

## 二、它绝对不能做什么（三条硬边界）

| 边界 | 规则 | 为什么 |
|---|---|---|
| **1. 不能改状态** | 只能读 `data/`，只能写 `state/` 和 `digest/` | 一旦它能改状态，**判断就从"写下来"变成了"隐含在代码里"**——而你们要的是前者 |
| **2. 不能判交付物** | **不能做复核者** | 见下 |
| **3. 不能自动关单** | 过期只报告，不自动 `expire` | 关单是判断。**"自动关掉"等于把判断藏在定时任务里** |

### ★ 第 2 条需要你决定，因为它和一条已有规则冲突

架构里定的 `p-003` 是"**复核者 ≠ 交付者**"。问题来了：

- 如果交付者是人、复核者是模型 → **形式上满足**（不同主体）
- 但如果这套模型和当初**生成**这份产物的模型是同一个 → 实质上是自审

**两个选项：**

| 选项 | 规则 | 代价 |
|---|---|---|
| **A. 只有人能复核**（我建议 v1 用这个） | 模型永远不是复核者 | 慢；三五个人时是瓶颈 |
| **B. 模型可复核，但必须不同源** | 复核模型 ≠ 生成模型家族 | 复杂；且"不同源"很难验证 |

**建议 v1 走 A，把 B 留到活跃成员 > 3 人之后再说。**

理由：你们现在**最缺的不是产能，是"这条记录值不值得信"**。而人复核是唯一能让"可信"这件事站得住的。**等到产能真的成为瓶颈，再引入模型复核，并且那时你已经有了足够多的"人复核"样本来校准模型复核的准确率。**

**顺序不能反。**

## 三、"自发运行"是什么情况

**"自发"和"本地优先"有直接张力。** 一个能自己按时醒来的东西，需要一台**常开的机器**。

| 方案 | 自发程度 | 需要什么 | 评价 |
|---|---|---|---|
| **手动跑** | ✗ | 你记得 | 会忘。但只要一周一次就够 |
| **本机 cron** | ✓ | 一台开着的电脑 | **★ v1 用这个。零成本** |
| **git hook** | 半 | 有人 push 才触发 | 补漏可以，不能当主调度 |
| **服务器常驻** | ✓✓ | **服务器** | **这就是"自发运行"的真实代价** |

**★ 这里有个必须点破的等价关系：**

> **"机器人自发运行" ≈ "租服务器"。**
> 因为"自发"需要的不是机器人，是**一台不关机的机器**。

所以这**不是一个独立决定**。它和前面那份承载文档里"什么时候才租服务器"是同一个决定，而且它现在多了一个触发条件：

> **触发条件 ⑤：需要机器人自发运行。**

**我的建议：v1 先用 cron，一周跑一次，产出 `digest/` 下的一份 markdown。** 这份 markdown 就是"本周该做什么"。

**为什么一周一次就够：** 因为所有告警的阈值都是天级的（3 天、7 天、30 天）。**每天跑和每周跑，结果几乎一样。** 而每天跑会让人麻木——**告警的价值来自稀缺，不来自频率。**

## 四、它跑出来的东西长什么样

```
digest/2026-09-23.md

# 本周该做的事

## 卡住的
- r-0004 已等待复核 5 天  ← 交付 d-0009
- r-0002 已 open 12 天无人接

## ★ 上周期通过了但没人用（3 件）
- d-0003  术语辨析：无对价行动
- d-0005  锚点校验脚本 v1
- d-0008  英译对照表（前 20 条）
  → 这三件都有第二人复核、需求方也确认了，但没有任何产物引用。
  → 要么是我们需要的东西和别人不一样，要么是它们没被看见。

## 需要人决定的
- r-0006 已过期 33 天：关掉，还是改 acceptance 重开？
- 异议 obj-0003 已 9 天未回应（维护者：请回应，哪怕驳回）

## 可能重复
- r-0007 和 r-0009 的 spec 相似度 0.81，建议合并
```

**★ 注意最后那段的措辞：它不下结论，它提出两种可能。**

**机器人永远只描述状态，不做判断。** 这是它安全的原因——**它报告"3 件产物没人用"，不说"所以我们做错了"。** 判断留给人。

## 五、多写者问题（这个必须现在处理，否则一拉人就崩）

**六份 JSONL 都是 append-only，但 `seq` 和 `prev` 让它们变成单写者结构。** 两个人同时 append 会直接冲突。

### 为什么不能自动合并

理论上 append-only 日志是 CRDT，可以合并。**但这里不行：**

- 每条记录的 `hash` 包含 `prev`
- `prev` 指向同文件上一条
- 合并后 `seq` 要重编 → `prev` 要重链 → **`hash` 变了 → 签名全失效**

**重链会摧毁签名，而签名是这套东西的全部意义。**

### 三个选项

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. 单写者节点**（建议 v1） | 只有一台机器有写权限；其他人交提案，由写者落账 | 写者是瓶颈；但三五个人时够用 |
| **B. 每人一份日志，周期合并** | 各自 append，周期把多份日志按时间归并 | 归并同样破坏哈希链，要改 schema（不链，只签名） |
| **C. 服务器 + API 串行化** | 服务器做唯一写者 | **需要服务器** |

**建议 v1 走 A。** 它和"agent 只提案不落账"是**完全同一个机制**——反正你们已经需要一个不可自动化的落账环节了，写者节点就是那个环节的自然延伸。

**而且 A 有个额外好处：它让 git 冲突不可能发生。** 一个人写，永远不冲突。

**B 是将来人多时的方向**，但它需要改 schema：**去掉 `prev` 链，只保留签名，把链交给 git 和周期 Merkle root。** 这个改动现在不做，但要知道它是**为将来留的门**——所以 `prev` 字段即便现在必需，也不要让 core 逻辑过度依赖它。

## 六、机器人要不要进账本

**不要。**

- 它不产出 `deliverable`
- 它不拿 credit
- 它不该有 `member` 记录

**它是一段定时运行的代码，不是一个成员。**

理由：一旦机器人有身份，就会有人问"它能不能复核""它的 credit 归谁"——**而这两个问题都没有好答案，且都是自找的。**

**唯一的例外**：如果将来某个模型真的产出了被采纳的产物（经人复核），**那时它是"工具"，credit 归操作它的人。** 这也和"模型是成本项还是产能"的讨论一致——**v1 就按工具算，别给身份。**

---

## 七、一句话

> **机器人是这套系统的钟，不是手。它只让"没人看的东西"变得刺眼。**
> **它最独特的作用是发现"通过了但没人用"——这是唯一能自动发现的真问题。**
> **它不能改状态、不能当复核者、不能自动关单。**
> **"自发运行" ≈ "租服务器"，因为自发需要的不是机器人，是一台不关机的机器。**
> **v1：cron 一周一次 + 单写者节点 + 机器人不进账本。**

---

## 八、还差你定的

1. **复核权**：v1 是否只允许人复核（我建议是，模型复核留到活跃成员 >3 人）
2. **自发程度**：接受"cron 一周一次"，还是"必须随时在跑"（后者等于决定租服务器）
3. **多写者**：v1 用单写者节点（我建议），还是直接上服务器 API
4. **机器人是否公开**：它的 digest 是发群里，还是只写文件
