# 架构：本地自建 Gitea

> 已确认：**托管用本地自建 Gitea** · **签名只用记录内签名** · **Cloudflare 用 Pages**。
> 这个组合有一个必须解决的技术冲突，本文给出答案。

---

## 一、★ 先说冲突：Cloudflare Pages 拉不到你本地的 Gitea

**Cloudflare Pages 只有两条取代码的路：**

| 方式 | 说明 |
|---|---|
| **Git 集成** | 连 GitHub / GitLab / **自建 GitLab** —— **不支持任意自建 Gitea** |
| **Direct Upload** | 你本地构建好，用 `wrangler pages deploy` 推上去 —— **不依赖任何 git 托管** |

**所以"Pages 从本地 Gitea 自动构建"这条走不通。**

**但有个好消息：走不通的只是"自动"，展示这件事有两个零成本的解法。见第三节。**

---

## 二、架构（三样东西，各就各位）

```
┌─────────────────────────────────────────────────────────┐
│  ① 真相层（你的本地磁盘）                                  │
│     data/*.jsonl  +  git 仓库                             │
│     ★ 唯一真相。所有改动最终落在这里                        │
└────────────────────┬────────────────────────────────────┘
                     │ git push / pull
┌────────────────────▼────────────────────────────────────┐
│  ② 协作层（Gitea）                                        │
│     issue（开单）· PR（交付）· CODEOWNERS（谁批）           │
│     ★ 别人在这里参与。必须公网可达                          │
└────────────────────┬────────────────────────────────────┘
                     │ Gitea 的"推送镜像"功能（内置，自动）
┌────────────────────▼────────────────────────────────────┐
│  ③ 展示与分发层（Cloudflare）                              │
│     Pages：公开网站（可浏览、可查账）                       │
│     ★ 只读。不接受 push                                    │
└─────────────────────────────────────────────────────────┘
```

**关键分工（很重要）：**

| 层 | 干什么 | 不干什么 |
|---|---|---|
| **本地** | 存真相、跑校验、生成网站 | **不接受别人的 push** |
| **Gitea** | 收 PR / issue、评审、合并 | **不做展示**（它的 web 很朴素） |
| **Cloudflare** | 好看、快、可分享、可下载镜像 | **不做协作**（没有 issue/PR） |

**★ 一句话：Gitea 是"工作台"，Cloudflare 是"橱窗"。**

---

## 三、★ Cloudflare Pages 怎么接（两个方案，选一个）

### 方案 A：Gitea 自动镜像到 GitHub，Pages 从 GitHub 构建

**这是我最推荐的，因为它一石三鸟。**

```
本地 Gitea（权威，收 PR）
      │  ★ Gitea 内置"推送镜像"功能，自动同步
      ▼
GitHub（只读镜像，公开）
      │  Cloudflare Pages 原生支持
      ▼
公开网站
```

**三个好处：**
1. **Pages 的 Git 集成直接可用**（从 GitHub 构建，零配置）
2. **顺带有了官方镜像**——而且**镜像这件事本身是防篡改的核心**（前面定的：副本越多，改账越难）
3. **不额外花任何成本**

**注意方向不能反：镜像方向是 Gitea → GitHub。** GitHub 那份是**只读副本**，权威永远在 Gitea。

（Gitea 的"推送镜像"是内置功能，配置一个地址和 token 就行。）

### 方案 B：Direct Upload（彻底不依赖任何外部托管）

```
本地构建 → wrangler pages deploy dist/ → 公开网站
```

**优点：** 完全自主，不需要 GitHub 账号，不需要 Pages 的 git 集成。
**缺点：** 每次要你手动（或 cron）跑一次部署命令。

**★ 建议：先 A，实在不想用 GitHub 再 B。或者两个都做——成本都是零。**

---

## 四、★ 但"本地自建 Gitea"有一个硬条件：机器必须在公网可达

**别人要能提交 PR，就必须能访问你的 Gitea。这就是"本地"和"公网服务"的张力。**

### 4.1 三种做法

| 做法 | 能公网可达吗 | 成本 | 备注 |
|---|---|---|---|
| **① 本机 + Cloudflare Tunnel** | ✅ | 0 | 不需要公网 IP、不需要开端口 |
| ② 本机直接开端口 | ⚠️ 常常不行 | 0 | 家宽多数是 CGNAT；80/443 常被封 |
| ③ 便宜境外 VPS | ✅ | ¥30～80/月 | 最稳，但不叫"本地"了 |

**① 是唯一能同时满足"本地自建"和"公网可达"的路。** Cloudflare Tunnel 的做法是：本机跑一个 `cloudflared` 守护进程，主动向 Cloudflare 建一条隧道，**不需要公网 IP、不需要改路由器**，外面通过你的域名访问进来。

**这正好也用了你本来就有的 Cloudflare —— 一个账号把 Tunnel 和 Pages 都办了。**

### 4.2 但四件事必须摆明

| 问题 | 说明 |
|---|---|
| **★ 机器必须常开** | 关机 = 别人打不开 = **PR 提交不了**。这不是"偶尔"，是"这个服务不存在" |
| **家宽不稳** | 断电、掉线、运营商维护，都会让协作中断 |
| **★ 法律边界** | 本机对外提供服务，**性质上仍然是"公网服务"**。没备案的域名提供 web 服务，和"自己服务器自己用"不是一回事 |
| **单点** | 你的电脑挂了，权威仓库就挂了 |

**★ 第三行值得单独说。** 你 09-16 说"自己服务器自己用，违鸡巴法"——**那个判断对"自己用"成立，但对外提供服务是另一回事**。Cloudflare Tunnel 绕过了端口封锁和 CGNAT，**但不改变法律性质**。

**我不劝你，只要求这个选择是知情的。**

### 4.3 我的建议

```
现在       本机 + Cloudflare Tunnel（零成本，验证整套流程）
              ↓ 当出现下面任一条
迁移到     境外 VPS 上的 Gitea（¥30～80/月）
              · 别人抱怨访问不稳
              · 你不想让机器常开
              · 参与人数超过 3～5 人
              · 数据量超出本机舒适区
```

**★ 迁移成本极低，因为 Gitea 的数据就是一个目录。** 换机器 = 拷目录 + 改 DNS。

**这也是这套架构的一个隐含优点：所有组件都是可替换的，唯一不可替换的是 `data/` 里的格式。**

## 五、完整数据流（一次别人提交的 PR）

```
① 别人在你 Gitea 上开 issue（= 开单）
      用 ISSUE_TEMPLATE 表单，强制填"缺什么 / 怎么算做完了"
                ↓
② 他 clone 仓库，本地跑 tools/sign 追加一行到 data/requests.jsonl
      ★ 用他自己的私钥签（记录内签名）
                ↓
③ 他提 PR 到你的 Gitea
                ↓
④ Gitea Actions 跑 tools/validate
      ★ 校验：链接得上吗、签名有效吗、acceptance 非空吗
                ↓
⑤ CODEOWNERS 要求第二人批准（deliverables / credits 必须）
                ↓
⑥ 你（或指定维护者）合并 → 进 main
                ↓
⑦ Gitea 自动推镜像到 GitHub → Cloudflare Pages 构建 → 网站更新
                ↓
⑧ 你本机 cron：git fetch && merge --ff-only
```

**★ 第 ⑧ 步的方向：你的本机也在拉取。** 所以本地不是"发布源"，是**另一个副本**——**这和"镜像越多越安全"是一致的**。

## 六、目录与组件清单

```
pool/                          本地仓库（真相）
├── README.md                  ★ 第一屏 = 当前公告板
├── MAINTAINERS.md             谁管哪个板块
├── CODEOWNERS                 谁的批准算数
├── CONTRIBUTING.md            ★ 新人 5 分钟指南
├── policies.jsonl             十一条规则
├── data/                      四份 JSONL ← 唯一真相
├── .gitea/workflows/          Gitea Actions（跑 validate）
├── .github/ISSUE_TEMPLATE/    ★ 开单表单（不用开发前端）
├── tools/
│   ├── validate               约 200 行
│   ├── sign                   ★ 约 80 行 —— 新人唯一的门槛
│   └── build-site             约 60 行
└── site/                      构建产物（不提交）

外部组件
├── Gitea（本机 Docker 或二进制）  协作层
├── cloudflared（隧道）            让 Gitea 公网可达
├── GitHub 镜像（Gitea 自动推）     分发 + Pages 源
└── Cloudflare Pages              橱窗
```

**★ 全部零成本（除了将来可能的 VPS）。**

## 七、本地只读纪律（不能破）

```bash
# 本机 cron，每 10 分钟
cd ~/pool && git fetch origin && git merge --ff-only origin/main
```

**`--ff-only` 是关键**：如果你本地直接改过文件，它会失败——**这正是要的**。一旦本地能直接改，就出现两份真相。

> **纪律：本地只用来跑校验、看状态、生成网站。所有改动都通过 Gitea 的 PR 走。**

**（例外：你自己作为维护者的改动也是 PR。唯一可以直接做的，是重建 `site/` 这类纯推导产物。）**

## 八、需要你确认

1. **★ Gitea 放哪**：本机 + Cloudflare Tunnel（零成本，但机器要常开），还是直接上 VPS
2. **★ Pages 接法**：方案 A（Gitea → GitHub 镜像 → Pages，我推荐）还是方案 B（Direct Upload）
3. **Gitea Actions 还是不用 CI**（建议用，否则校验只能靠人跑）
4. **关于"开单需要你看情况"**——你这句话我没完全确认意思。是指：
   - (a) **你自己开单时**是否需要别人批 → 我建议**开单本人自批**（它只是一句声明）
   - (b) **别人开单时**要不要你审 → 我建议**自动合入**，因为开单不产生 credit
   **请指一下是哪个。**

## 九、一句话

> **Gitea 是工作台，Cloudflare 是橱窗，本地是真相。**
> **Three 层都零成本，但"本地 Gitea"有一个硬条件：机器必须常开且公网可达——用 Cloudflare Tunnel 能做到，代价是它变成了一个真正的公网服务。**
> **Cloudflare Pages 拉不到你的本地 Gitea，解法是让 Gitea 自动镜像到 GitHub，Pages 从那里构建——顺手拿到第二份镜像。**
> **而本地也只是一个副本：cron 定时 `fetch --ff-only`，所有改动都走 PR。**
